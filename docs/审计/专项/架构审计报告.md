## 1. 总评

工程纪律是亮点：规则层刻意写成纯 C# 静态类配大规模测试、无头验证台、EventBus 快照遍历、
Domain Reload 关闭时的静态清理意识、事件契约登记意识——这些在同类作品集项目里少见。

核心问题不在纪律意识，而在**这些纪律没有被工程结构固化，靠文档和自觉维持**：
模块化没有程序集边界（单 asmdef）、场景组装是「生成式场景 + 顺序敏感脚本链」、
全局生命周期三套并存、组合根（Bootstrapper）名存实亡。
其中第 1、4、5 号问题会随 M4 大海世界化继续加系统而滚大，修得越晚越贵。

### P0-1 「模块化」没有程序集边界，分层只是纸面约定

**现象**：全部运行时代码在单个 `PirateCrew.Runtime.asmdef` 里
（`Assets/Scripts/PirateCrew.Runtime.asmdef`，references 仅 Cinemachine/TextMeshPro）。
唯一例外是 `PirateCrew/Rendering/PirateCrew.Rendering.asmdef`（因需引用 URP 包）。
AGENTS.md 定的「Core ← 玩法模块 ← UI」分层，编译器完全无法检查。

**违规已发生——低层依赖高层**：`BattleController.cs:3-5` 直接
`using PirateCrew.Campaign; using PirateCrew.CrewManagement;`，并在：
- `BattleController.cs:251` 调 `CampaignApi.PendingBattleLevelNumberOr(fallbackLevelNumber)`；
- `BattleController.cs:494-497` 读 `CampaignApi.PendingLevelId`、`CrewManagementApi.Roster.Active`。

战斗模块（被编排的低层玩法）反向依赖了战役模块（编排高层），方向违反
「高层可依赖低层，反向禁止」。正确方向是 Campaign 把选关结果、出战名单**注入** Battle
（数据传入或中立请求对象），而不是 Battle 主动伸手拉高层状态。

**修复方向（提案/待定）**：每模块一个 asmdef——`PirateCrew.Core`（零模块引用）、
`PirateCrew.PirateCrew`（仅引 Core）、`PirateCrew.Campaign`、`PirateCrew.CrewManagement`、
`PirateCrew.UI`；拆分前必须先修上面的反向依赖。asmdef 是 Unity 里把架构原则变成编译约束的标准手段，
成本低收益大，且「用 asmdef 强制分层」本身是简历可讲的工程点。

### P0-2 场景组装：生成式场景 + 顺序敏感三步脚本链 + 3.4 万行场景入库

**现象**：
- `Assets/Scenes/Battle.unity` 有 **34539 行**（对比：Bootstrapper.unity 220 行、
  CrewManagement.unity 1849 行、LevelSelect.unity 4002 行、MainMenu.unity 8030 行）；
- 交接文档 §2.1 明确记录战斗场景由 Editor 脚本链生成：
  `Editor/BattleSceneSetup.BuildAll → Editor/HudMinimapSceneSetup.WireMinimap → Editor/ManagementSceneSetup.BuildAll`，
  且「**顺序敏感**：前两步会重建/增量接线 Battle，最后一步写构建列表」。

**为什么这是问题**（问题在组合，不在「程序化生成」本身）：
1. 场景文件是**生成产物**却被当真源入库；手工在编辑器里摆的任何东西，下次跑 Setup 链可能被覆盖或漂移；
2. 接线知识活在一次性 Editor 脚本里，而不是 Unity 原生的 Prefab + `[SerializeField]` 连线——
   等于放弃了引擎最核心的场景组装与复用能力；
3. 程序化装配没有静态引用可连，直接催生 P2-7 的 `FindObjectOfType` 存量（因果链证据：
   `FxRoot.cs:27` 注释自述「battle_started 时用一次 FindObjectOfType<BattleController> 建立」）；
4. 求职展示角度减分：面试官打开 Battle.unity 看到的是脚本生成的巨型扁平层级，
   体现不出 Unity 场景组织能力。

**修复方向（提案/待定）**：稳定结构（HUD、相机 rig、队伍挂点、服务宿主）固化成 Prefab 并在
Prefab 内连好 `[SerializeField]`；Setup 脚本只保留「按关卡参数生成内容」的部分；
写明「哪些结构归生成、哪些归手工」的契约（落进 AGENTS.md 或场景 README）。

### P0-3 全局生命周期三套并存，组合根失效

**现象**：`Core/Bootstrapper.cs:64-74` 只创建 SceneLoader 和 SaveManager 两个服务；
其余全局状态各自为政，共三套生命周期机制并存：

| 机制 | 使用者 |
| --- | --- |
| Bootstrapper 单例 + DontDestroyOnLoad | SceneLoader、SaveManager |
| 静态可变状态 + `[RuntimeInitializeOnLoadMethod]` 自清 | CampaignApi、CrewManagementApi、AudioService、FxBootstrap、FxRoot、BattlePause、EventBus、PlayerArtCapture、SceneKitPilotCapture（共 9 个文件） |
| 场景内 Setup 脚本装配 | Editor/BattleSceneSetup 等 4 个 Setup 脚本 |

两个具体风险：
1. 每个「Reset 手法」各写一遍（对照 `Core/EventBus.cs:112-116` 与 `Campaign/CampaignApi.cs:327-331`），
   漏写一个就是 Domain Reload 关闭时的脏状态；
2. **接线入口埋在 UI 层**：`Campaign/CampaignApi.cs:89-91` 自述「EnsureBootstrapped 由 UI 层
   （主菜单/管理界面）在 Awake 调用」——没人打开主菜单，`battle_started → crew_died → match_finished`
   的整条结算链就不接线。组装顺序靠「用户恰好会走这个流程」保证，而非结构保证。

**修复方向（提案/待定）**：全局状态收敛到 Bootstrapper 显式组装（哪怕内部仍是静态外观，
也由 Bootstrapper 统一调用 Ensure）；接线从 UI.Awake 挪到 Bootstrapper 或场景装载入口。

### P1-6 EventBus：弱类型没换来解耦，Core 层带头违反自己的事件规范

三个层次的问题：

1. **载荷弱类型**：`Core/EventBus.cs:21` payload 为 `object`，注释还「建议用 Dictionary」。
   后果已现形：`"change_scene"` 一个事件**两种载荷类型**——`string`（场景名）或
   `Dictionary<string,object>`（带 replaceTop 标志），见 `Campaign/CampaignApi.cs:123-138`，
   订阅方 `Core/SceneLoader.cs` 只能对载荷做类型嗅探。

2. **Core 层自己用魔法字符串**：`Core/SaveManager.cs:165,183,292` 发布
   `"save_completed"` / `"load_completed"` / `"auto_save_triggered"`；
   `Core/SceneLoader.cs:81-88` 订阅、`SceneLoader.cs:270-282` 发布
   `"change_scene"` / `"go_back"` / `"scene_load_started"` / `"scene_load_completed"` /
   `"scene_transition_finished"`。AGENTS.md 明令「代码侧用常量类承载（如 BattleEvents.cs），
   禁止散落魔法字符串」——最讲规矩的 Core 层带头违规。
   另外 `docs/技术/架构/EventBus事件契约.md` 登记表存在重复登记行
   （`battle_started`、`crew_died`、`match_finished` 各出现两次）。

3. **根本问题——字符串总线没有换来真解耦**：发布方与订阅方共享载荷类型
   （`CrewDiedPayload`、`MatchFinishedPayload` 等跨模块引用），编译期耦合本来就没断；
   字符串键只带来「拼错即静默失败」的运行时风险，没换来编译期收益。

**修复方向（提案/待定）**：二选一——
a) 强类型事件总线：事件常量与载荷类型一一对应的泛型总线（`Publish<T>(T payload)`），
   拼错事件/载荷不匹配直接编译失败；
b) 承认这些是强关系，模块间直接接口调用（EventBus 只留真正「多对多广播」的场景）。
无论选哪个，先给 Core 补上事件常量类、清理契约表重复行。
