## 三、发现

### F-1 装配链是"三步 + 顺序敏感"，但顺序敏感只在第一步与第二步之间

实测三个脚本的职责：

| 脚本 | 对 Battle.unity 做什么 | 幂等性 |
| --- | --- | --- |
| `M2BattleSceneSetup.BuildAll` | `EditorSceneManager.NewScene(EmptyScene)` **全量重建**（`M2BattleSceneSetup.cs:201`），末尾 `SaveScene` | 幂等（每次都从空场景重造） |
| `HudMinimapSceneSetup.WireMinimap` | `OpenScene` 后**增量**补小地图面板/层级/引用，不重建 | 幂等（按名复用，`HudMinimapSceneSetup.cs:243-297`） |
| `M3SceneSetup.BuildAll` | 只建 CrewManagement / LevelSelect 两个场景 + 写 Build Settings 5 场景；**不碰 Battle**（`M3SceneSetup.cs:1-29`） | 幂等 |

所以"顺序敏感"的真实约束是：**第二步必须在第一步之后**（否则没有场景可增量接线）；
第三步与 Battle 无关（交接文档 §2.1 把它写进链里是因为它写 Build Settings 列表）。
契约结论：**第一步重建后必须重跑第二步**，这是一条需要被测试或工具钉住的隐式约定（现在没有任何东西钉它）。

### F-2 关卡内容被烘进 HUD：163 个 `IslandTile_*` + 按关卡 1 定尺寸的小地图

`HudMinimapSceneSetup.BakeIslandTiles` 用 `FallbackLevelNumber = 1`（`HudMinimapSceneSetup.cs:56`）
把 level_1 的岛格逐格烘成 `Image` 存进场景（`HudMinimapSceneSetup.cs:376`），实测 **163 格**
（`DotLayer/IslandLayer` 下，命名模式 `IslandTile_<gx>_<gy>`）。

后果有三条，都是实测可见的：

1. 世界地图模式必须**按字符串前缀把它整层关掉**——这就是 `BattleController.cs:420` 那处
   `FindObjectsOfType<Image>(true)` + `name.StartsWith("IslandTile_")` 的由来，
   注释自述"它按原版关卡网格烘死"；
2. `BattleMinimap.arenaWidth/arenaDepth` 同为 level_1 值（50×17 格，`HudMinimapSceneSetup.cs:623-624`
   写入），**运行期没有任何 setter 改它**（`BattleMinimap.cs:45-47` 只有序列化字段，
   公开面只有只读的 `DotLayer`/`TileLayer`/`DotCount`）→ 换关卡/换世界图后小地图的点位映射
   仍按 level_1 的竞技场尺寸换算（`BattleMinimap.cs:309`）；
3. 这条烘焙路径同时让 `BattleMinimap.terrain` 被显式清空（`HudMinimapSceneSetup.cs:634`），
   代价是"地形炸毁后小地图不更新"，已在交接 §13 登记为已知取舍。

### F-3 两处每帧 Find 的根因是"字段压根没序列化"——最便宜的修法

| 位置 | 现状 |
| --- | --- |
| `BattleCameraController.cs:397`（`AdvanceScopeBlend`，LateUpdate 路径）、`:412`（`UpdateChargeZoom`，Update 路径）、`:1107`（`UpdateManualCameraInput`） | 三处都是 `if (aimThrow == null) aimThrow = FindObjectOfType<AimThrowController>();`，而 `aimThrow` 是**裸私有字段**（`BattleCameraController.cs:901`，无 `[SerializeField]`）→ 场景里根本连不上，Find 是唯一通路 |
| `BattleHud.cs:331`（`SetHudMode`） | 同样：`_cameraController` 是裸私有字段（`BattleHud.cs:251`，无 `[SerializeField]`） |

**修法（提案）**：给这两个字段加 `[SerializeField]`，由装配脚本（阶段 3 后为 Prefab 连线）写入。
两处都是"懒加载兜底"，加了序列化字段后 Find 变成永不命中的死分支，可整体删除。

### F-4 两处 Find 的根因是"字段不存在"

| 位置 | 目标 | 目标在场景里的位置 | 修法（提案） |
| --- | --- | --- | --- |
| `BattleController.cs:379` | `AmbientDirector` | `SceneArt/Ambient`（`BattleController` 已持有 `sceneArt` 引用，`BattleController.cs:78`） | 加 `[SerializeField] AmbientDirector ambientDirector` 并在装配期写入 |
| `BattleController.cs:420` | 烘死的小地图岛层 | `BattleCanvas/MinimapPanel/DotLayer/IslandLayer` | `BattleMinimap` 加 `[SerializeField] RectTransform islandLayer`（`HudMinimapSceneSetup` 已持有该对象，只差一个字段，`HudMinimapSceneSetup.cs:152`），`BattleController` 经 `BattleHud`→小地图或直接持引用访问 |

两条都不需要改事件契约、不需要新资产，属"补一个字段 + 一行装配接线"的量级。

### F-5 三处 Find 属全局服务/环境兜底，性质不同，不能一刀切

| 位置 | 性质 | 评估 |
| --- | --- | --- |
| `WaterSimulationDriver.cs:446` | 平行光兜底（仅缓存失效时调用，且**已优先用 `RenderSettings.sun`**，`WaterSimulationDriver.cs:425`） | 已被 §21 批次 D 的"AmbientDirector 登记 RenderSettings.sun"覆盖到，可评估**直接退役**该兜底 |

### F-6 Prefab 实例 = 0：复用能力为零，且这是 P2-9 的量化证据

372 个对象、0 个 Prefab 实例、23 个根全部手摆式装配。`Assets/Prefabs/` 下只有

### F-7 26 条跨根引用 = Prefab 边界的天然切分线（可逐条核对）

```
相机 rig 内部 1 条
  BattleVCam → CameraTarget                         [CinemachineVirtualCamera.m_Follow]
服务宿主组 16 条
  TurnManager → BattleController                    [TurnManager.battle]
  AimThrowController → Main Camera / BattleController / TrajectoryPreview
  BattleCameraController → BattleVCam / CameraTarget / Main Camera / BattleController
  BattleController → Team0_Red / Team1_Blue / Water / TurnManager / AimThrowController
                   / BattleCameraController / Terrain / SceneArt
HUD 组 5 条
  BattleHud → BattleController / TurnManager / AimThrowController
  BattleMinimap → Team0_Red / Team1_Blue
世界/环境组 4 条
  AmbientDirector → Directional Light / Team0_Red / Team1_Blue / Main Camera
```

关键结论：**26 条全部是"场景内对象 → 场景内对象"**，没有一条指向别的场景或运行时单例。
这意味着**只要把这 23 个根收进同一个 Prefab，26 条引用会全部内化成 Prefab 内部连线**，
场景里剩下 0 条接线——这是本任务最小风险的第一步（见 §四 阶段 2）。

## 四、切分契约（提案/待定，待用户过审后写入 `Assets/Scenes/README.md`）

### 原则

1. **稳定结构归 Prefab，参数化内容归生成**：Prefab 持有"结构 + 相对关系 + 资产引用"；
   装配期只写"关卡参数"（尺寸/位置/材质）；运行期只造"内容"（单位/瓦片/陈设/FX）。
2. **不允许"生成脚本里连引用"成为长期状态**：Prefab 化完成后，装配脚本不再用 `SerializedObject`
   写稳定结构的引用（那是 Prefab 的职责），只负责实例化 + 写参数。
3. **Prefab 内不出现关卡数据**：任何由 `LevelCatalog` 推出的数值（尺寸、位置、瓦片数、
   小地图 arena 尺寸）都不许烘进 Prefab 的序列化值里。

### 方案：4 个 Prefab（`Assets/Prefabs/PirateCrew/Battle/`）

| Prefab | 含哪些根 | 对外槽位（场景/Prefab 变体上要连的） |
| --- | --- | --- |
| `BattleCameraRig.prefab` | `Main Camera` / `CameraTarget` / `BattleVCam` | 无（自带 1 条内部引用） |
| `BattleHudCanvas.prefab` | `BattleCanvas` 全树（含 `BattleHud` / `BattleMinimap`） | `battle` / `turnManager` / `aimController`（3）+ `minimap.unitRoots`（2） |
| `BattleWorldRig.prefab` | `Water` / `Seabed_Far` / `Seabed_L0..L4` / `Terrain` / `SceneArt`(+`Ambient`) / `Team0_Red` / `Team1_Blue` / `Directional Light` / `GlobalVolume` | `ambient.targetCamera` ← 相机 rig（1） |
| `BattleDirector.prefab` | `BattleController` / `TurnManager` / `AimThrowController` / `BattleCameraController` / `TrajectoryPreview` / `EventSystem` | 相机 rig（3：vcam / cameraTarget / fallbackCamera）+ 世界 rig（6：terrain / sceneArt / team×2 / water / ambient）+ HUD（3） |

跨 Prefab 引用合计 **约 14 条**，全部显式连线（Unity 原生 Inspector 连线，不是脚本写私有字段）。

**分两步走（推荐，等价性风险递减）**：

- **阶段 2a**：23 个根整体收进**单个** `BattleRig.prefab`（26 条引用全部内化，场景里 0 条接线）。
  这一步的价值是**用最小的行为风险拿到"原生连线"**，且等价性最容易证明（转储 diff 应只有
  "根对象变成 Prefab 实例"一类差异）。
- **阶段 2b**：在 2a 基础上按上表拆成 4 个嵌套 Prefab（组织性收益，P2-9 归位）。

### 生成侧契约（哪些仍然程序化生成，以及谁生成）

| 内容 | 生成者 | 时机 |
| --- | --- | --- |
| 关卡几何（瓦片平台、collider） | `PlatformClusterLayout` → `BattleTerrainView` | 运行期（换关即重建） |
| 场景陈设 | `RuntimeSceneArt.RebuildFor(关卡号)` | 运行期 |
| 单位 | `BattleController` + `PirateBase.prefab` + 8 个船员视觉 prefab | 运行期 |
| 世界地图灰盒/kit/远景环带 | `WorldMapComposer` / `HorizonFeatureRules` | 运行期 |
| 海洋（世界图） | `Water.OceanRig.Create` | 运行期 |
