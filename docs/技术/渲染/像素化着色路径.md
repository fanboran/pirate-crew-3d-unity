# 渲染管线 · 像素化着色路径

> **这份文档是什么**：**像素化着色路径**（v3 蓝本重写线）的实现口径——它是什么形状、每一趟在干什么、
> 缓冲怎么分、着色数学从哪来、怎么出图与判据，以及改它之前必须知道的几个**静默失效点**。
> **它回答的是"怎么改"**；"为什么选 v3 这条路"的论证在 [蓝图-新渲染管线-v3蓝本.md](蓝图-新渲染管线-v3蓝本.md)（下称**蓝图**）。
> **配套**：实拍图与实测判据 [docs/images/pixelart-path/r1/](../../images/pixelart-path/r1/README.md)；
> 与旧视觉链的关系见 §1；材质/场景装配在 `Assets/Editor/PixelartPilotSetup.cs`。

## 1. 这条路径是什么

**一句话：几何不投影不着色地写进低分辨率 G-buffer，全部着色在低分辨率域跑一趟，最后一次点采样放大上屏。**

与"全分辨率前向着色 + 事后降采"（旧链 `PirateToon` + `PixelationRendererFeature`）的分野不在用哪个 shader，
而在**着色发生在哪一档分辨率**：

| | 旧链（并行存在，本路径不引用其任何实现） | 本路径 |
|---|---|---|
| 物体 pass 的产出 | 最终颜色（全分辨率） | **数据**（albedo / 法线 / 逐物体参数，低分辨率） |
| 着色发生处 | 全分辨率 | **低分辨率域**（一趟全屏） |
| 降采之后 | 画面即最终结果，没有第二次着色机会 | 结果本来就是低分辨率算出来的 |
| 色带边界 | 靠"逐像素操作与 RT 块对齐"这条纪律兜住 | 天然落在低分辨率像素上，不需要块对齐补丁 |

代码位置：`pirate-crew/Assets/Scripts/PirateCrew/Rendering/Pixelart/`（程序集 `PirateCrew.Rendering`，命名空间 `PirateCrew.Rendering.Pixelart`）。

## 2. 执行顺序（双相机 + 四个 Feature）

一台相机的"视野"与"渲染分辨率"被拆成两台：

| | 主相机（上屏器） | Cast 相机（渲染代理） |
|---|---|---|
| 是什么 | 场景里那台相机（本路径的宿主） | **主相机的子物体、local 恒等** ⇒ 自动继承 Transform（v3 同一手法，`SloanePixelartCamera.cs:283-285`） |
| 相机设置 | `clearFlags = Nothing`、`cullingMask = 0`、后处理关 ⇒ **什么都不画** | 正交、与主相机同 size、`targetTexture = ResultBuffer` |
| 渲染器 | `PixelartScreen_Renderer`（只有上屏 blit） | `PixelartCast_Renderer`（另外三个 Feature） |
| 层掩码 | 0（不参与剔除） | **主相机被清掉之前的那份**（⇒ 几何只被 Cast 相机看到一次） |

> **为什么必须是两个渲染器**：两台相机若共用同一个渲染器，主相机会把刚画好的 G-buffer 清掉再着色一遍，
> 画面退化成纯背景色（且不报错）。这是结构性的，不是配置疏漏。

Cast 渲染器里三个 Feature 的时机与职责（**数组顺序 = 同一 `RenderPassEvent` 内的入队顺序**）：

| 序 | Feature | 时机 | 干什么 |
|---|---|---|---|
| 1 | `PixelartBeforeRenderFeature` | `BeforeRendering` | 视图矩阵平移分量 snap 到 1 低分辨率像素的整数倍（`cmd.SetViewProjectionMatrices`），下发 `_PixelartUnitSize` / RT 尺寸 |
| 2 | `PixelartObjectFeature` | `AfterRendering` | 清 Cast 相机颜色目标为背景色 → 绑 **3 张 MRT + 深度** → 按 renderQueue 分两段 `DrawRenderers`：**大平面本体**（队列 < 2000）先画完 → **描边壳**（`PixelartInk`）→ **描边物本体**（`PixelartOpaque`）→ 把三张设成 shader 全局 |
| 3 | `PixelartShadingFeature` | `AfterRendering` | 一趟全屏 blit：读三张 G-buffer 算最终色，写进 Cast 相机的颜色目标（= `ResultBuffer`） |

> **物体 pass 的三段绘制次序是描边成立的前提**（渲染篇 §5 的三条实测因果链，缺一条描边就断）：
> ① 大平面（地面/海面，`renderQueue = 1999`）必须先整体画完——它的本体是 `ZWrite On` 的，
> 若在壳之后画会把轮廓环整圈盖掉；② 壳**先**画、本体**后**画，重叠区由本体自然盖回、只余轮廓环；
> ③ 壳 `ZWrite Off` + 沿视线拉近 5× 线宽，才能在"轮廓外侧那圈像素压在地面上"时赢下深度。
> 次序由 `PixelartPath.BackgroundPlaneRenderQueue` / `ForegroundRenderQueueMin` 两个常量定义。

主相机侧：`PixelartScreenCopyFeature`（`AfterRendering`）用 URP 自带 `Hidden/Universal/CoreBlit` 的
**pass 0 Nearest** 把 `ResultBuffer` 点采样放大上屏——这就是"像素化"这个观感的物理来源。

## 3. 缓冲（5 张，全部低分辨率）

分配在 `PixelartCameraRig.EnsureBuffers`。尺寸口径：**锁"一个艺术像素占几个屏幕像素"这个整数倍数**
（`pixelScale`，现 5），RT 尺寸由**实际屏幕**反推。1920×1080 → 384×216、2560×1440 → 512×288、
3840×2160 → 768×432，块边长恒为 5 屏幕像素。
**不要再退回"锁 RT 高度"**：那套只在屏幕高是画布高的整数倍时成立（2560÷384 = 6.67 非整数 ⇒
块边长在 6/7 之间混排，症状是"全屏像素不齐、放大到 1:1 看却正常"）。
**档位定值见 `PixelartPilotScene.PixelScale`（装配器、出图脚本、判据脚本三方共用同一份）**。
可见范围另由 `worldPerPixel`（每艺术像素多少米）决定：**分辨率越高看到的范围越大**
（1080p 28m、1440p 37m），这是"艺术像素的世界尺寸固定"这条口径的直接结果。

| 缓冲 | 格式 | 内容 |
|---|---|---|
| `PixelartAlbedo` | `ARGB32`（UNorm8，sRGB 关） | rgb = 亮部色（墨线像素里是墨色）；**a = 1 表示这里有几何**（着色 pass 据此 clip 出背景） |
| `PixelartNormal` | `ARGBHalf` | 世界法线，原样存 `[-1,1]` |
| `PixelartProperty` | `ARGBHalf` | r = 色带档数、g = 抖动偏移（0..1，中心 0.5）、b = 法线边加成档、**a = 墨线标记（只有墨线 pass 写 1，本体必须写 0）** |
| `PixelartDepth` | depth 24 | 物体 pass 的深度附件（不透明物之间靠它分前后） |
| `ResultBuffer` | `ARGB32`、**`FilterMode.Point`** | 着色结果；Cast 相机的 `targetTexture`，上屏时点采样放大 |

**与 v3 的 15 张是什么关系**：v3 的 15 张里，7 张 MRT 中的**高光（Physical）、第 2 法线（法线贴图）、
lightmap UV、边缘光属性**在本路径都没有对应物——本仓已砍高光（渲染篇 §4.3）、不做法线贴图、
GI 简化为环境光项，而边缘光是 P4 的事。**优先级通道**（v3 的 `_UVBuffer` / `ShapeProperty.r`）在 v3 里
是一条死 pass 的输入（蓝图 §4.1），本路径不接。剩下的数据（albedo / 法线 / 逐物体参数）就是这 3 张。

**为什么不用 `SNorm16` + 字节打包**：v3 把"档数/抖动/AA 缩放"塞进 `SNorm16` 的同一批通道、
用法线与位标记共用，靠 core 的 `PackFloatInt8bit` 读写——那套打包与 MRT 格式强耦合，
随手换格式（哪怕换成 `UNorm`）就会静默失效（蓝图 §2 注意 1）。本路径用 16 位浮点（法线/参数）
与 8 位（albedo），**编解码一步都不需要**。

## 4. 着色数学（低分辨率域那一趟）

`PixelartShading.shader` 的片元，逐条对应 v3 `ShadingPass.hlsl:37-63` 的 `DiffuseShading`：

```
ndotl = saturate(dot(L, N))
ndotl = pow(ndotl, 1/2.2)                 // 让色带边界落在感知均匀的位置
ndotl += singleLevel * dither             // 抖动：偏移量 = 一个色带步长 × 逐物体图案值
ndotl = multiStep(ndotl, level, 0, 0)     // 量化成 level 档（= "色带"本体）
ndotl = clamp(ndotl, 0, 1 + singleLevel)
颜色 = ndotl × 光色 × albedo + 环境色 × albedo
```

- `multiStep` 是 v3 `Math/Step.hlsl` 的**逐行翻译**（函数本体只有 10 行）。
- `level`（档数）与抖动偏移**逐物体**给（走 G-buffer），因为远景大平面与近景角色需要不同档数——
  全局常量做不到这件事，这正是 v3 把它们放进缓冲的理由。
- **墨线像素不走着色数学**：物体 pass 的反向壳把 `prop.a` 写成 1，本趟见到就直接输出 `albedo.rgb`
  （即材质上的 `_InkColor`）。否则墨色会被色带量化 + 环境光染成"深蓝的带"，就不是墨线了。
- **暗部色的来源是环境光项**（当前实现）：暗面 = `albedo × 环境色`。
  ⚠ 这是**待裁决**的一处口径冲突：渲染篇 §4.2 要求"暗部不做纯乘暗、用替换式预制暗部色"，
  而 v3 的 `DiffuseShading` 加上环境光项就是纯乘暗。实测纯乘暗的暗面落在 `#2E3232` 上下，
  和 1px 墨线（`#0D0D16`）在缩略图里容易糊成一片。两条路的取舍见
  [实拍 r4 的 §7](../images/pixelart-path/r4/README.md)。
- **本阶段刻意留空**：连通域降档（`connect < threshold` 时减一档 ⇒ 内部转折线）与法线边加成——
  两者都要 P4 的连通域缓冲；`Property.b` 已把法线边加成档从物体 pass 带过来了，接的时候只差一个分支。

### 4.1 外轮廓：反向壳（物体 pass 的第二个 pass）

口径是**渲染篇 §5 的六轮实拍配方**，不是屏幕空间边缘检测（渲染篇 §5 明确"不用"；蓝本 §8 裁决点 3
的推荐也是"外轮廓 = 反向壳"）：

| 项 | 值 | 为什么 |
|---|---|---|
| 渲染状态 | `Cull Front` + `ZWrite Off` + **`ZTest Always`** | 壳只留轮廓环；写深度会挡住随后画的本体；**深度测试必须关**——见下 |
| 顶点外扩 | `positionVS.xy += normalize(normalVS.xy) × unitSize × _OutlinePixels` | **必须归一化**：不归一化时朝屏的面外扩不足 1 像素、整圈被光栅化吃掉（实测下缘墨线覆盖 0%） |
| ~~沿视线拉近 5× 线宽~~ | 保留但**不再是关键** | 它原来是为"跟先画完的地面抢深度"服务的；改 `ZTest Always` 后这条路不再依赖它 |
| 线宽 | `_OutlinePixels = 1`（**低分辨率像素**） | 渲染篇 §5「RT 空间 1px 起步」。旧链取 2px 是"全分辨率渲染 + 3× 点降采"时代的补偿，本路径几何直接渲进 RT，不适用 |
| 大平面 | `_OutlinePixels = 0`（整 pass discard）+ `renderQueue = 1999` | 不描边；且必须先于描边物画完 |

> **实测记录（r5）**：`ZTest LEqual` + 拉近 5× 的配方在本路径的取景下**下缘一条线都没有**
> （程序化判据：平台剪影上缘有墨线的列 97%、下缘 0%）——深度测试的对手是**大平面**，
> 而壳在下缘那圈投射出的深度是物体的**背面**（18m 见方的台面、背面深达十几米，0.65m 的拉近杯水车薪）。
> 改成 `ZTest Always` 后下缘闭合（0 → 48%，其余是"相邻物体互相漏线"）。
> 代价：**相邻物体互相漏线**（角色站在台面上时底下那圈被台面本体盖掉），旧链也记过同一条，
> 要抑制得按层规划 Stencil。
>
> **v3 自己的 `OutlinePass.hlsl` 是另一条路**：屏幕空间 4 邻域膨胀 + 连通域门控。
> 它在 v3 里**是关着的**（蓝本 §4.3），且门控依赖 P4 才有的连通域结果——所以本路径不照搬它。
> 何时把"内部转折线"接进来，见蓝本 §8 裁决点 3。

**抖动两范式**（物体 pass 写入 `Property.g`，幅度由材质的 `_DitherStrength` 施加）：

| `_DitherMode` | 图案 | 性质 |
|---|---|---|
| 0 | 4×4 Bayer 矩阵（中点归一化 `(m+0.5)/16`） | **渐变态**：16 级，只有色带阈值附近的像素翻档 |
| 1 | 1-bit 密度图案纹理（v3 口径，4/6/8/16 边长） | **两态撕边**：图案是 0/1，阈值带内的一半像素往上翻、一半往下翻 |

九张 v3 口径的图案由 `Assets/Editor/DitherPatternBaker.cs` 烘焙（矩阵按其资产逐像素量出后以字符串重制，
参照库不入库）。两者不可叠加，**默认关**（`_DitherStrength = 0`，与 v3 自带材质同口径）。

## 5. 出图与判据

**出图**：`PirateCrew3D.exe -pixelartOut <绝对目录>` → 进 `PixelartPilot.unity` 拍 5 张 1920×1080 无损 PNG
（`PlayerArtCapture.RunPixelartCapture`）。机位/档位表：

| 文件 | 机位（正交 size） | 抖动 | 想看什么 |
|---|---|---|---|
| `pa-wide` / `pa-mid` / `pa-close` | 14 / 9 / 4 | 关 | 基本观感：场景尺度、色带切分、档数、暗面亮度、描边闭环、格子是否硬 |
| `pa-mid-bayer` | 9 | Bayer 0.5 | 渐变态抖动 |
| `pa-mid-density` | 9 | 密度图案 1.0 | v3 口径的撕边 |

**机位口径不在出图脚本里**：俯角/方位/机位距离/构图中心取自 `PixelartPilotScene.cs`，装配器与出图脚本共用。
（曾经两边各写一份：场景 35.264°、脚本 30°，那张"30° 对照图"根本不是同一场景的机位，比对结论全错。）

**判据**：`python tools/pixel-review/judge_pixelart_pilot.py <图片目录>`（在**无损 PNG** 上跑，别用入库 JPEG）。
五项：块边长（⇒ RT 宽）、跳变率、平坦占比、低分辨率色数、**亮暗跨度**（"光照有没有被整屏旁路"的回归判据）。

**实测（2026-09-22，r4 批）**：

| 图 | 块边长 | RT 宽 | 色数 | 跳变率 | 平坦占比 | 亮暗跨度 |
|---|---|---|---|---|---|---|
| `pa-close` | 5 | 384 | 10 | 0.011 | 0.971 | 0.76 |
| `pa-mid` | 5 | 384 | 17 | 0.024 | 0.949 | 0.80 |
| `pa-wide` | 5 | 384 | 17 | 0.016 | 0.968 | 0.80 |
| `pa-mid-bayer` | 5 | 384 | 18 | **0.139** | 0.765 | 0.80 |
| `pa-mid-density` | 5 | 384 | 18 | **0.996** | 0.000 | 0.80 |

三条读数：

1. **RT 档位与宽度公式生效**：RT 高 216 → 宽 384 → 块 5，与期望一致（判据脚本从 `PixelartPilotScene.cs` 读期望值）。
2. **无抖动时是纯平涂**：平坦占比 0.95~0.97、跳变率 0.01~0.02——色带是平的，只有真实几何边缘才跳。
3. **两范式抖动的差别被量化**：Bayer 只让阈值附近的像素翻档（0.139）＝渐进过渡；
   v3 密度图案让阈值带内几乎每个像素都翻（0.996）＝**两态撕边**。

**色号已与解析式逐位对上**（r4）：按 `sRGB(multiStep·lightColor·albedo + ambient·albedo)` 手算 tan 台面三档，
与实拍主色块吻合到 1~3 个色阶（顶面 241,205,141 → 实测 240,205,141），
⇒ 线性/伽马没有错层。**已知量化损失**：墨色存进 8 位线性的 albedo 缓冲时偏暗
（`#120C14` 显示为 `#0D0D16`）。

## 6. 改这条路径之前：五个静默失效点（都已在代码里注释）

这条路径的失效方式**很少报错**，多数表现为"画面只剩背景色"或"某个效果不生效"。已踩过的点：

1. **`Shader.Find` 的 shader 会被播放器构建剥离**。构建只收"被资产引用链摸到"的 shader；
   只在 C# 里 `Shader.Find(名字)` 的 shader 既没有编译记录也不报错，运行时返回 null。
   ⇒ 着色 shader 必须由 Feature 的**序列化字段**持有（`PixelartShadingFeature.shadingShader`），
   装配器负责写入。装上屏 blit 用的 `Hidden/Universal/CoreBlit` 不受影响（URP 运行时自身引用它）。
2. **层掩码不能跟着主相机同步**。主相机的 `cullingMask` 被本路径清成 0（它只上屏），
   若 Cast 相机跟着同步，物体 pass 的 `cullResults` 就是空的——**不报错，只是什么都没画**。
   ⇒ Cast 相机用"主相机被清掉之前的那一份"（`PixelartCameraRig._savedCullingMask`）。
3. **抖动的幅度必须在物体 pass 施加**。着色 pass 只负责"读出偏移量"，若在物体 pass 里忘了乘
   `_DitherStrength`，抖动就恒等于满幅度——症状是"关着也有规律点阵"（4 低分辨率像素周期的网）。
4. **G-buffer 的通道语义必须排他**。事故实例：`prop.a` 一肩挑两职（着色 pass 判"这是墨线像素"
   的标记 ＋ 物体 pass 写 `_AAScale` 占位属性），而 `_AAScale` 的 Properties 默认值恰好是 **1.0**
   ⇒ **每一个不透明像素**都满足"这是墨线"、直接输出 albedo、跳过全部着色数学。
   症状是"所有面同色、与 albedo 逐位相同、没有任何光影、无任何报错"，旧的四项判据还全过。
   ⇒ 通道语义排他 + 判据五「亮暗跨度」兜底（复现事故时每一张都会 FAIL）。
5. **"编辑器里对、播放器里错"是这条路径的一类独立故障**。实例：船员预制体根上带
   `Rigidbody`，剥组件时漏掉它 ⇒ 编辑态不跑物理、包围盒完全正确，进播放器后自由落体
   （采集在载入后约 1.5 秒，下落 ≈11m，正好埋进地面以下被挡住）。
   ⇒ 从预制体实例上取物体时，**先 `UnpackPrefabInstance(Completely)` 解包**，再按
   **白名单**剥组件（只留 Transform/MeshFilter/MeshRenderer），并**当场断言无残留**。
   （实测：预制体实例上 `DestroyImmediate` 删不掉 `Rigidbody` 与 `PirateBase`，
   场景的 `m_RemovedComponents` 里根本没有它们。）
6. **描边不是"参数对不对"，是"次序 + 深度测试"**。四条，缺一条就断（见 §2 的注与 §4.1 的实测）：
   ① 大平面先整体画完（否则环被它盖掉）；② 壳先画、本体后画（否则一根线都看不到）；
   ③ 壳只写颜色不写深度（否则挡住本体）；④ **壳关掉深度测试**（否则近侧下缘跟先画完的大平面抢深度、
   整条边丢光——实测下缘覆盖 0%）。

自检：`PixelartCameraRig` 首帧会打一行装配自检（两台相机的层掩码、RT 尺寸、走本路径物体 shader 的
renderer 数）**并把实际下发的光照量打一行**（光方向/光色/环境色/unitSize/RT 尺寸，用于比对色号）；
三个 Feature 各打一行"已执行"。**这些日志齐全 + 判据脚本全绿**，才算这条路真的在跑。
