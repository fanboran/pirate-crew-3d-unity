## 0. 一句话结论

**v3 与本仓的分野不在"用哪个 shader"，而在"着色发生在哪一档分辨率"。**

- **本仓现行**：物体用 `PirateToon`（`LightMode=UniversalForward`）在**全分辨率**前向着色 → `PixelationRendererFeature` 在 `AfterRenderingPostProcessing` **事后降采**到 640×360 → nearest 放大回屏。**降采之后画面已经是最终结果，没有第二次着色机会**。
- **v3**：物体 pass 只往 **7 张 G-buffer（1600×900 超采样）**写数据，**不做任何着色** → 超采样降采到 **320×180** → **在 320×180 域上**才跑连通域、边缘光、漫反射、高光、GI、帧级调色板 → 最后一次 Point 放大上屏。

所以"换成 v3 架构"的真实含义是：**把着色从全分辨率域搬到低分辨率域，物体 pass 退化成写数据**。这不是"换个 shader"，是把管线的重心挪一格。渲染篇 §3.1 推论 4 说的"几何直接渲进 RT"只覆盖了这条改动的**一半**（省 fill rate 那一半），另一半——**低分辨率域上的着色与后处理**——才是 v3 真正多出来的东西。

## 1. v3 的真实执行顺序（源码级）

### 1.1 双相机分工

| | 主相机（`_ThisCamera`） | Cast 相机（`Cast Camera`） |
|---|---|---|
| Renderer 资产 | `Sloane Pixelart Main Renderer` | `Sloane Pixelart Cast Renderer` |
| Renderer 特征 | **只有 1 个**：`CopyTargetRendererFeature` | **9 个**（见 §1.2） |
| 相机设置 | `clearFlags = Nothing`、`cullingMask = 0`、`farClipPlane = 0.02f`（`$P/Scripts/MonoBehaviour/SloanePixelartCamera.cs:113-115`） | 正交、`depth = -64`、`orthographicSize = 6.125f`（Celeste 那个数）、`targetTexture = ResultBuffer`（同文件 `:290-296`、`:276`） |
| 渲染模式 | `m_RenderingMode: 1`（Deferred，但层掩码 0 ⇒ **什么都不画**） | `m_RenderingMode: 0`（Forward） |
| 干的活 | `cmd.Blit(ResultBuffer → cameraColorTarget)` 一次上屏（`$P/Scripts/RendererFeature/SloanePixelartCopyTargetRendererFeature.cs:46`） | 全部几何与全部着色 |

**关键结构性事实（决定"Cinemachine 不用重接"的那条）**：Cast 相机是主相机的**子物体**、用 `SetParent(transform, false)` 建、**local 恒等**（`SloanePixelartCamera.cs:283-285`），因此它自动继承主相机的 Transform——Cinemachine 照常驱动主相机，白搭一个渲染代理。主相机自身被清掉了 cullingMask 与远裁面，退化成"纯变换持有者 + 把结果 blit 上屏"。

> ⚠ **一个本仓必须纠正的细节**：v3 的 `ResultBuffer` 固定 **320×180**，上屏那次 blit **不随屏幕宽高比调整**（全仓没有一处设 `Camera.aspect` 或 `rect`）。非 16:9 屏会横向拉伸。本仓 `PixelationRendererFeature` 现在的做法（**高锁 360、宽 = 高 × 相机宽高比、偶数对齐**，`PixelationRendererFeature.cs:140-142`）是更对的，**这一条要保留、不要退化成 v3 的写法**。

### 1.4 物体顶点变换（要逐字复刻的部分）

`$P/Shaders/Includes/Passes/CommonPass.hlsl:5-57` `PixelartBaseVert`，三层叠加：

1. **逐物体 snap 矩阵**（`_SnapOffset`，`UNITY_ACCESS_INSTANCED_PROP`，`float4x4`，哨兵 `snapOffset._m33 == 1.0` 判定是否启用）— `modelMatrix = mul(snapOffset, modelMatrix)`（`:12-14`）。C# 侧在 `SloanePixelartObject.cs:80-97` 算出：沿父链累积 local TRS → 乘视图矩阵 → **把视图空间的平移分量四舍五入到 `unitSize` 整数倍** → 乘回 `viewMatrix.inverse` → `snapOffset = snappedMatrix * localToWorldMatrix.inverse`，经 `MaterialPropertyBlock` 下发（`:66-70`）。**效果是把物体整体挪到像素网格上。**
2. **顶点着色器里的原点对齐**（`#define ALIGN_TO_PIXEL`，两个 mesh shader 的 `HLSLINCLUDE` 里无条件开着）：
   ```hlsl
   float3 originWS = float3(modelMatrix._m03, modelMatrix._m13, modelMatrix._m23);
   float3 originVS = mul(PIXELART_CAMERA_MATRIX_V, float4(originWS, 1.0));
   float unitSize = _UnitSize / _LocalUnitScale;          // UNIT_SCALE 分支
   float3 originVSAligned = float3(UNITSNAP(originVS.x, unitSize), UNITSNAP(originVS.y, unitSize), originVS.z);
   float3 originVSOffset = originVSAligned - originVS;
   ...
   output.positionVS += originVSOffset;                    // 全顶点同一位移
   ```
   **它只 snap 物体原点、不 snap 每个顶点**——同一物体的所有顶点共享一个位移，所以形状不变形，只是整块落在格子边界上。
3. **`positionSSO`** = `positionSS.xy - originSS.xy`，其中 `originSS` 由 `originVSAligned` 投影而来（`:48-51`）——这是**"相对物体原点的屏幕偏移"**，专供抖动贴图采样（§7.2 第 6 条）。

> ⚠ 第 1、2 层**作用重叠**（都在把物体原点对齐到网格），两层同时开时第 2 层的 offset 会趋近于 0。移植时**只需一层**——本仓取哪层见 §7.2。

**两条移植注意**：

1. **MRT 用 `SNorm` 格式，且法线与"字节打包"共用同一批通道**——`PaletteProperty.a` / `ShapeProperty` 里的位标记走的是 `Packing.hlsl` 的 `PackFloatInt8bit(f, i, maxi)`（core 包自带，`PackFloatInt8bit(f,i,maxi) => PackFloatInt(t, i, maxi, 256.0)`）。**随手换格式（比如换回 `UNorm` 或 `Float`）会让 `PackFloatInt8bit/UnpackFloatInt8bit` 读写不一致**，症状是"连通域门控随机失效"。
2. **只有 7 个 MRT 目标被绑定**：`m_OpaqueBuffersIdentifiers` 长度 = `StageRenderObjects(7) - MarkerDepth(0)` = **7**（`:37`），绑定缓冲 1..7；而片元着色器有 **8 个输出**（`DefaultPass.hlsl:42`，多一个 `BUFFER_LIGHTMAP_UV`）。第 8 个（`COLOR7`）**没有目标**，且全仓**没有任何一处绑定 `_LightmapUVBuffer`**（枚举里根本没有对应的 `TargetBuffer` 成员）。⇒ **v3 声明了 lightmap UV 通道但它永远是空的**，GI 的 `SAMPLE_GI(lightmapUV, SH, normalWS)` 实际只走 SH。

## 3. 三个 compute 阶段在算什么

驱动代码：`$P/Scripts/RendererFeature/SloanePixelartConnectivityMapGenerationRendererFeature.cs`（`m_Threshold = 0.25`、`m_IterationScale = 1.5`）。通用 pass 封装是 `$P/Scripts/RendererFeature/ComputeShaderPass.cs`。

### 3.1 `ConnectivityCheck.compute` — 超采样域打点（1600×900）

`[numthreads(8,8,1)]`，派发 `200×113×1`。逐像素往四个方向（+x/+y/−x/−y）各调一次 `CheckConnectedDepthNormal`，把结果打包进 **4 个通道各 1 字节**，位布局（`ConnectivityCheck.compute:30-42`）：

```
bit7 = connected     （该方向是否连通）
bit6 = closer        （中心是否比邻者更近）
bit5 = center        （本像素是否是所在 _SamplingScale 单元的正中心）
```

`center` 位是关键：它标出"每个低分辨率像素的代表样本"，供后续 Flood 与 Result 在 5×5 单元里定位中心。

判据本体在 `$P/Shaders/Includes/Connectivity.hlsl:42-104`：跨 `step` 个中间像素逐步走，**用两端法线各自预测深度**，与实测深度比残差；只有**两端残差同时超阈值**才判"不连通"：

```hlsl
float2 pixelSpacing = (centerPos.xy - targetPos.xy);
float dz_x = -normalCenter.x * pixelSpacing.x / normalCenter.z;
float dz_y = -normalCenter.y * pixelSpacing.y / normalCenter.z;
float predictDepth = centerDepth + dz_x + dz_y;
...
if(dot(normalTarget, normalTarget) < 0.5 && dot(normalCenter, normalCenter) >= 0.5) connected = 0;
else if(dot(normalTarget, normalTarget) >= 0.5 && dot(normalCenter, normalCenter) < 0.5) connected = 0;   // 判断是否为空
else if(resultCenter > _Threshold && resultTarget > _Threshold) connected = 0;
```

这正是"平面预测残差"——**它是 v3 判据比 v2 强的地方**（v2 是裸深度差 + 邻域法线点积过阈值），也是"石阶的暗线、柱子的亮边"能出去的原因。

### 3.2 `ConnectivityFlood.compute` — 单元内传播（1600×900，**跑 8 次**）

派发次数 = `Mathf.RoundToInt(DownSamplingScale * m_IterationScale)` = `RoundToInt(5 × 1.5)` = **8**（`...ConnectivityMapGenerationRendererFeature.cs:65-66`）。每次派发前 `GetTemporaryRT` + `Blit` 把当前 map 复制成 `_PrevConnectivityMap`（`:82-91`），是真 ping-pong。

`Flood`（`ConnectivityFlood.compute:13-48`）沿四方向把"中心像素的连通性"在**同一个 5×5 单元内**扩散：先算 `center`（单元正中），目标必须落在 `halfScale` 半径内（`:14-16`）；源像素的 `center` 位为 1 就跳过（那是中心自己）；然后比较源→目标的 connected/closer 位，通过则把目标那一路的 bit 写回源（`:44-48`）。**它解决的是"两个低分辨率像素之间到底连不连"，即跨单元的连通性传递。**

### 3.3 `ConnectivityResult.compute` — 降采成结论（320×180）

派发 `40×23×1`。逐低分辨率像素遍历它对应的 5×5 超采样单元（`ConnectivityResult.compute:36-38`），累计三个量并写成一个 `float4`：

```hlsl
float4 output = float4(totalConnectedCount / float(_SamplingScale * _SamplingScale),      // .r 单元内连通比例
                       totalConnectedOrCloserCount / float(_SamplingScale * _SamplingScale), // .g 连通或更近的比例
                       0.0, 0.0);
output.b = normalDiff;                                                                     // .b 单元内最大法线差
output.a = PackFloatInt8bit(0.0, (connectedRight << 7) + (connectedLeft << 6) + (connectedUp << 5) + (connectedDown << 4)
                                + (closerRight << 3) + (closerLeft << 2) + (closerUp << 1) + (closerDown), 256.0);  // .a 跨单元四方向
```

`connected`/`closer` 的跨单元判据用 `step = _SamplingScale`（步长 5 个超采样像素）再调一次同一个 `CheckConnectedDepthNormal`（`:67-81`）。

### 3.4 `RimLightCorrection.compute` — 去孤立点（320×180，就地）

**它是在跑的那个"rim light compute"**（Cast Renderer asset 里 `m_RimLightComputeShader: guid 541451e9…` = 本文件）。3×3 邻域扫，若周围非黑邻居为零就把 RGB 清零（保留 alpha）——是边缘光结果的**清洁工**，不是累加器。

## 4. v3 里其实没在跑的东西（**别当观感来源**）

这一节是本次读源码最有价值的部分：**有几处"看起来很核心"的机制，在实际配置下对画面零贡献**。照搬之前必须知道，否则会把作者的实验遗留当成观感的因。

### 4.1 `PriorityManagement` 是死 pass【实测·三条独立证据】

1. **目标被覆盖**：`...PriorityManagementRendererFeature.cs:35-36` 连着调两次 `SetTargetBuffer`，而 `ComputeShaderPass.SetTargetBuffer` 是**覆盖**语义（`ComputeShaderPass.cs:53-63`）⇒ 最终目标是 `_ConnectivityDetailBuffer`，不是 UV。
2. **它要写的缓冲从未绑定**：kernel 写 `RWTexture2D<float4> _UVBuffer`（`PriorityManagement.compute:5, 75`），但 C# 只 `AddSourceBuffer` 了 `ShapeProperty` 与 `Albedo`（`:33-34`），**全仓没有一处绑 `_UVBuffer`**。
3. **它读越界**：目标缓冲换成 1600×900 后 `ComputeShaderPass` 下发 `_Width/_Height = 1600/900`，而 kernel 的 guard 与 `sourceCoordStart = id.xy * _SamplingScale` 都按"目标 = 低分辨率"设计 ⇒ `id` 走到 (1599,899) 时读坐标是 (7995, 4495)，**远超 1600×900**。越界读在 D3D11 返回 0 ⇒ `targetConnectedToCenter == 0` ⇒ 每次 `continue` ⇒ `targetCoordOffset` 永远是初值。

**后果**：UV 缓冲保持第 1 步（BeforeRender）清成的**灰色 (0.5,0.5)** ⇒ `GET_UV_WITH_PRIORITY` 的位移恒为 0 ⇒ **"优先级仲裁 / 用高优先级像素的代表色"这套机制在 v3 的画面里完全没生效**。它对观感的贡献是 **0**。

> ⇒ **移植结论：不要移植 PriorityManagement**。它同时是"本仓不必为它设计材质属性通道"的直接依据。（顺带一提，它的本意是好的——解决"两个物体争同一个低分辨率像素时该显示谁"——但那是**没有先例、需要自己从头设计**的一块，不是照抄能拿到的。归 §8 裁决点 4。）

### 4.2 三个孤儿 compute

| 文件 | 证据 | 状态 |
|---|---|---|
| `SloanePixelartDownSampling.compute` | GUID 无任何 C# 引用；`DownSamplingAA` kernel 声明了 `_DiffThreshold`/`MinCount`/`targetColor` 但函数体只写了一样的点采样 | **没接线，且 AA 分支是空壳** |
| `KuwaharaFilter.compute` | GUID `acc295e5…` 在 assets/scenes/prefabs/cs 里**零引用**；且 down 方向分支写的是 `averageColor.rgb = col;`（其余三向是 `(col + currentColor)/2.0`）；`_ShapePropertyBuffer` 声明了没读 | **没接线，且自身不对称** |
| `SloanePixelartExecuteComputeShaderRendererFeature.cs` | 全仓 asset/scene/prefab 里没有实例 | **通用封装，但没被用过** |

**重要推论**：§36 已记"v3 的干净不来自超采样"，这里补上后半句——**它的降采就是"取单元中心那一个样本"的点采样**（`_Target[id.xy] = _Source[id.xy * _SamplingScale + uint2(1,1)*_SamplingScale/2]`），**没有 box 平均**。所以那 5× 超采样的真实用途**不是画质，而是给 ConnectivityCheck 提供"单元内 5×5 的细粒度深度/法线"**——判据要跨步走中间像素，就必须在超采样域做。这一条直接决定本仓的超采样档要不要保留（§7.2 第 2 条）。

### 4.3 两处 `m_Active: 0` 与一处被动过语义的全局量

- `OutlineRendererFeature` 关着。**但它的 `OutlinePass.hlsl` 源码是完整的**（4 邻域膨胀 + `connectedTo* < 1 && closerThan* < 1` 门控 + 调色板里取 `applyOutline` 位），要移植"内线"时它是现成的一手材料。
- `Debug` 关着（本仓不用它出图，走 MCP + 程序化判图）。
- 唯一的 `_OUTLINE_SOLID_COLOR` 全局关键字只在 Outline 启用时有意义。

### 4.4 两处真 bug（照搬会继承）

1. **`ReleaseBuffers` 只释放第一个缓冲，其余 14 张全泄漏**：`SloanePixelartCamera.cs:127-131` —— `m_TargetBuffers = null;` 写在 `foreach` **循环体内部**，第一次迭代后就把字段置空，后续迭代的 `if (m_TargetBuffers != null)` 恒假 ⇒ 缓冲 1..14 永不 `ReleaseTemporary`。而这些 RT 是从 `GetTemporary` 拿到后**调了 `.Create()`**（`:168` 等）的，等于自管生命周期，不会被池自动回收。`GetBuffers()` 挂在 `OnEnable` 与 `OnValidate`（`:76-77`、`:95`）⇒ **编辑器里每动一次 Inspector 泄漏 14 张 1600×900 RT**（约 70MB 起）。
2. **边缘光抑制 AA 时漏了蓝通道**：`ShadingPass.hlsl:93` 与 `:222` 都是 `if(rimLightInfo.r > 0.0 || rimLightInfo.g > 0.0 || rimLightInfo.g > 0.0)` —— **`g` 判了两次、`b` 一次没判**。⇒ 纯蓝边缘光不会抑制色带降档。

另有两处无害但不该复刻：`SloanePixelartObject.cs:77` 每次更新都 `Debug.Log`（刷日志）；`SloanePixelartRimlight.RefreshRimLights` 往定长 32 的数组里写、**没有越界保护**（场景里超过 32 个 rim light 光就崩）；各 compute 的 guard 用 `>` 而非 `>=`（越界一行/列，靠 `CeilToInt` 派发的余量兜着）。

| 高光 | **去掉** | 有独立 Specular 缓冲 | 按渲染篇 §4.3 砍掉 ⇒ **4 张着色缓冲 → 3 张** |

| HDR | 关 | ResultBuffer 用 `DefaultFormat.HDR` | 按渲染篇 §6 |

## 6. 重写蓝图：分阶段（P0→P5）

每一阶段都**独立可验收、独立可回退**，并且尽量让前几阶段"零架构改动"就有画面收益。顺序是按"先拿观感、再掏架构"排的。

### P0 · 零架构改动的两件对照（**建议第一步**）

| 项 | 做什么 | 落点 | 验收 |
|---|---|---|---|
| P0-1 | RT 高 **320×180 vs 360** 对照出图（v3 默认粗一半，"粗得好看"可能是偏好来源） | `PixelationRendererFeature.settings.renderHeightPixels` | 两张同机位截图 + 程序化判据（块尺寸/色数） |
| P0-2 | 抖动从 4×4 Bayer 换 v3 的 **1-bit 密度图案**（4×4/6×6/8×8/16×16 九张）出对照 | `PirateToon.shader` 抖动段 | 同上 |

**为什么先做**：这两件都**不碰架构**，却直接回答"观感锚是不是 v3"这个前置问题（§8 裁决点 1）。**在做完 P0 之前不要动 P1**。

### P1 · 把着色搬进低分辨率域（几何直接渲进 RT）

- 新建 **Cast 相机**（主相机子物体、`SetParent(transform, false)`、local 恒等）+ **两个 Renderer 资产**（Main = 只有 CopyTarget；Cast = 其余全部）。
- 物体 shader 增加一条 `LightMode = "PixelartOpaque"` 的 pass，**先把现有 `PirateToon` 的着色逻辑原样搬进去**（不拆 G-buffer），渲进低分辨率 RT。
- 主相机清 cullingMask/远裁面，只留上屏 blit。
- **收益**：fill rate 真正下降；渲染篇 §3.1 推论 4 的"直接渲进 RT vs 全分辨率后降采"对照同时完成。
- **风险**：`PixelationRendererFeature` 现在的宽高比处理必须一起搬过去（§1.1 ⚠）。

### P2 · 物体 pass 退化成 G-buffer

- pass 拆成多 `SV_Target` 输出。**按本仓裁决只要 4 张**（Albedo / Normal0 / Shape / Palette），砍掉 v3 的 Normal1（法线贴图——本仓低模程序化件无 bump）、Physical（高光去掉）、RimLightProperty（若边缘光不逐物体给色）、第 8 个 lightmap UV。
- 逐物体参数（优先级/法线边阈值/AA 缩放/主光档位/边光档位）→ 材质 Inspector 或顶点色。本仓**已有**顶点色 R = 色带阈值偏移的规划（渲染篇 §4.7），与 v3 的 `ShapeProperty` 通道功能重叠，**取一处**。
- **风险**：MRT 格式必须与字节打包一致（§2 注意 1）。

### P3 · 低分辨率域的着色 pass

- Diffuse pass 搬 `DiffuseShading()`：`pow(ndotl, 1/2.2)` → `+= singleLevel*offset` → `multiStep` → 连通域降档 → 法线边加成。
- 本仓按渲染篇砍掉 shadow 关键字族与 `GetMainLight(shadowCoord)`，改成读烘好的静态 uniform。
- GI pass 简化为环境光项。

### P4 · 连通域三阶段 + 边缘光

- `ConnectivityCheck` / `ConnectivityFlood` / `ConnectivityResult` 三个 compute + 降档门控。
- 边缘光（`RimLightShading` 的屏幕空间光向 × 连通域门控）——**注意本仓现有边缘光语义是反向壳墨线，命名不要混**（§36 已定"v3 那支视频不是讲描边"）。
- **是否需要超采样档**在这里定：判据要跨步走中间像素 ⇒ 若不做超采样，`step` 要改成按世界/屏幕距离而不是固定像素数。**这是移植里唯一需要重新推导的算法部分**【提案】。

### P5 · 帧级调色板

- `PaletteGenerationCIEDE.compute`（把它接到 C#：**注意它用 `[numthreads(8,8,8)]` + 三维派发，通用 `ComputeShaderPass` 的 z 恒为 1 装不下**，必须像 `SloanePixelartPalette.cs:62-63` 那样自己 `Dispatch`）。
- `ColorCorrection.shader` 的采样公式直接可用。
- 调色板资产：v3 用 `List<Color>` + hex 文本导入（`SloanePixelartPaletteEditor.cs:32-47`），本仓可复用这个编辑流程。

## 7. 三张清单

### 7.1 可直接翻译（读懂后照搬，风险低）

1. **双相机结构**：主相机清空 + Cast 相机子物体 local 恒等 + 主相机 blit 上屏。**不需要重接 Cinemachine**（§1.1）。
2. **`BeforeRender` 的视图矩阵 snap**：`viewMatrix.m03/m13` 四舍五入到 `unitSize` 整数倍（`SloanePixelartBeforeRenderRendererFeature.cs:39-40`）——**不碰任何 Transform**。
3. **`unitSize` 的定义**：`orthographicSize × 2 / TargetHeight`（`SloanePixelartCamera.cs:47`）。本仓渲染篇 §2 的 `texel = 2×size ÷ RT 高` 与之**逐字一致**。
4. **`multiStep(value, level, minValue, offset)`**（`$P/Shaders/Includes/Math/Step.hlsl`，12 行）。
5. **连通域判据本体**（`Connectivity.hlsl:42-104`）与三段 compute 的数据流。
6. **`ConnectivityCheck` 的位布局**（bit7 连通 / bit6 更近 / bit5 单元中心）——简单、明确、可复核。
7. **`RimLightShading` 的屏幕空间光向门控**（`RimLight.hlsl:16-20`）：把 `TransformWorldToViewDir(direction).xy` 归一化后按四方向 clamp，乘 `(1 - connected)`。
8. **`PaletteGenerationCIEDE` 的 CIEDE2000 实现**（`PaletteGenerationCIEDE.compute:45-95`，含 `my_sin/my_cos` 的度数版）+ **`ColorCorrection` 的 LUT 采样公式**。
9. **`RimLightCorrection` 的 3×3 去孤立点**——若要给边缘光做"干净化"。
10. **材质参数分工表**（`Default.shader:5-21`）：主光档位 / 边光档位 / 法线边阈值 / AA 缩放 / 覆盖率。

### 7.2 必须按本仓裁决改（不能原样搬）

1. **相机 snap 只做了半套**：v3 没有任何"把 snap 残差转成 UV 偏移补偿回平滑移动"的实现（全仓搜不到）。本仓现行的两步法有那一半。**若采用 v3 的"改视图矩阵"，必须自己补 UV 补偿**，否则相机平移会是阶梯抖动而不是渲染篇 §2 要的"snap + 反补偿 = 平滑移动"。【提案：保留本仓的补偿逻辑，把 snap 的施加点从 `BattleCameraController` 的 Transform 改成 BeforeRender 的矩阵——这样既绕开 Cinemachine 冲突（风险 R6），又保住平滑移动。】
2. **超采样档**：v3 的 5× 超采样**不是画质手段**（降采是点采样，无 box 平均），而是给连通域判据提供细粒度深度/法线（§4.2）。⇒ 本仓要么保留一个超采样档（并接受 25× fill rate），要么**把判据的 `step` 从"固定像素数"改成"按世界距离"从而在 1× 下也能走**。后者的代价是判据阈值要重标。【裁决点】
3. **RT 分辨率与像素化强度**：v3 默认 320×180。本仓渲染篇 §3 起步 **640×360**、且"像素度是随资产成熟可调的演进项"。P0-1 出对照图之后再定。
4. **光照模型**：本仓"单平行光 + 单环境光、烘静态 uniform、跳 shadow 关键字族"（渲染篇 §4.6）⇒ **砍掉 `GetMainLight(shadowCoord)`、`_MAIN_LIGHT_SHADOWS` 那组 `multi_compile`、以及 `LIGHT_LOOP_BEGIN` 附加光段**。（若"局部暖光池"要走附加光路线，则这一条要改判——渲染篇 §7 已记 t3ssel8r 的第三条路。）
5. **缓冲集裁剪**：本仓按渲染篇裁决砍 Specular、砍 Normal1、砍 lightmap UV ⇒ 物体 pass 从 **8 个输出降到 4 个**（Albedo / Normal0 / Shape / Palette），GI 用扁平环境光。**这一条顺带把 §2 注意 2 那个"第 8 个 MRT 无目标"的问题直接消掉。**
6. **抖动图案的坐标系**：v3 用 `positionSSO`（**相对物体原点**的屏幕偏移，逐物体贴附），本仓用 `floor(positionCS.xy / pixelScale)`（**贴屏幕**、与 RT 块对齐，渲染篇红线 4）。两者观感不同，照搬会同时违反红线 4。⇒ **建议保留本仓的"贴屏幕 + 块对齐"**，只把图案本身（4×4 Bayer → 1-bit 密度图）换掉。【裁决点】
7. **上屏宽高比**：**保留本仓的"高锁 N、宽随屏宽高比"**，不要退化成 v3 的固定 320×180（§1.1 ⚠）。
8. **HDR / MSAA / Bloom / 附加光数**：一律按渲染篇 §6（HDR 关、MSAA 0）。v3 的 ResultBuffer 用 HDR 格式，**不要跟着写**。
9. **物体-像素对齐**：v3 让**每个物体**整体吸附到像素网格（§1.4 两层），本仓现行只 snap 相机。逐物体对齐会让单位的移动观感变"跳格"——**与玩法手感相关，归裁决，不要默默开**。
10. **参照库纪律**：源码级翻译改编，**不要 vendor 整包**（AGENTS.md 参照库纪律）。

### 7.3 建议不要搬

1. **`PriorityManagement`**——死 pass（§4.1，三条证据）。它想解决的"多个物体争同一个低分辨率像素"是**真问题**，但 v3 的实现没生效，**本仓若要做，得从头设计**（归 §8 裁决点 4）。
2. **`SloanePixelartDownSampling.compute`**——孤儿 + AA 分支空壳。
3. **`KuwaharaFilter.compute`**——孤儿 + 四向不对称 + `_ShapePropertyBuffer` 未读。
4. **`SloanePixelartExecuteComputeShaderRendererFeature`**——没人用的通用封装。
5. **`Debug` 特征 / `PixelartPreview` 那条 pass**——本仓出图走 MCP + 程序化判图（AGENTS.md 图形学调试截图规范），不需要在管线里留调试通道。
6. **`RimLightCorrection` 直接照搬**——它服务的是"逐物体边缘光色 × 32 个自定义 rim 光"这套东西；本仓的边缘光是反向壳墨线，语义不同。**照搬会把墨线洗掉**。
7. **`_LightmapUVBuffer` / 第 8 个 MRT 输出 / `SAMPLE_GI` 的 lightmap 分支**——v3 自己没接通（§2 注意 2）。
8. **`_SnapOffset` 与 `ALIGN_TO_PIXEL` 两层同时开**——作用重叠（§1.4 ⚠），取一层。

## 8. 裁决点（要创始人拍的）

| # | 裁决点 | 选项 | 影响的量级 |
|---|---|---|---|
| 1 | **观感锚**：锚 v3 还是维持现行 Art Bible | （a）锚 v3：**先做 P0 两件对照图**再定；（b）维持现行：本篇归档为参照 | 决定下面 2-5 是否还要做 |

## 10. 验收与门禁

- **编译**：改 shader 后 `read_console` 零 shader error（AGENTS.md 唯一算数标准；额外 Pass 必须有独立未被占用的 `LightMode`——本仓墨线用 `SRPDefaultUnlit`，**新增 `PixelartOpaque` 不冲突**）。
- **出图**：走 MCP（编辑器开着时不要另起 Unity 进程，`Library/` 锁独占）；**判图用程序化判据**（色带层数、每块方差、色数、连通域降档的像素占比），不靠"看着像"。
- **测试**：纯 C# 逻辑（连通域的位打包/降采统计）写成静态类进无头验证台（`external/m2-harness/`，命令见 AGENTS.md）；MonoBehaviour 胶水层由 batchmode 收口。
- **无头完整性**：改工程结构/manifest 后跑 AGENTS.md 里那条 `-batchmode -nographics -quit` 命令，退出码 0 才算数。
- **性能对照**：P1 完成后必须出"全分辨率渲染+降采"vs"直接渲进 RT"的帧时间对照——这是渲染篇 §3.1 推论 4 悬着的那个问号。
