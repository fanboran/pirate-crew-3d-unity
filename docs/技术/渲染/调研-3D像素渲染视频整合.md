## 1. 逐支视频讲了什么

### 1.1 v1 · Red Giraffe — 网格问题与颜色问题【采纳为本文主线框架】

作者的开场立论：像素画是**工程妥协长出的视觉语言**，要复现它就得"逆着现代硬件的纹理走"。他把问题切成两个：

**① 网格问题（the grid problem）**
- 病因讲清了：图像放大时新像素要赋值，双线性过滤会取 UV 周围 4 个纹素按亚像素偏移加权混合 —— 于是"把锐利边缘抹成意外的渐变，并引入原资产里根本不存在的颜色"。片中用一个水果碗场景演示：**只降分辨率再放大，画面是糊的**。
- 解法是**两段式 render pass**：先把整个场景 **point 过滤降采样**到固定目标分辨率（"把像素锁进离散网格，低分辨率 buffer 里每个像素都持有对应源像素的精确颜色值"），再用 **point clamp 采样器放大**回屏幕（"每个纹素精确映射到显示器上一块均匀像素块，保住我们建立的硬边"）。
- 注入点：**在不透明几何渲染到相机目标之后、重建开始之前**执行。片中出现的是 Scriptable Render Pass + 把低分辨率贴图放进一个 handle 供后续使用；并明确说"Unity 提供 opaque / skybox / post-processing 等多个注入点，各给不同的场景视图"。
- 复现判据：棋盘格图案的身份在放大后必须保住（不然就是双线性路上去了）。
- 他也承认边界：**"到此为止拿到的确实是像素画的形式，但像素画的美感和感觉仍然缺席"** —— 这句是整份文档最重要的一句，与本仓 M0「像素化是不可见基座」的复核结论**完全互证**。

**② 颜色问题（the color problem）**
- 论据链完整：有限调色板是经典像素画最持久的审美钩子，**这当年是硬件约束而**非艺术选择（NES 全场共 54 色、同屏仅 25 色；C64、Game Boy 同理），艺术家被迫让一个棕色同时充当土地/阴影/肤色。现代像素画则**主动**选 16 或 32 色来保住统一感——"对的调色板决定一个游戏的情感基调、一眼可读性、以及几十上百个资产之间的视觉一致性"。
- 对 3D 渲染器而言，**"致敬这个传统意味着不能只是低分辨率渲染，还得量化：有意识地把输出色彩空间压到一份手选调色板"**。
- 关键论证（本项目最该吸收的一段）：**朴素做法是用欧氏距离在 RGB 立方体里找最近色，数学没错但视觉观感是错的** —— 人眼对绿色远比蓝色敏感，RGB 空间**不是感知均匀的**（相同数值步长 ≠ 相同感知变化），而且 RGB 距离**忽略明度敏感度、色度压缩、以及色相响应的非线性**；这在像素画里格外致命，因为"局部对比与微妙色相渐变在视觉结构里占的权重不成比例"。
- 解法：**感知均匀色彩空间**。片中旁白讲的是 **CIE Lab**（70 年代中期由国际照明委员会制定；L 明度、a 绿-品红轴、b 蓝-黄轴；转换要先线性化 RGB → CIE XYZ → 用"模拟视锥响应"的非线性变换映进 Lab；每像素计算量偏重但在 GPU 上高度可并行）。
- 三次并排对比（双线性 / 像素化+RGB 量化 / 像素化+Lab 量化）：作者判断 Lab 那版"艺术意图最明确"，并承认"仍有局部你会质疑像素的选色，这是做 3D 的取舍之一"。
- 收口（**这条最有价值**）：因为量化被抽象成了一个感知数学问题，**游戏的观感就不再烘死在资产里**——"图像的色彩身份变成 GPU 上纯数据，一小撮随时可换的值"；换一份调色板 = 换一整个观感。
- 片尾预告：后续视频会讲描边、光照、反射等额外 pass（**v2 正好补的就是描边这一格**）。

> ⚠ **口径矛盾（必须记录）**：本支视频**旁白讲的是 CIE Lab**，但同一条视频的 **YouTube 官方简介写的是 OKLab**（"use perceptual color space (OKLab) to quantize colors"）；B 站搬运简介也跟着写"C IE L\*a\*b\*"。我 grep 了官方英文字幕全文，**"OKLab"零出现，"Lab"出现 10 次**——**画面/旁白口径是 CIE Lab**，OKLab 只存在于简介文案。本仓取 **OKLab**（理由见 §4.5：Ottosson 原文指出 CIELAB 无法准确预测色相、蓝色区预测很差、蓝→白混合会偏紫）。

### 1.2 v2 · Edwardo 的 Godot 教程 — 像素化 + 深度/法线描边【本文的描边实现依据】

**前半：像素化（Godot 的"零成本"做法）**
1. 场景里加 `SubViewportContainer`，其下加 `SubViewport`，把**需要像素化的物体全部移进去**，**相机也必须是 SubViewport 的子节点**；
2. 切到 2D 视图便于观察；容器锚点设**全屏**，打开**拉伸（stretch）**，调小拉伸数值就能看到分辨率下降；
3. **坑**：不设纹理过滤的话画面会**变模糊**——必须在纹理设置里把过滤模式改成 **Nearest（最邻近）**，"这样就完成了"；
4. 作者的定性：**单凭这个效果就 3D 像素艺术了**（同样呼应 v1 与 M0 的结论：像素化只是基座）。

**后半：边缘检测后处理着色器（七步）**
1. **先解决"编辑器里看不到效果"**：按 **Godot 官方《Advanced post-processing》** 的办法做一个可预览的后处理：
   - 加一个 `MeshInstance3D`，网格设为 **QuadMesh**，尺寸改 **2**，打开**面片翻转**，几何属性里把**额外剔除边距调到最大值**（保证不被视锥体裁剪——这正是官方文档列的"用 Viewport 做全屏后处理的两个缺点：拿不到深度缓冲、编辑器中不可见"的绕法）；
   - 顶点函数里加一行让四边形**始终覆盖整个屏幕**（把顶点直接放到 clip space，绕过模型→视图→投影变换）；
   - 用一张空间着色器做它的 **surface material override**。
2. **取三张屏幕信息**：屏幕纹理 / 深度纹理 / **法线-粗糙度纹理**，各自一个 uniform；
3. **深度边**：`DEPTH_TEXTURE` 是非线性的，**用 Godot 文档给的代码转成线性**（作者把它封成带 UV 偏移参数的函数复用）；逐像素尺寸 = `1 / VIEWPORT_SIZE`；**四个方向**（左/右/上/下）偏移 UV 采样后与原始深度**相减取绝对值**，累加（累加时用 `clamp` 限幅）；把 UV 偏移放进数组用循环处理；
4. **阈值**：`step()` 过滤小变化——作者演示 **0.3 的阈值**得到的外轮廓效果，并强调阈值要按项目实调；
5. **法线边（内线）**：流程同深度，但**法线是向量不能相减**——先 `0..1 → −1..1`（乘 2 减 1），再算**相邻像素法线的点积**（"结果反映两者之间的角度差异"），用 `smoothstep` 设阈值过滤。此时能检测**物体内部边缘**；
6. **两个真实缺陷与修法**：
   - 缺陷 A「轮廓有 **2 像素宽**」→ 参考 **Cody King 的工程**（链接在视频简介）用特定函数拿到清晰的**单像素轮廓**：新建处理函数接收法线/深度边缘偏移参数，把当前像素与相邻像素的法线点积结果乘上权值与深度信息混合；
   - 缺陷 B「外轮廓出现**双重轮廓线**」→ 造一个**隔离外轮廓的遮罩**：取深度边缘检测的**反向**结果（初始化 0.5，循环里用"主深度值减偏移后深度值"反向累加），`smoothstep` 设阈值后乘一个值锐化并 clamp；**用这个遮罩去减掉法线边缘结果**；
7. **合成"明暗双线"**：两个参数分别控制**高亮内线**与**暗色外轮廓**；内线 = 法线差减深度差（clamp），屏幕纹理当 albedo（unshaded），叠上高亮；外轮廓乘暗线参数。作者结论："明暗双线效果非常接近传统像素风"。片尾提到进阶玩法（让轮廓随场景光照变化）已放在简介的示例工程里。

> 这一支是本组视频里**唯一把描边写成可照抄步骤**的，也是唯一明确点出"外轮廓 vs 内线"两种边要用两套检测（深度 / 法线）再合成的一支。

### 1.3 v3 · 死罗恩 — 连通域驱动的「边缘光 + 色带升降档」【源码级已核】

- 这支**没有旁白**（whisper 转写返回 0 段语音，全片只有音乐），唯一文字信息是上传者简介：**"叠了个边缘光，在法线变化剧烈的地方把光照放暗一级。另外加了点微弱的抖动，其实啥形状都可以。"**
- 我抽帧复核（帧 003 / 006）：低模石构遗迹；石块棱线与轮廓上挂着**淡紫/墨色细线**；帧 006 换夜/暗调，背景是**大面积抖动渐变**（紫褐点阵），投影带抖动颗粒。
- **机制（源码级已核，工程见 §6 的 `sloane-urp`；2026-09-22 复核，纠正本文初版的"法线变化率"猜测）**：简介的两句话**逐字对应源码**——
  - `multiStep(ndotl, level, 0.0, 0.0)` 先把 `N·L` 量化成 `level` 档（色带）；
  - `if (ndotl > singleLevel && connect < _ConnectivityAntialiasingThreshold) ndotl -= applyAA * singleLevel;` —— **在连通域断开处压暗一级**（`singleLevel = 1/(level-1)`）；这正是"在法线变化剧烈的地方把光照放暗一级"；
  - `if (normalDiff > normalEdgeThreshold) ndotl += singleLevel * normalEdgeLevel;` —— 再按法线差升降一档；
  - 边缘光是**独立门控项**：`(1-connectedTo*)*clamp(±screenSpaceLightDir.*, 0, 1)` 四方向加权求和后再 `multiStep` 量化。
  ⇒ v3 的"内线"**不是描边 pass 画的**，而是**色带在有连通域断开处降了一档**得到的。初版本文猜的"零成本内线"方向对，但**判据是 compute shader 算出的连通域 + `normalDiff`，不是 `fwidth` 导数**。
- 与 v2 的关系：v2 是"屏幕空间检测 + 独立合成"；v3 的**内线走"着色器内搭色带便车"**（另一路），但它的**外轮廓另有屏幕空间实现**——`OutlinePass.hlsl` 用连通域做 **1px 膨胀**、再按 `_PalettePropertyBuffer` 的优先级仲裁谁画线。**所以 v3 是两层都用的**，见 §2.1。

### 1.4 v4 · 稀有纸张 — 逆向 t3ssel8r 的抖动 shader【源码已拿下】

视频本身是一条**逆向教学**，流程：
1. 起因：看到搬运的 Blender 3D 像素艺术视频（= **v5**），以为是降分辨率，**看到像素抖动后去看 shader**；
2. 准备一张 **2×2 的图片资源**——"它决定了像素抖动的风格"；
3. 搭节点：`SubViewport` → `Sprite2D`；建 **VisualShader（CanvasItem 模式）**；**用 UV 坐标对 2 取模**去采样那张 2×2 图得到混合色；把基础色（Texture2D）与混合色做**柔光混色**；最后**常量插值**输出到颜色上。（作者自己说这一段"是用来讲思路的，**不要这样写**，因为 VisualShader 功能不全"）
4. 想要自定义 VisualShader 节点：**去 Godot 官网抄那段自定义节点代码**，稍作修改、重启项目就能用；
5. 把 VisualShader **改成手写 shader**：两个 uniform 定义物体颜色；把抖动风格图拖进来；定义**抖动程度**（"实际上就是在混合前和混合后的颜色之间做插值"）；
6. 采样位置**模 2**；写入**柔光代码**；输出颜色；
7. 3D 部分：一个球、一盏光、一台相机；
8. 脚本部分：相机脚本（作者自嘲"刚学 Godot 时写的，后来稀里糊涂改了好几次，现在成了一坨"）+ 一个 **HSlider 滑动条绑 `dith_level`**（提醒设最小长度）。

**仓库 `rarepaper/whpu`（我已 clone 并逐文件读过源码）里的四套配置**：`2d（LIGHT）`（Godot 2D 光照 + 法线贴图做 toon）、`3d （LIGHT）`（spatial shader 的 `light()` 版本）、`3d（viewport）`（SubViewport 像素化版）；着色器有 `成品.gdshader`（视频里那支）、`toon.gdshader`、`2d像素化.gdshader`（**作者自己标了"这是废稿"**）。**具体代码与实测像素值见 §4.2–§4.4**——这份源码是本组六支视频里唯一能**逐行核对**的实现。

### 1.5 v5 · t3ssel8r — 场景制作实录（资产侧参照）

B 站标题写"Unity像素风引擎"，**实为 t3ssel8r 的 making-of**，原片简介自述：用一周的常规技术更新间隙录一条"从零做一个场景"的实录，讲他**在 Blender 里发现的修改器栈技巧**（给岩石、石砖、树做**程序化、非破坏性**的细节），目的是"省下大量资产制作时间，让一个人做出大世界变得可行"。

内容脉络（旁白逐段）：
1. Blender 空场景起步；**楼梯** = 拉伸立方体 + **Array 修改器**复制；**柱子** = 简单挤出；再补柱子/阶梯/石板；
2. **树** = 圆柱 + 合并球体；单株建成后复制、改旋转与缩放散布；**岩石** = 细分立方体；顶部大石板用**布尔切割**做破损；
3. **水池**在大平面上挖轮廓 + 围石；此时项目"乱成一团"，于是**整理成集合（collections）**；
4. **程序化细节**：给岩石加 **Displace + Remesh**（"reduce the poly count"）；石砖加程序化细节（brick-like）；叶子加随机 displacement 并**修法线以改善光照**；树干加木质 displacement 后 **decimation**；
5. **导入引擎**：解说称引擎会**自动把所有程序化 displacement 烘成静态几何**（画面在导入环节是跳切，具体导出参数未展示）；
6. Unity 侧：加 **Terrain** 画高度图、配**树叶/草的 sprite 绘制**（"告诉引擎在哪里画 leaf 和 grass sprites"）、在 Terrain 上画土路、加小丘；
7. 回 Blender 拯救"太球形"的树冠；最终成品展示同一机位的**白天/黄昏/夜晚**三套观感；全片耗时不到 2 小时。

**这个引擎的观感特征**（抽帧客观描述，用于校准我们的观感目标）：低分辨率渲染后放大；地面大片纯色 + **点状/棋盘状抖动过渡**；树冠 2~3 档绿；阴影**块状、边缘带抖动颗粒**；建筑与石头外围有**约 1 像素的浅色描边**（材质里确有独立的 `Edges` 材质），**草叶 sprite 没有描边**；单平行光、硬边；全天候变化靠**整套材质换色**（`DayNightCycle` 文件夹里 Leaves/Stone/Terrain/Water × blue/day/golden/night）。

**关于它的描边：在物体/材质层，不是屏幕空间（2026-09-22 复核，纠正本文初版结论）**
初版本文写"v5 的描边在材质/几何层"，方向没错，但**当时用"内部棱面也有线"去排除反向壳，这个推断是错的**。复核后的物证：
1. Hierarchy 实测是**上百个独立物体**（帧 021：`Cube.030…042`、`Cylinder.003…007`、`Icosphere.003…011`）—— 所谓"内部棱线"其实是**相邻独立物体之间的接缝**，因此反向壳／逐物体边缘光**完全能解释**画面，没有被排除；
2. `Assets/Materials` 里有一个**独立的 `Edges` 材质**（帧 022，纯蓝色块缩略图 → 恒定色/Unlit 类 shader），且它**不在** `DayNightCycle` 文件夹内，而该文件夹是 4 种表面 × 4 个时段共 16 个材质（帧 026）—— **屏幕空间后处理不需要任何逐物体材质**，这个材质是"逐物体方案"的物证；
3. 画面上的细线随昼夜变色（夜里淡紫、白天近白），不是固定墨色。
⇒ **v5 的边缘处理在物体/材质层（逐物体）**；但**具体是反壳外扩、着色器内边缘光、还是程序化生成的线几何，画面无法确定**——这支片的官方字幕里 `outline` / `edge` / `shader` / `rim` **一次都没出现**，全片只讲建模。旁证：受 t3ssel8r 启发的 [David Holland](https://www.davidhol.land/articles/3d-pixel-art-rendering/) 提到"t3ssel8r 在 2020 年前后的早期视频里展示过漂亮的 **procedural outlines**"，而 v5 正是 2020-11。

> 对本文的用处：v5 自身不讲算法，它提供的是**"这套观感长什么样"的实物样本**，以及资产侧的做法（见 §3.3）。

> **后续（2026-09-22）**：v5 的算法**已经找到作者本人的口径**——他在其余 26 条投稿的**官方简介里逐条写清了引擎的算法**（含"边缘高光/阴影 = 深度缓冲取邻域比较后提亮/压暗"、"边缘检测器重写为 normal pass"、"light-aware edge coloration"、"640×360 + snap + 偏移补偿"）。整理成 **[参照-t3ssel8r像素引擎.md](参照-t3ssel8r像素引擎.md)**，本文 §3.1 的"内线"缺口与 §5 的优先级在那里有更轻的路线。

### 1.6 v6 · bugFree — 程序化像素水面（六层）

全片是一支"**零素材下载、全部代码生成**"的水面 shader 教学：
1. **一张遮罩图驱动整片海**——水深、泡沫区、陆地**全藏在颜色通道里**；所有纹理都是代码生成的，**天然无缝平铺**；
2. **第 1 步 深度底色**：一张渐变条染出浅滩到深海；
3. **第 2 步 阳光光斑**：**两层光往相反方向滚动、互相干涉**——"阳光就这样被水面揉碎了"；
4. **第 3 步 波光闪烁**：小小的星芒一跳一跳，**只在波峰上亮起**；
5. **第 4 步 动态泡沫**：白色泡沫一条一条**成环推向岸边**；
6. **第 5 步 波浪岸线**：**"只扭采样坐标，整条海岸线开始呼吸"**（扰动采样 UV，而不是动几何）；
7. **第 6 步 像素化**：**颜色压到 8 级色阶**，再撒上复古的**抖动颗粒**；
8. **第 7 步**：六层按顺序合成 →"一片会呼吸的像素海"。

## 2. 整合出的方案：一条七层管线

把六支讲的散点按"从资产到屏幕"排成一条线。**括号里是出处**；标 ⚠ 的是本仓**尚无**的格。

```
【L0 资产】Blender 低模 + 程序化修改器栈（非破坏性，导出时烘焙）        (v5)
      ↓
【L1 光照与色带】单平行光 + 硬边色带（2~3 档 / 两色端点 N 段常量插值）   (v3 v4 v5)
      │   └─ ⚠ 法线剧变处压暗一级 = 搭色带便车的"隐式内线"              (v3)
      ↓
【L2 抖动】ordered dither，作量化前的扰动                              (v1 v3 v4 v5 v6)
      │   ├─ 范式 (a) 加法阈值偏移，加在"待量化值"上                   (v4 的 2d像素化 废稿 / godotshaders)
      │   └─ 范式 (b) 抖动贴图与颜色做 soft-light 混合                 (v4 v5 主线，t3ssel8r 系)
      ↓
【L3 调色板量化】⚠ 感知色彩空间里取最近调色板色 + 双最近色二选一抖动    (v1 v4 v6)
      ↓
【L4 描边】外轮廓（反向壳）+ ⚠ 内线（深度/法线屏幕空间）               (v2 v5)
      │   └─ 单像素优化 + 明暗双线合成                                 (v2)
      ↓
【L5 像素化】point 降采样到低分辨率 → point 放大回屏（两段式）          (v1 v2 v5)
      │   ※ 本仓铁律：L2/L3 的颜色处理必须落在低分辨率域内（见 §3.1）
      ↓
【L6 水面】⚠ 六层程序化合成，最后一层压 8 级色阶 + 抖动颗粒            (v6)
      ↓
【L7 UI】全分辨率 overlay，不像素化                                    (本仓现行，六支均未涉及)
```

**这条管线告诉我们三件事**：

1. **像素化（L5）只是入场券，观感是靠 L1~L4 撑起来的**。v1 明说"有了像素画的形式，像素画的感觉仍然缺席"；v2 明说"单凭像素化就 3D 像素艺术了"（指技术架子），而 v5 的实物样本里真正让人认出风格的是**抖动过渡、硬色带、细浅描边**这三样。**与本仓 M0 复核结论（像素化在无纹理场景里视觉增量≈0）完全互证**。
2. **L2 与 L3 的顺序是硬约束**：抖动必须在量化**之前**、且作用在"即将被量化的那个值"上（v1 的"颜色问题"与 v4 的实现都指向这里；本仓 §4 现有 Bayer 也是这个位置）。反过来做（先量化再抖动）只会得到噪点。
3. **本仓相对这条管线的缺口只有三格**：L1 的隐式内线、L2/L3 的**帧级调色板量化与第二种抖动范式**、L6 的水面。其余（两段式像素化、相机 snap、色带、反向壳描边）本仓已有，且**比六支里任何一支都更成体系**（相机 snap 两步法、RT 尺寸纪律、正交线宽公式这三点六支视频都没讲）。

### 2.1 v2 / v3 / v5 是同一个算法吗？——不是，得把两条线拆开看

这三支最容易被归成"同一套边缘检测"，实际要拆成**两条独立的线**，而两条线上的结论**正好相反**：

| 看哪条线 | v2（Godot） | v3（Unity URP） | v5（t3ssel8r） |
|---|---|---|---|
| **描边画在哪一层** | 屏幕空间后处理：**原始深度差 + 邻域法线点积**过阈值 | 屏幕空间后处理：**连通域**（用法线预测深度、看残差）→ 1px 膨胀 + 优先级仲裁 | **物体/材质层（逐物体）**：独立 `Edges` 材质；**无**屏幕空间证据 |
| **边缘光 / 内线** | 视频未涉及 | **着色器内**：边缘光门控在连通域上 + 色带在断开处升降档 | **物体/材质层**：细线随昼夜变色，机制未展示 |

- **描边这条线：v2 与 v3 同族**（都屏幕空间、都用深度+法线缓冲、都出 1px 线、都做四邻域判断），但**判据不同**——v2 是"差值过阈值"，v3 是"**平面预测残差 + 连通域**"：后者能跨 `step` 步长桥接断口、能处理法线翻转与空像素，还多一层优先级仲裁，**明显更强**。
- **边缘光 / 内线这条线：v3 与 v5 同族**（都在物体/材质层、都不开额外的全屏 pass），v2 没讲。
- 共同点只有**目标观感**（低分辨率 + 色带 + 抖动 + 细边缘），**不是一个算法**。v3 是六支里唯一**两层都上**的。

### 3.3 资产侧的增量（v5）

v5 的资产做法与本仓 [管线合并-糖豆人式资产架构任务书](../架构/管线合并-糖豆人式资产架构任务书.md) 的「Blender 无头管线 → FBX → SceneKit」主线**方向一致**，可搬的是：

- **"修改器栈留在源文件里、导出那一次才烘焙"** —— 这正好是无头管线的正确姿势：源 `.blend` **不 Apply**，在导出脚本里开 `use_mesh_modifiers=True`（blender FBX 导出）复刻"导出即烘静态几何"，而不是把 Apply 写回源文件；
- **可作起点的修改器预设**（抽帧判读，个别数值存疑，见 §7）：岩石 `Remesh → Displace(noise, Normal, Local, Midlevel 0.0, Strength 0.3~12) → Decimate(Collapse, Ratio 0.11~0.18)`；树干 `Displace(bark, Normal, Local, Midlevel 0.500, Strength 0.100) → Decimate(Collapse, Ratio 0.1795)`；楼梯 `Array(Fit Type: Fixed Count, Relative Offset Y 1.1 / Z 1.2)`；叶球 `Subdivision(Catmull-Clark, Render 2 / Viewport 1) + 2× Displace(noise)`；
- **集合即模块**：他的库文件按 `bricks / materials / primitives / rock / ruins / ruins2 / ruins3 / tree` 切，场景集合按 `地面 / Rocks / Monuments / Leaves / Trunks` 切——与本仓"一个功能模块一个源 .blend"口径可直接对齐；
- ⚠ **不能照抄的两点**：① 他让 **Unity 直吃 `.blend`**（靠本机装 Blender 后台导出）——省事但依赖机器环境、编辑期变慢、版本漂移不可控，本仓走显式 FBX 更稳；② **`Auto Smooth` 在 Blender 4.1 已被移除**（改成 `Smooth by Angle` 修改器 / `shade_auto_smooth` 操作）——写无头脚本时要换写法，这一条直接关系到本仓"低模硬边 + 平滑法线防裂线"的链路。

### 3.4 最有价值的外部参照：`SL0ANE/SloanePixelartURP`（Unity 原生）

本次调研的**最大收获不是六支视频本身，而是顺 v3 追到的这个仓库**——它是**同引擎版本（Unity 2022.3.43f1 + URP 14.0.11）、MIT 协议的自定义像素渲染管线**，且恰好覆盖本仓最缺的两格：

| 仓库里的东西 | 对本仓的意义 |
|---|---|

## 4. 关键实现细节（公式 / 代码 / 参数）

### 4.1 两段式像素化（v1）

```
全分辨率渲染场景 → 在"不透明几何写入相机目标之后、重建之前"插入 pass
  → point 过滤降采样到固定目标分辨率（把像素锁进离散网格）
  → point clamp 采样器放大回屏幕（每个纹素映射到均匀像素块）
```
要点三条：① 两段**都**必须 Point（第二段用 bilinear 就回到糊）；② 注入时机决定了"下游还能不能再动颜色"；③ 验收判据 = **棋盘格图案放大后身份不变**。本仓实现与此同构，差异只在本仓把它放在 `AfterRenderingPostProcessing`（事件 600）。

### 4.2 t3ssel8r 系抖动：2×2 抖动贴图 + soft-light + 常量插值（v4 源码逐字）

`rarepaper/whpu` 的 `3d（viewport）/着色器/成品.gdshader` 三件套（我已 clone 逐行读过）：

```glsl
// ① 2×2 抖动贴图，按"屏幕像素坐标"取模索引（%2 只取到贴图的左上 2×2 个纹素）
vec4 n_out2p0 = texelFetch(dithstyle, ivec2(n_out15p0) % 2, 0);   // n_out15p0 = UV / TEXTURE_PIXEL_SIZE

// ② soft-light 混合（dith_level 是该混合的强度，0 = 不抖）
//    注意：blend == 0.5 是恒等；blend < 0.5 压暗、> 0.5 提亮
base < 0.5 ? mix(base, base * (blend + 0.5),                 dith_level)
           : mix(base, 1.0 - (1.0 - base) * (1.0 - (blend - 0.5)), dith_level)

// ③ 两色端点 + N 段常量插值 → 最近邻取样得到硬色带
vec3 final_color(vec3 cin, vec3 c0, vec3 c1) {          // c0=vec3(0.8) c1=vec3(0.2) 是默认端点
    float best = 1000.0; vec3 r = vec3(0.0);
    for (int i = 0; i < 3; i++) {                        // ← 3 档（分母 2.0，即 float(i)/2.0）
        vec3 c = mix(c0, c1, float(i) / 2.0);
        float d = distance(cin, c);
        if (d < best) { best = d; r = c; }
    }
    return r;
}
```
`3d （LIGHT）/s/gdshader.gdshader` 是同一套的 spatial 版，`light()` 里写：
```glsl
vec3 base  = clamp(dot(NORMAL, LIGHT), 0.0, 1.0) * ATTENUATION * LIGHT_COLOR / PI;
DIFFUSE_LIGHT += final_color(soft_light(base, blend), Vector3Parameter, Vector3Parameter2);
```
`toon.gdshader`（2D 光版）则把 `NdotL` 乘完光色后 `clamp(0.05, 0.95)`，**再拿它去采样一张 1D 渐变 falloff 纹理**（`gradient_falloff : filter_nearest`）得到色带，然后同样走 soft-light + 常量插值——**即"1D ramp 纹理做色带"这个本仓 §4.1 记为等价形态的写法，在 v4 源码里确实被用了**。

**三条读出来的结论**：
1. **soft-light 是简化版**，不是 W3C/Photoshop 那套：把抖动值直接当"混合量"，语义是"在 base 与一个被抬升/压低的 base 之间插值"；`blend = 0.5` 两支都退化为 `base`（恒等）——**这一点决定了抖动贴图的取值必须围绕 0.5 分布**，见 §4.3。
2. **档数由 `float(i)/(n-1)` 的分母定**：源码写死 3 档；要更多硬色带就把循环上限与分母一起调大。
3. **抖动索引用的是"被渲染对象的像素坐标"**（`UV / TEXTURE_PIXEL_SIZE`，在 SubViewport 里即最终像素格坐标），不是世界坐标也不是全分辨率坐标——这与本仓"Bayer 必须按 `floor(positionCS.xy / pixelScale)` 对齐"是同一个纪律。

### 4.3 抖动贴图实测：它就是 2×2 Bayer，且 v4 的归一化会**系统性偏暗**（本条为第一手实测）

我把两张 `dithstyle.png` 都解码成像素（`3d（viewport）/` 与 `3d （LIGHT）/` 各一张），**两张完全相同**，尺寸 2×2、单通道灰度：

| (x,y) | (0,0) | (1,0) |
|---|---|---|
| **(0,·)** | 0.000 | 0.502 |
| **(1,·)** | 0.753 | 0.251 |

即 **`[0 2; 3 1] / 4 = {0, 0.25, 0.5, 0.75}`——标准 2×2 Bayer 有序抖动矩阵**（递归式出处 [Ditherpunk](https://surma.dev/things/ditherpunk/)，2×2 基元即 `[[0,2],[3,1]]`）。索引 `ivec2(pixel) % 2` 使 (x,y) 映射到 (x%2, y%2)，与矩阵排布一致。

**但它没有做中点归一化**（不是 `(m+0.5)/4 = {.125,.375,.625,.875}`）。而 §4.2 的 soft-light 以 **0.5 为恒等点**，取值集合 `{0, .25, .5, .75}` 的**均值是 0.375**，即每个像素平均落在"偏暗 0.125"的混合量上。代入 soft-light 两支：

- `base < 0.5`：乘数 `blend + 0.5 ∈ {0.5, 0.75, 1.0, 1.25}`，均值 **0.875** ⇒ 平均压暗 base 的 12.5%；
- `base ≥ 0.5`：`1 − (1−base)·(1−(blend−0.5))`，因子均值 1.125 ⇒ 结果 `= base − 0.125·(1−base)` ⇒ 同样压暗。

**两支都压暗** ⇒ 整幅画面被这层抖动系统性拉暗（推导为本【第一手】结论，未找到规范级论述，标【AI 提案】）。若本仓要引入范式 (b)：**抖动贴图应用中点版 `(m+0.5)/4`**，让均值回到 0.5 = 恒等；或保持 `m/4` 但把 soft-light 的恒等点从 0.5 挪到 0.375。**本仓现行的 4×4 加法偏移抖动用的是 `(m+0.5)/16`，归一化本来就是对的 —— 这一条不要被 v4 带偏。**

### 4.4 5 色最近邻 + 「双最近色 + 棋盘二选一」抖动（v4 废稿，但有价值）

`2d像素化.gdshader`（作者自标"废稿"）给的是一个**完整可用的调色板量化 + 抖动**算法：

```glsl
// 找到最近的两色 min_index1（最近）、min_index2（次近）
vec4 dither_color = mix(colors[min_index1], colors[min_index2], 0.5);   // 两者中点
if (distance(colors[min_index1], temp) * dith_level >= distance(dither_color, temp)) {
    ivec2 pos = ivec2(UV / TEXTURE_PIXEL_SIZE);
    COLOR = dither_rule(pos) ? colors[min_index1] : colors[min_index2];  // 棋盘格二选一
} else {
    COLOR = colors[min_index1];
}
// dither_rule(pos) = (pos.x + pos.y) % 2 == 0        ← 2×2 棋盘
```
读法：**离最近色"够远"（超过到中点的距离 × 1/dith_level）时，才在最近两色之间按棋盘格二选一**——这等价于"先把待量化值按抖动格偏移、再取最近色"，即 §2 里的**范式 (a)**，只是把"最近两色"的搜索与"选哪一个"解耦了（调色板很小时比逐色求最近更省）。**这正是本仓缺口最直接的参考实现**：本仓要补的"帧级锁板"可以照这个骨架写（把 RGB 距离换成 OKLab 距离即可，见 §4.5）。

### 4.5 OKLab 量化（本项目取 OKLab 而非 CIE Lab 的理由与公式）

**为什么不用 v1 讲的 CIE Lab**：Ottosson 的原文论证是 CIELAB / CIELUV "最大的问题是无法准确预测色相"、"蓝色色相预测很差"；在 Munsell 数据上 CIELAB 会把 chroma 等值圆**压扁**；**蓝→白的混合在 CIELAB / CIELUV / HSV 里会漂向紫色**。OKLab 的设计目标正是"准确预测感知明度/彩度/色相，同时保持简单、数值稳定、可微"。⇒ 本仓【AI 提案】**取 OKLab + 欧氏距离**（OKLab 的设计前提就是让欧氏距离近似感知差，自洽且最省）；CIEDE2000 只在把调色板压到 8~16 色还要抠精度时再考虑（其参考实现约 150 行，含手写 `my_sin/my_cos/my_atan` 等）。

**可直接抄的 OKLab 变换**（基线 sRGB → OKLab，跳过 XYZ，Ottosson 原文代码）：
```cpp
float l = 0.4122214708f*c.r + 0.5363325363f*c.g + 0.0514459929f*c.b;
float m = 0.2119034982f*c.r + 0.6806995451f*c.g + 0.1073969566f*c.b;
float s = 0.0883024619f*c.r + 0.2817188376f*c.g + 0.6299787005f*c.b;
float l_ = cbrtf(l), m_ = cbrtf(m), s_ = cbrtf(s);
L = 0.2104542553f*l_ + 0.7936177850f*m_ - 0.0040720468f*s_;
a = 1.9779984951f*l_ - 2.4285922050f*m_ + 0.4505937099f*s_;
b = 0.0259040371f*l_ + 0.7827717662f*m_ - 0.8086757660f*s_;
```
前置：sRGB 编码值必须先**线性化**（`S ≤ 0.04045 ? S/12.92 : ((S+0.055)/1.055)^2.4`）。⚠ **白点坑**：CIELAB 的实现（如 color.js 的 `lab`）用的是 **D50**（ICC PCS），而 **OKLab 的常数按 D65 推导**，两者不可混用；本仓若同时接 Lab 参照实现，务必核对白点。

**该不该上 KD-tree**：终帧只有 640×360 ≈ 23 万像素、且是一趟后处理，`23 万 × 调色板 16~64 色` 的 OKLab 欧氏循环在 GPU 上先别优化（GPU 上 KD-tree 会被分支发散吃掉收益）。真要加速，优先 ① 把颜色预量化成 **32³ 3D LUT 纹理**采样，② 只在导入期（CPU）用 KD-tree 生成 LUT。【AI 提案，未找到选型出处】

### 4.6 深度 + 法线屏幕空间描边（v2 的七步，补内线用）

```
屏幕像素尺寸 e = 1 / VIEWPORT_SIZE
① 深度边：四次 UV 偏移（左/右/上/下）采样 DEPTH_TEXTURE → 先转线性
           累加 Σ|depth(主) − depth(偏移)|，clamp 限幅，step(阈值) 硬切   （作者演示阈值 0.3）
② 法线边：采样法线纹理 → 值域 0..1 转 −1..1（×2−1）
           不用相减，用「相邻法线点积」→ smoothstep 设阈值      （点积反映角度差；专打内部边缘）
③ 单像素化：把 ①② 的结果按权重合成到同一个函数里（参考 Cody King 的工程）
            —— 直接四次偏移会让轮廓变 2 像素宽
④ 去双重轮廓：造"外轮廓遮罩" = 深度边检测的【反向】结果
              （初值 0.5，循环里改用 depth(主) − depth(偏移) 累加，smoothstep + 锐化乘数 + clamp）
              然后用它去减 ③ 的法线边结果
⑤ 合成明暗双线：内线 = 法线差 − 深度差（clamp）；外轮廓 × 暗线参数；
              屏幕纹理当 albedo（unshaded）→ 叠高亮内线 → 叠暗色外轮廓
```
**与反向壳的分工【AI 提案】**：保留反向壳做**外轮廓**（正交下天然等宽、便宜、可控），新增这一趟只补两类边——① 同色物体的**内部结构线**、② 凹陷处。**必须在低分辨率域跑**（采样步长固定 1 个低分辨率 texel），否则 1 全屏像素 = 0.5 低分辨率像素，边会消失。本仓 `MSAA=0` 正合适（深度/法线纹理用全分辨率光栅，不依赖 MSAA）。

**v3 的替代路线（源码已核，2026-09-22 复核）**：v3 的内线**根本不走描边 pass**——它在 `DiffuseShading()` 里把 `N·L` 用 `multiStep()` 量化成 `level` 档之后，**在连通域断开处把该像素的档位减一**（`ndotl -= singleLevel`），于是"棱线"自然呈现为**降了一档的暗带**；边缘光是另一个独立门控项（连通域 + 屏幕空间光向）再 `multiStep`。⇒ **零额外 RT、零额外全屏 pass**，代价是线宽受几何/密度限制、且只对"表面不连续处"有效（同平面上的贴图交界检测不到）。它的外轮廓则另有屏幕空间实现（`OutlinePass.hlsl`：连通域 → 1px 膨胀 + 优先级仲裁）。**两条路线都留作候选**，M1 样张出对照图裁决。

### 4.7 程序化像素水面六层（v6 + 参考实现）

| 层 | 做法 | 参考出处 |
|---|---|---|
| 遮罩 | 一张贴图的 **RGB 通道分别存水深 / 泡沫区 / 陆地** | v6 第 0 步 |
| ① 深度底色 | `depthDifference = 线性深度(场景深度) − 水面自身深度`；`saturate(diff/_DepthMaxDistance)` 取渐变条 → `lerp(shallow, deep, t)` | [Toon Water — Roystan](https://roystan.net/articles/toon-water/)（`✅调研轮`） |
| ② 阳光光斑 | **两层噪声反向滚动互相干涉**；实现上可用 flow 双层或"双 UV 反向滚动" | v6 第 2 步；[Directional Flow — Catlike](https://catlikecoding.com/unity/tutorials/flow/directional-flow/)（`✅调研轮`） |
| ③ 波光闪烁 | 高光噪声 + 反向滚动噪声 overlay/subtract 后**阈值**出亮点，只在波峰亮 | [Pixel Art Water — godotshaders](https://godotshaders.com/shader/pixel-art-water/)（`✅调研轮`） |
| ④ 动态泡沫 | `saturate(diff/_FoamDistance)` 压低噪声阈值，`step` 硬切出泡沫带（硬边才像素味） | Roystan 同上 |

| ⑥ 像素化 | **压到 8 级色阶** + 抖动颗粒 | v6 第 6 步 |
| ⑦ 合成 | 六层按顺序叠加 | v6 第 7 步 |

**在哪个分辨率域做【AI 提案】**：**着色/焦散/泡沫/量化/抖动这些"每像素"的东西放低分辨率域**（抖动的正确索引本就是最终像素坐标，低分辨率 buffer 的像素坐标正是它；且焦散/sparkle 是高频细节，全分辨率渲染再降采样会被均值抹成灰雾，等于白送一次 box blur）；**顶点波浪保留在几何 pass**（顶点不受像素格约束）。焦散先上"贴图版"（黑白 caustics 两次采样相乘、双 UV 反向滚动），**Voronoi 的 F2−F1 先不上**——朴素 F2−F1 在格子边界会归零、线宽断掉，正确写法要用最近两点的垂直平分线距离甚至两趟 Voronoi（[Voronoi Lines — iq](https://iquilezles.org/articles/voronoilines/)，`✅调研轮`），而像素风下这些高频细节很可能被 640×360 直接吃掉。

## 7. 未解与存疑（诚实清单）

### 7.1 素材与复现
- 6 支视频、逐条转写、抽帧、高倍裁切、两份 YouTube 官方字幕**都在 `external/pixel-render-ref/`（gitignored，不入库）**；一页复现说明（文件对照表 + 复现命令 + 两条网络踩坑）见该目录下的 `MANIFEST.md`。
- 两份参照源码也在工作台：`external/rarepaper-whpu/`（v4）、`external/sloane-urp/`（疑为 v3，见 §7.2 的置信度说明）。
- 转写方式：B 站无 CC 字幕轨（需登录），故用 `faster-whisper`（small / int8 / CPU）本地转写；v1 与 v5 另有 **YouTube 官方英文字幕**作权威对照（v1 的旁白口径以英文字幕为准）。
- **声明**：本轮**没有**逐帧通读全部 264 张抽帧。逐帧只用于三处：v5 的 Blender 面板判读、v3 的观感确认、以及各支的关键帧抽检。因此本文里凡是"画面里某某面板显示了 XX"的细节（尤其 v5 的修改器参数），都存在抽帧判读误差。

### 7.2 存疑清单
1. **v1 的色彩空间口径自相矛盾**：旁白/字幕 = **CIE Lab**（我 grep 官方英文字幕，"OKLab" 零出现、"Lab" 10 次），YouTube 简介与 B 站简介 = **OKLab**。本仓取 OKLab（§4.5），但这意味着**不能把 v1 的实现照着抄成 Lab**。
2. **v3 无旁白**：这支本身只有"叠了个边缘光，在法线变化剧烈的地方把光照放暗一级"一句简介。**该机制已由源码核实**（§1.3 与 §4.6；对应 `ShadingPass.hlsl` 的 `connect < threshold` 时 `ndotl -= singleLevel`），但**"该仓库就是这支视频的工程"这一步仍未闭合**，见下条。
3. **`SL0ANE/SloanePixelart...` 与 v3 作者是同一人的判断：强旁证，未闭合**。支持：① 名字对得上（B 站 `死罗恩` sǐ luó ēn ↔ GitHub 用户 `SL0ANE`、MIT 署名 `Sloane`）；② 简介两句与源码**逐字对应**（"叠了个边缘光" ↔ `RimLightCorrection.compute` / `RimLight.hlsl`；"法线变化剧烈的地方把光照放暗一级" ↔ `DiffuseShading()` 里连通域断开时 `ndotl -= singleLevel`）；③ 题材与资产吻合（仓库全是岩石/石构件资产、有 `005 Rocks.unity`，v3 画面正是石构遗迹）。**不支持的**：v3 的 B 站简介**没有贴**该仓库链接（贴链接的是 v4，指向 `rarepaper/whpu`），仓库内也搜不到任何 B 站链接；且 v3 是系列 #4，与仓库场景编号 001–008 不能一一对应。⇒ 引用时请按"高度可能"而非"已确认"对待。
4. **v5 的修改器参数**：抽帧 960px 判读，若干数值（`Array` 的 `Count`、叶球两个 `Displace` 的 Strength、一处被截断的修改器名 `Set S…`）标为存疑；三个自建 texture datablock（`brick` / `bark` / `noise`）的**纹理类型与生成参数画面完全未展示**——无头管线里必须自己定标准并固定 seed/scale，否则不可复现。
5. **v5 的导出环节整段缺失**（没有 FBX 参数、没有导出脚本；只看到 Unity 侧 `ruins Import Settings` 的 Materials 页）。"引擎自动烘程序化 displacement"**只有解说一句**，未见执行过程。
6. **v6 的完整源码未拿到**（作者要求关注公众号回复关键词领取）。第 5 步"只扭采样坐标"的具体扰动量与第 6 步"8 级色阶"的量化方式（线性 or 感知空间；量化前后顺序）**未确认**。
7. **v2 提到的 Cody King 工程链接未取得**（"单像素轮廓"的具体函数因此只记录了作用、没有记录实现）。
8. **§4.3 的"偏暗"结论是我自己的推导**：抖动贴图未中点归一化这点是**实测**（像素值），但"因此系统性压暗 12.5%"这一步的规范级论述**未找到**，标【AI 提案】；建议引入范式 (b) 时用对照图实测确认。
9. **`(m+0.5)/n²` 与 `m/n²` 的差异**在文献层面未找到一手论述（调研轮的给出推导），标【AI 提案】。
10. **未覆盖的同族技术**：PS1 的顶点吸附与仿射贴图（六支均未讲，属邻支）；体素化/Minecraft 向；手绘 sprite 与 3D 混合渲染。本文只在 §3.1 #12 记录"为何不引入"，未展开实现。
