## 1. 管线总图（顺序铁律）

```
几何（赛璐璐着色） → 描边 pass（反向壳） → 全屏像素化（降采样 640×360，nearest）
    → 最近邻放大回屏幕 → UI overlay（全分辨率，不像素化）
```

**四条顺序红线**：
1. **描边必须在像素化之前**——先降采样会把描边打成断续噪点；RT 空间 1px 的线放大后即 3px 屏幕像素，线宽天然均匀（线宽必须在低分辨率域定义，调研-全屏像素化 §1）。
2. **UI 必须在像素化之后**——否则文字全毁（UI 走独立全分辨率 Canvas，天然满足）。
3. **世界空间文字（伤害数字）走像素化层**用像素数字，别放 UI 层。
4. **上采样（nearest）之后零颜色操作**——之后再做任何引入中间色的操作，都会在明暗交界处插出错误中间调（Catlike Render Scale，调研-全屏像素化 §1.3）。**全分辨率域内的逐像素颜色操作必须与 RT 块对齐**（Bayer 已按 `floor(positionCS.xy / pixelScale)` 对齐，`PirateToon.shader:187-191`）；URP 自带后处理（tonemap/调色/Bloom）跑在像素化**之前**的全分辨率域——属"块对齐"约束的对象，不属"低分辨率域"。

### 2.1 投影比：俯角是唯一决定"像不像"的量

正交 + 方位角 45° 时，两个基元的屏幕投影（世界米 → 屏幕米；ppm 见 §3.1）：

```
地面单位向量 (1,0,0) → (0.7071, ∓0.7071·sinθ)   ⇒ 地面直线屏幕斜率 = sinθ，倾角 α = arctan(sinθ)
竖直单位向量 (0,1,0) → (0, cosθ)                ⇒ 同样世界高度按 cosθ 压缩
边长 s 的地砖 → 菱形宽 1.414·s·ppm、高 1.414·s·ppm·sinθ ⇒ 宽:高 = 1 : sinθ
```

| 俯角 θ | 菱形宽:高 | 地面线倾角 α | 竖线压缩 cosθ | 观感口径 |
|---|---|---|---|---|
| **30°** | **2 : 1** | 26.57° | 0.866 | 经典像素等距（手绘像素画沿用至今的网格）——**本方向裁决档**（2026-09-22） |
| 35.26° | 1.732 : 1 | 30° | 0.816 | 真等距（菱形角 120°/60°）——2026-09-21 的旧裁决档（**已废**：sinθ = 0.5773 与像素网格无整数比，栅格化出的阶梯长短不一） |
| 45° | 1.414 : 1 | 35.26° | 0.707 | 原 AI 提案档（**已废**）；更俯视、更"战棋" |
| 55° | 1.22 : 1 | 39.3° | 0.574 | 近俯视；墙与单位的竖向被压掉 43% |

两条要点：

- **俯角与玩法零耦合**：弹道/AI 落点/分路全在 XZ 平面表达（[M2 空间契约](../../设计/3D空间模型对齐.md) §1/§3），不含任何俯角量。改俯角只改画面、不改规则——"45° 与空间契约一致、零迁移成本"这条论证因此不成立（俯角本来就没有迁移成本）；"2:1 是 2D 贴图时代的约定、3D 无收益"也只说对了一半：**3D 里 2:1 不再承担贴图拼接职责，但它仍然唯一决定屏幕上的菱形比**——这正是观感本身。
- **方位角只有 45° 给对称菱形**：设方位角 φ，两条地面轴的屏幕斜率 `tanα_X = sinθ·tanφ`、`tanα_Z = sinθ/tanφ`——φ=45° 时两轴相等（菱形）；φ=30° 时是 18.4° 与 45°（歪四边形）。自由环绕另会让所有边缘落到非整数像素格上（爬行/闪烁）。
- **地面纹素在屏幕域纵向压缩**（30° 时 1:0.5，纵向屏幕密度 = ppm × sinθ）：全场景一致，读作等距风格本身，不需要修；资产篇 §6 的 Jacobian 检查是 UV 域均匀性，与此无关——试产出图勿把该压缩误判为贴图做错。

**【创始人裁决 2026-09-22】游戏内俯角固定 30°、方位可自由旋转**（原话：「游戏内应该俯仰角固定 30 度，但是左右可以随便旋转」）。三个落点，都已落地：

1. `BattleCameraController.OrthoPitchDegrees` = **30°**（值直接引用 `PixelartPilotScene.PitchDegrees`，不再各写一份——出图与游戏内的投影必须是同一个，否则"拿宣传图比观感"这件事本身不成立）；
2. 场景烘焙 FollowOffset = 30 × (cos30°·0.7071, sin30°, cos30°·0.7071) ≈ **(18.371, 15, 18.371)**（走 `BattleScenePipeline` 重烘，不手改场景；公式由 `BattleCameraController.OffsetDirectionForPitch` 单向提供，装配器不再自带一份）；
3. 方位角**不进常量**：由右键拖拽的 `_manualYaw` 承担，0 方位 = 烘焙机位朝向（45° 对称菱形）。
   2026-09-21 的"真等距 35.264° + 方位固定 45°"整条作废（含当时的"右键环绕退役"）。

## 3. 全屏像素化（RendererFeature）

- **不要用 URP Render Scale**（放大是线性过滤，会糊）。
- 自写 `ScriptableRendererFeature`：`AfterRenderingPostProcessing` 时机抓 `_CameraColorTexture` → **nearest Blit** 到 640×360 的 **Point filter** RT → **nearest Blit** 放大回屏幕。两步全 Point，块感才干净。
- **blit 材质用 URP 自带 `Hidden/Universal/CoreBlit` 的 pass 0 "Nearest"**（不要自写 blit shader：首版自写 PixelBlit 在播放器真实 GPU 会话报 not supported，编辑器/构建期都不暴露；CoreBlit 被 URP 运行时引用、构建必然保活）。实现：`PixelationRendererFeature` + 安装器 `PixelationInstaller`。
- 正交 size 与 RT 分辨率无关（正交下 size 直接就是可见世界半高；「渲到 RT 按 ÷3 缩 size」是透视时代残留，见 §3.1 推论 2）；改 RT 必须同改 size 才保住 ppm 密度。
- RT 分辨率起步档 **640×360**（16:9 整数四分之一）；像素度是随资产成熟可调的演进项（美术指南待定项 #2/#3）。

### 3.1 像素密度方程：RT 高 / 正交 size / 纹素密度 是一组耦合量

```
ppm（屏幕像素/米，本方向唯一的美术密度量） = RT高 ÷ (2 × 正交size)
可见世界高（米）                            = RT高 ÷ ppm
「1 纹素 = 1 屏幕像素」的达成条件【AI 提案】 = 纹素密度（资产篇 §1）= ppm
1 RT 像素描边的世界厚度                      = 1/ppm 米 = 单位身高 h 的 1/(ppm · h · cosθ)
```

现役档位对照（RT 高 360、纹素密度 32px/米、单位 1.2m、俯角 30°）。【AI 提案·待补】后两列按**旧**的单位高
1.2 m 与旧俯角手算，而现行单位高是 1.85 m（`CrewVisualPrefabBuilder.TargetUnitHeight`）、俯角 30°
（cosθ = 0.866）——重算前只当前后档位的**相对**比较用：

| 正交 size | 档位（`BattleCameraController`） | ppm | 1.2m 单位屏高 | 纹素/屏幕像素 | 1px 描边占单位屏高 |
|---|---|---|---|---|---|
| 5 | 特写（开局默认） | 36 | 35px | 0.9 | 2.8% |
| 9~10 | 美术指南 §2.1 举例值 | 18~20 | 18~20px | 1.6~1.8 | 5.1~5.7% |
| 17 | 全场（烘焙档） | 10.6 | 10px | 3.0 | 9.6% |
| 30~48 | 全景（`span×0.3`） | 6~3.8 | 6~4px | 5~8.5 | 17~27% |

四条推论：

1. **"1 纹素 = 1 屏幕像素"只在特写档成立**：32px/米 的纹素密度是照特写档定的；全场/全景档纹素被缩 3~8 倍，纹理里的结构线与砖缝随之消失，而 1px 描边相对单位身高涨到 10%~27%（单位糊成一团黑）——**线宽与纹素密度都必须按目标档位核算，不能全项目单值**。
2. **RT 高与正交 size 必须成对改**：固定 RT 改 size = 改密度；改 RT 必须同改 size 才保住密度。"正交 size 按比例缩（目标视野 ÷ 3）"是透视时代残留——正交下 size 直接就是可见世界半高，与 RT 分辨率无关。
3. **缩放区间（3~60）跨 20 倍密度**：要么锁死单一档位，要么让 RT 高/线宽/纹素密度随档联动（每档一颗 RT），要么对远景档降级像素化口径——**先定"缩放预算"再报工期**（这就是美术指南待定项 #2/#3 与裁决点 #4 的实质内容）。
4. 【AI 提案·未实拍验证】**降采样路径本身是观感变量**：现行实现是"全分辨率渲染 → point 降采到 640×360 → point 放大回屏"（`PixelationRendererFeature`），几何的亚像素细节（细纹理、细线）会被 3× 点采样欠采，产生摩尔纹与线宽抖动；若改为**几何直接渲进 640×360 RT**（再整数放大），则每个 RT 像素由光栅化直接判定，纹理与线宽天然干净，且真省 fill rate。§1 红线 1"线宽在低分辨率域定义、放大后天然均匀"只在后者成立，前者需 M1 对照图验证（对照项：直接渲进 RT vs 全分辨率渲染后降采）。

## 4. 赛璐璐（Cel-Shading）

1. **档位实现**：2~3 档用**显式非等宽阈值阶梯**（每档阈值 + 每档颜色独立暴露给美术）；等价形态可选 3~4 px 的 1D ramp 纹理（点采样，美术改色方便；X-Toon/UTS 框架）。边界主路径 `step()` 硬切——640×360 nearest 会自动像素化边界；fwidth/平滑保留为高分屏预览宏，**硬切↔羽化做成 0~1 参数**交样张裁决（FTK/Tunic 实为软过渡，调研-赛璐璐 §6）。
2. **暗部不做纯乘暗，也不在 shader 里跑 HSV 变换**：**替换式预制暗部色**（材质参数或 ramp 对应档，偏冷/偏紫一档由美术在调色板内选色表达）——产品级管线（UTS3 三色域/Xrd 暗部贴图）全部如此；数学在线性空间，光色乘在亮暗两侧（调研-赛璐璐 §3）。
3. **镜面高光去掉**；rim light 可选但与描边叠加会"双倍边缘"，只用时收窄到背光侧。半兰伯特默认不用（压缩两端对比），剪影内部死黑成片再开。**实现现状**：`PirateToon` 用 `t = NdotL×0.5+0.5` 重映射（`PirateToon.shader:184`）——因为颜色不乘 `t`、只拿它选档，重映射不压缩对比，属等价形态而非条款违背。
4. **色带过渡加 4×4 Bayer ordered dithering**：抖动加在**档位选择值**上（`t = NdotL + (bayer-0.5) / levels` 再切档），幅度 ≈ 1 个量化步长；矩阵用**中点归一化 `(m+0.5)/16`**（直接除 16 整体偏亮）；比较在线性空间（调研-赛璐璐 §4）。
5. 接收阴影关闭（色带表面接实时投影必脏），体积感靠色带 + blob shadow + 描边三板斧。
6. **单平行光 + 单环境光**，方向永远左上（全局光约定，美术指南 §3.1）——实现上把方向/颜色烘成静态 uniform，**跳过 URP shadow 关键字族与 shadowCoord**（砍掉全部 shadow variant，调研-赛璐璐 §2）。
7. **顶点色 R = 色带阈值偏移**（Xrd 工作流性价比最高的一条）：美术刷顶点色即可逐区域改色带切分点，专治脸/下颌/披风切错位置（调研-赛璐璐 §5）。

## 5. 描边（卡线）

- 方案：**反向壳**（新 pass：Cull Front + 顶点沿法线外扩 + 纯色），LightMode 用 `SRPDefaultUnlit`（独立 LightMode 铁律，[描边Shader调试.md](描边Shader调试.md) §八）。
- 不用屏幕空间边缘检测：正交下反向壳线宽天然恒定，且内缘不出杂线。
- **低模硬边会裂**：外扩用**平滑法线**——Blender 导出前把 custom split normals 烘进**顶点色**（写入导出模板，见资产篇 §6），shader 读顶点色外扩。
- 线宽：RT 空间 1px 起步；颜色统一墨色（与 UI 令牌 `INK` 同色，3D/2D 描边同色统一）。**试点实测取 2px**（`ToonPilotSetup`：1px 经 3× 点降采不可见）——终值必须按 §3.1 的 ppm/档位核算，不是全项目单值。
- **线宽公式（正交）**：`positionCS.xy += normalCS.xy（x 乘纵横比修正）× (2 ÷ RT高) × 像素数`——正交 `w≡1` 自动等宽；**不对 `normalCS.xy` 二次归一**（法线朝屏时数值不稳）；RT 尺寸变化时 C# 每帧下发 RT 高（Toon RP 生产级公式，调研-反向壳 §4）。
- ZTest LEqual、ZWrite Off、Cull Front；斜面 near-parallel 处的 z-fight **实现上未用 `Offset 1,1`**，改用**沿视线拉近 5× 线宽**（`PirateToon.shader:331` `positionVS.z -= pixelWorld*5.0`，覆盖前缘 ~0.4u 深度差；shader 头注释仍写 Offset，待改）；相邻物体互相漏线是反向壳固有限制（像素风下通常可接受，需抑制时按层规划 Stencil）；壳环还需 **Geometry 队列 +50** 才不被海面盖掉、`|P.m11|` 需**负值钳位**（防投影翻转时线宽爆 5000 倍）——两条实拍结论待回写调研-反向壳。
- **平滑法线的烘焙与编码**：角度加权平均 + 位置容差合并（优于等权平均）；静态网格存**顶点色**（与 Xrd 阈值偏移共存【提案】：法线占 GBA、阈值占 R，8bit 编码 `×0.5+0.5`）或 UV2 八面体编码（编解码必须成对锁死演化）；程序化件在 Unity 生成时直接算，Blender 手作件走文件名后缀 + AssetPostprocessor 自动烘焙（完整先例见调研-反向壳 §3）。
- **内部结构线**（船舷棱线/甲板边缘）不靠 shader：画进纹理（资产篇 §5）。

## 6. 阴影与光照全局设置（URP Asset）

| 项 | 值 | 理由 |
|---|---|---|
| HDR | **关** | HDR 下色带渐变脏 |
| MSAA | **0** | 边缘平滑与像素化冲突（"灰边"头号来源） |
| Bloom | **关**（现状未达标：`Assets/Art/Rendering/BattleGlobalVolumeProfile.asset` 仍 `active: 1`/`intensity: 0.42`/`threshold: 1.05`，由 `Battle.unity` 的 Global Volume 生效，随 M2a 退役） | 理由**不是**"辉光横跨像素网格"——URP Bloom 跑在像素化**之前**，光晕会被 point 降采量化进 360p 网格（得到块状辉光，与参考图的柔光观感同源）。真问题是柔光/星芒缺替代机制（§7、裁决 D1） |

## 7. 配套系统

- **特效**：粒子 + 全屏像素化（自动风格化，不要给粒子写像素 shader）；大招可配 8~12 帧手绘序列帧点睛。
- **帧级调色板（演进项，暂不实施）**：现行锁板只发生在烘焙期（纹理侧），渲染期经光照乘法/色带选择/Bayer 抖动后颜色会漂出板外——目标是「接近板内」（替换式暗部/tonemap 全拆提案/HDR 关都在收敛此差距）而非「严格板内」。严格锁板需在 360p 域内加一道全屏最近邻板映射 pass；出图判色出现「颜色不够板」时先归因到这条再调参【创始人裁决 2026-09-21：列为演进项】。
- **柔光与星芒【裁决 D1·待定】**：参考观感里最显眼的一层（宝箱/宝石光环、四角星芒）在当前条款组合下（附加光 0 + Bloom 关 + 无自发光通道）**无任何实现机制**。两条候选：①**像素化之前的低分辨率域内 bloom**（光晕随 360p 一起量化，观感接近手绘柔光；URP Bloom 现成，只需从"退役项"改判为"保留项"）；②手绘替代（发光纹素/星芒贴片/8~12 帧序列帧）。两者都要回答"发光色如何进 32~64 色板"（建议留 4~8 个 emissive 板位）。M1 出对照图后裁。
- **局部暖光池【缺口·已有一条外部解法】**：单平行光 + 扁平环境光 + 附加光 0 的组合下，火把/宝箱那种"局部暖光池"只能靠自发光贴图或贴花——通道与锁板归属未定，归 M1 样张（若要，建议走烘焙式贴花而非实时附加光）。**2026-09-22 补充**：t3ssel8r 的动态光做法证明**附加光可以存在而不破坏色带**——**加法式附加光、显式绕开 ramp**，再把结果**量化回档位**；另外他把**光源位置/强度按极低帧率抖动**来强化手绘闪烁感。出处见 [参照-t3ssel8r像素引擎.md](参照-t3ssel8r像素引擎.md) §1.7（作者原文）——即本缺口不必只走烘焙贴花，且这条同时是"柔光与星芒"候选①之外的第三条路。
- **运动游动**：慢速移动直接接受（复古感）；高速物体（炮弹）可按像素格 snap。
- **性能**：现行两段 blit 是"全分辨率渲染 + point 降采/升采"，**没有 fill rate 收益**（反而多两次全屏 blit）；要真省 fill rate 得让几何直接渲进 640×360 RT（§3.1 推论 4）。正交无 LOD。

## 8. 实施顺序（新方向第一个会话的开工序列）

> 本节五步序列已升格为 [立项任务书](../美术翻新-等距像素卡通立项任务书.md) §4 的里程碑 **M0–M5**（样张先行：退役项后置到样张过审之后），执行以任务书为准。

1. ⚠ **正交相机切换 + 像素化 RendererFeature**——技术件已落地（`PixelationRendererFeature`/`PixelationInstaller`/
   `BattleCameraController` 正交化/URP 四件），但 **2026-09-21 复核判定观感目标未达成**：r1 验收的「3×3 块内方差 0.00」
   判据无法区分「像素化生效」与「平涂画面本无细节」，且正交 17 取旧透视当量、像素化作用于无纹理场景 ⇒ 视觉增量≈0。
   本步定性为**不可见基座**，第一个可验收的观感里程碑是第 2+3 步合并的「风格样张」；返工与判据纠偏见
   [美术翻新立项任务书](../美术翻新-等距像素卡通立项任务书.md) M0（基线纠偏）/M1（风格样张）；
2. **赛璐璐 shader + 反向壳描边**——拿现有 Battle 场景一个岛台试点；验收 = read_console 零 shader error + 出图判据（程序化判图纪律，AGENTS.md）；
3. 调色板定档（32~64 色）+ Blender 量化脚本，翻新第一个资产对效果（衔接 [像素纹理资产管线.md](../资产管线/像素纹理资产管线.md)）；
4. UI 生成器 + 一屏换装试点；
5. 批量翻新，像素化强度随资产成熟逐档调低。

## 9. 排障速查（出问题先查这里）

1. **像素有灰边** → MSAA 没关 / RT filter 不是 Point。
2. **色块脏/渐变脏** → 纹理进了 BC1/BC3 压缩（见资产篇）/ HDR 开着 / 没加 Bayer dithering。
3. **描边断续或 UI 被像素化** → 管线顺序错（§1 四条红线）。
4. **上采样后颜色又变脏** → 违反红线 4（颜色处理必须全部在 360p 域内完成）。
5. **颜色漂出调色板** → 预期内（帧级锁板未实施，§7 演进项）；只有贴图本身唯一色数超板才算资产事故（资产篇 §8）。
