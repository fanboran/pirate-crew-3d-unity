## 1. 同构先例（按相关度排序）

### 1.1 bababuyyy/unity-isometric-pixel-pipeline（309★）【已核 README 全文】——本仓的「参考答案」

与本仓定位几乎重合：等距 + 640×360 + 描边 + toon 的 Unity 管线。关键架构结论：
- **5-Pass RendererFeature**：CopyColor（相机目标不能同帧读写，先拷贝）→ 降采样到 640×360 → **描边在低分辨率上计算**（`_BlitTexture_TexelSize = 1/640,1/360`，每个 kernel 步长恰为最终 1 像素，与屏幕分辨率无关）→ Composite → Sharp Upscale（fwidth+smoothstep，非纯 nearest）+ `_PixelPanOffset`。
- **Pixel-Perfect Panning 两步法**（见 §2，防像素游动的核心）。
- 已知限制：**SSAO 必须关**（草地 artifact）——与本仓 M-A 退役 SSAO 的裁决互证。

### 1.2 whateep/unity-simple-URP-pixelation（110★）【已核源码】——结构相同、细节反面教材

两段式 blit（`GetTemporaryRT` Point + 材质 blit 下去 + 无材质 blit 回来）与本仓 `PixelationRendererFeature` 同构。反面教材：宽度 `(int)(h * aspect + 0.5)` 四舍五入——**非 16:9 窗口下宽度非整、采样网格与屏幕网格不重合 → 不均匀像素**。本仓现行实现是 `ceil(高×宽高比/2)×2` 偶数对齐，方向正确。

### 1.3 Catlike Coding — Custom SRP: Render Scale【已核】——顺序铁律的权威出处

低分辨率渲染 + 后处理 + 最后一次上采样的完整方案。**关键排序结论：一切颜色处理（tone mapping / 调色分级 / 抖动 / 量化）必须发生在低分辨率 buffer 内，上采样（nearest）之后不得再做任何会引入中间色的操作**——对插值出来的颜色做 LUT 会在明暗交界处插出错误中间调。`_ScreenParams` 与 buffer 尺寸不一致时自备 `_CameraBufferSize` 修正。

## 2. 相机像素游动（Pixel Swim）两步法【本调研最重要的新增量】

**症状与机理**（David Holland【已核】）：低分辨率下移动 3D 相机，屏幕像素 swimming/creeping/jittering——世界坐标连续变化，但像素网格离散，边缘像素在两档之间跳变。

**两步法**（David Holland 提出、bababuyyy 工程化）：
1. **视空间 snap**：把相机位置 snap 到「视对齐的、texel 大小的网格」——消除游动，但移动变顿挫；
2. **UV 反向补偿**：把 snap 误差转成 UV 偏移传给放大 shader（`_PixelPanOffset`）——恢复平滑移动同时像素网格稳定。

流程：`真实位置 → worldToCamera → XY snap 到 texel 网格 → 求误差 → 相机用 snap 后位置 → 误差转 UV（×2/RT 尺寸）→ 上采样 shader uv += offset`。texel 尺寸 = `正交 size × 2 / RT 高`。

**对比**：Caldera Interactive【已核】的世界轴分轴 snap（俯角 45° 时 Z 步长按 √2×(1/32) 斜边换算）只对特定机位成立；**视空间 snap 更通用**（任意旋转/俯角），本仓采纳视空间方案【提案】。正交 size 变化（缩放）时 snap 网格随缩放更新、缩放本身按整数像素步进（Unity 官方 Pixel Perfect Camera 同款做法）。

**官方词汇参照**（Unity 2D Pixel Perfect【已核】，2D 包本身不适用 3D renderer）：Reference Resolution + Upscale RT（"unaliased and unrotated pixels"）+ Snap 网格 = 1/PPU + **Cinemachine 与像素完美组件会争夺正交尺寸控制权**——本仓 Cinemachine 驱动相机，snap 要做在 `BattleCameraController` 输出与 vcam 之间，不能挂独立组件打架。

## 3. RT 尺寸与整数缩放纪律

- 内部高锁 360；宽 = 偶数对齐（本仓已实现），**不要**四舍五入（whateep 反例）；
- 屏幕恰为 640×360 整数倍（1080p=3×）走纯 nearest 零失真；非整数倍窗口接受 ±1px letterbox/crop（官方 Crop Frame 思路），不追求满屏拉伸；
- 降采样与升采样全程 Point filter + `sampler_point_clamp`（本仓 CoreBlit pass 0 已满足）。

## 5. 备用件

- **正交深度线性化**（KYRIOTA【已核】）：正交下 raw depth 已是 linear01，但 near/far 跨度大（本仓 0.1~400）时差异过小，叠深度类效果需按 near/far 重缩放——像素海面/深度特效时用得上。
- **伪带限过滤**（themaister【已核】，属纹理侧）：像素纹理在 3D 曲面上 Point 采样的闪烁边界情形——等距固定机位下风险低，闪烁时在 shader 内加 2x2 伪带限（一次 bilinear fetch），不重开 mip（详见[调研-调色板量化](../资产管线/调研-调色板量化与纹素密度.md) §6）。

## 6. 对渲染篇的回写结论汇总

采纳【AI 提案】：① **相机 snap 两步法**（视空间 snap + 上采样 UV 补偿，接入 `BattleCameraController`，M-B 落地）——这是渲染篇 §2「按像素格 snap」一句的工程化升级；② 颜色处理顺序铁律成文（dither/量化/调色全部在 360p 域内，上采样后零颜色操作）；③ RT 宽度偶数纪律维持；④ Frame Debugger 核对双 blit 的验收习惯。
维持：两段 nearest blit 架构、CoreBlit pass 0、UI Overlay 分离。
提示：FTK/Tunic/Prodeus 公开材料均为观感佐证、无管线细节可引用（Tunic 仅玩家侧证实「低内部分辨率渲染」）——本仓规格依据以本文已核技术来源为准。
