## 1. 分层与程序集

工程用 **10 个 `.asmdef`** 把依赖方向**钉在编译期**——违规不是"代码审查时被指出"，而是编译不过。

| 程序集 | 位置 | 引用 | 平台 |
| --- | --- | --- | --- |
| `PirateCrew.Core` | `Scripts/Core/` | （无） | 运行时 |
| `PirateCrew.Gameplay` | `Scripts/PirateCrew/` | Core, Rendering, TMP | 运行时 |
| `PirateCrew.CrewManagement` | `Scripts/CrewManagement/` | Core, Gameplay | 运行时 |
| `PirateCrew.Campaign` | `Scripts/Campaign/` | Core, Gameplay, CrewManagement | 运行时 |
| `PirateCrew.UI` | `Scripts/UI/` | Core, Gameplay, Campaign, CrewManagement, TMP | 运行时 |
| `PirateCrew.Rendering` | `Scripts/PirateCrew/Rendering/` | URP Core + Universal | 运行时 |
| `PirateCrew.SceneArtBake` | `Scripts/PirateCrew/SceneArtBake/` | Core, Gameplay, Rendering | **Editor only** |
| `PirateCrew.Tests` | `Tests/` | 全部 + TestRunner | **Editor only** |
| `PirateCrew.PlayModeTests` | `Tests/PlayMode/` | 核心几个 + TestRunner | 运行时（PlayMode） |
| `PirateCrew.ArtPipelineTests` | `Art/Tests/` | TestRunner | **Editor only** |

绘制成图（箭头 = "可引用"）：

```
                    ┌────────────────┐
                    │ PirateCrew.Core│ ← 零游戏依赖：事件总线/服务/日志/存档/场景流转/组合根
                    └───────┬────────┘
                            │
                    ┌───────▼────────┐
                    │PirateCrew. │ ← 玩法与表现的主体（见 §3 的边界说明）
                    │Gameplay │
                    └───┬────────┬───┘
        ┌───────────────┘ └───────────────┐
┌───────▼────────┐ ┌─────────▼────────┐
│PirateCrew. │ │PirateCrew. │
│CrewManagement │ │Campaign │
└───────┬────────┘ └─────────┬────────┘
        └───────────────┐ ┌───────────────┘
                ┌───────▼────────▼───────┐
                │ PirateCrew.UI │ ← 顶层：只被场景依赖
                └────────────────────────┘

旁支：PirateCrew.Rendering（依赖 Core + URP 的像素化渲染工具层，被 Gameplay / SceneArtBake 引用）、PirateCrew.SceneArtBake（Editor-only 烘焙器，依赖 Core / Gameplay / Rendering）
```

**三条依赖规则**（违反即在编译期失败）：

1. **只许指向下层**。`Core` 不引用任何游戏程序集——它连"关卡"是什么都不知道。
2. **不得成环**。元游戏（Campaign / CrewManagement）可以依赖玩法，玩法**不得**反向依赖元游戏。
3. **跨模块只走两条通道**：`XxxApi` 静态外观（如 `CampaignApi`）或事件总线（§5）。**禁止**跨模块裸
   `GetComponent`、禁止运行期按名字/类型查找（§7）。
   **豁免——数据目录类**：`XxxCatalog` 这类纯 C# 只读数据目录（如 `WorldMapCatalog`）允许下游模块
   直读（既成事实如 `CampaignProgress` 直读 `WorldMapCatalog` 校验海图 id），不走 Api/事件——
   它们是常量表不是服务，套 Api/事件外壳只会加一层转发；豁免仅限**只读查询**，写操作仍走两条通道。

> 为什么用 `.asmdef` 而不是"目录习惯"：本项目此前的跨模块依赖是**靠人记**的，
> 结果 `BattleController` 引用了 `Campaign`，而 `Campaign` 又引用 `Battle` 的类型——
> 只有把所有代码编译在一起才不报错。程序集边界让这类问题当场暴露。

## 3. 运行时分层：规则与服务

工程在「**纯 C# 规则**」与「**MonoBehaviour 胶水**」之间有一条刻意维持的界线：

| 层 | 形态 | 例子 | 测试通道 |
| --- | --- | --- | --- |
| **规则层** | `static` 纯函数类，不 new GameObject、不引 MonoBehaviour | `Combat/ExplosionResolver`、`Battle/TurnRules`、`Battle/InteractionRules`（两态状态机）、`Battle/StandardThrowRules`（标准投掷模组）、`Battle/Levels/LevelAssetRules`、`UI/SettlementPanelRules` | 无头验证台（秒级）+ EditMode |
| **数据层** | 纯 C# 载荷 + `ScriptableObject` 宿主（§6） | `LevelAssetPayload`、`WeaponCatalog` | 无头 + EditMode |
| **编排层** | `MonoBehaviour`，只做"取引用 → 驱动 → 调纯函数" | `BattleController`、`TurnManager`、`BattleInteractionController`（两态交互 + 操作模组编排） | PlayMode |
| **表现层** | `MonoBehaviour` + 资产 | `AudioService`、`FxRoot`、`OceanRig`、`AmbientDirector` | PlayMode |

**为什么坚持这条线**：无头验证台（`dotnet` 直接编译工程源码跑 NUnit）在 `new GameObject()` 上必抛
`SecurityException`（原生 ECall 离不开 Unity 运行时）。把规则写成纯 C# 就能**在几秒内跑 1200+ 条断言**，
而不必每次开 Unity（开一次要几十秒且独占 `Library/` 锁）。这不是洁癖，是迭代速度。

> 写新逻辑时的默认动作：**先问它能不能是纯函数**。能，就放规则层并写无头测试；
> 不能，就写成薄壳并把判断逻辑推回规则层。

## 4. 生命周期：唯一入口 → 组合根 → 模块接线

### 4.1 一张图看懂启动

```
[引擎] RuntimeInitializeOnLoadMethod(BeforeSceneLoad) ← 全仓只有这一处
   Core/GameEntryPoint.Enter()
     │
     ├─① 清空静态残留
     │ EventBus.ResetForNewSession() / Services.Clear()
     │ → 各模块 [GameBootstrap(ResetStatics)]：LevelAssetLibrary / WorldMapRuntime /
     │ CampaignApi / CrewManagementApi / BattlePause
     ├─② 解析命令行（唯一一次 argv 读取）
     │ Core/CommandLineOptions.Parse() → ToolFlags 登记的全部开关
     ├─③ 保证服务宿主存在（从任意场景按 Play 也能跑）
     │ Core/Bootstrapper.EnsureInstalled()：建 "Services" 宿主（DontDestroyOnLoad）
     │ → AddComponent<SceneLoader>() + Services.Register()
     │ → AddComponent<SaveManager>() + Services.Register()
     └─④ 跑模块接线
           → 各模块 [GameBootstrap(Initialize)]：AudioService.Install → FxBootstrap.Install →
             CampaignApi.Install → 命令行工具模式（出图 / 样板）

[引擎] 首个场景加载 → 各 Awake → Start
   Core/Bootstrapper（只出现在入口场景）：
     Awake → EnsureInstalled()（幂等，已在 ④ 装好则只对齐实例）
     Start → SceneLoader.ChangeScene(MainMenu)
```

### 4.2 三条规则

1. **入口唯一**：全仓只有一个 `[RuntimeInitializeOnLoadMethod]`，在
   `pirate-crew/Assets/Scripts/Core/GameEntryPoint.cs`。
   `grep -rn "RuntimeInitializeOnLoadMethod" pirate-crew/Assets/Scripts` 只应命中该文件。
   选 `BeforeSceneLoad` 的理由：`SubsystemRegistration` 早于程序集加载完成（发现不到模块程序集），
   `AfterSceneLoad` 晚于首个场景 `Awake`（"从任意场景按 Play 也能拿到服务"立刻失效）。

2. **组合根唯一**：`Core/Bootstrapper` 是创建与登记全局服务的地方，服务注册进
   `Core/Services`（`Register<T>` / `Get<T>` / `TryGet<T>` / `Clear`）。`Services` 是
   **组合根专用的显式服务定位器**，不是全局单例垃圾桶：它不创建实例、不做反射注入，
   只登记"组合根拥有、进程级存活"的服务。`EnsureInstalled()` 幂等，被入口场景的 `Awake`
   与 `GameEntryPoint` 两条路径共用。

3. **模块接线显式声明**：`Core` 零游戏依赖，编译期看不到高层模块，所以"组合根调用模块 Initialize"
   不能写成静态调用。模块用 `[GameBootstrap(phase, order)]` 声明自己的接线入口，唯一入口按
   `ResetStatics → Initialize` 两阶段、阶段内按 `order` 调用；顺序可由
   `GameBootstrap.DescribeAll()` 全量列出，并由测试钉死。

### 4.3 明确禁止

- **禁止在 `Awake` 里"把自己接进全局系统"**。重构前 `CampaignApi.EnsureBootstrapped()` 由三个
  UI 控制器的 `Awake` 调用：换一个进入路径就少一份接线，且没有任何日志能证明它跑没跑。
- **禁止自挂 `[RuntimeInitializeOnLoadMethod]`**。重构前有 14 处分散在 5 个程序集，初始化顺序
  靠执行时机而非代码。
- **禁止在业务代码里扫 `Environment.GetCommandLineArgs()`**。运行时唯一读取处是 `Core/CommandLineOptions.cs`
  （`Assets/Editor/` 下的批处理工具入口各自读取 argv，属编辑器工具链，不在业务代码范围）。

## 5. 事件契约

模块间通信走 `Core/EventBus`，事件键是**类型化频道**——每个事件在所属模块的 `XxxEvents` 类里
声明一个 `public static readonly Event<TPayload>` 字段（无载荷用非泛型 `Event`）：

```csharp
EventBus.Publish(BattleEvents.CrewDamaged, payload); // 载荷类型由频道锁定
EventBus.Publish(SceneEvents.GoBack); // 无载荷事件
EventBus.Subscribe(BattleEvents.CrewDamaged, handler); // handler: Action<CrewDamagedPayload>，T 由频道推断
EventBus.Subscribe(SceneEvents.GoBack, handler); // handler: Action
EventBus.Unsubscribe(BattleEvents.CrewDamaged, handler);
```

### 5.1 为什么键要进类型系统

频道实例即事件键，泛型参数把「键 → 载荷类型」在声明处锁死一次：**键拼错、键与载荷张冠李戴**
都是**编译错误**（CS1503）。发布方与订阅方对着同一个频道字段取类型，两侧行不一致在编译期
不可能写出。无载荷事件用非泛型 `Event` 频道 + 无参 `Action`，不要 `Event<NoPayload>`。
契约全貌的登记表在 [EventBus事件契约.md](EventBus事件契约.md)。

### 5.2 误用守卫

变量声明成基类 `Event` 会逃过重载选择，两类结构性误用由 EventBus 在订阅/发布时拦截：
`Event<NoPayload>` 频道走泛型重载、载荷频道经基类引用误用无载荷重载。EventBus 拒绝投递、
记 `EventBus.ContractViolations` 并在编辑器/开发构建下告警。残余盲区（频道声明本身定错、
载荷字段填错）见契约文档 §5。

### 5.3 热路径不分配

每个事件频道维护**缓存快照**，只在订阅/退订改变列表时置脏重建，订阅表不变时重复 `Publish`
零分配。两条测试钉住它（订阅表不变时 1000 次 `Publish` 不重建快照；`GC.GetAllocatedBytesForCurrentThread()` 差为 0）。

### 5.4 逃生口（唯一一处）

`AudioService` 按频道表循环订阅，处理器按频道查表取得，编译期固定不了载荷类型——它走
`EventBus.SubscribeDynamic(Event, Action<object>)`（收到该频道任何载荷、无载荷收到 `null`，
不受频道泛型参数的类型锁定保护）。
全仓仅此一处，代码里有注释说明用途与代价。

### 5.5 什么时候不该用 EventBus

同模块内部调用、父子层级生命周期通知、每帧高频数据——前两类用直接引用/Unity 生命周期，
第三类用轮询或直接引用。判断依据：**别把强关系伪装成松耦合**。

### 5.6 为什么不用 DI 容器 / SO 事件通道 / 响应式

行业三类替代方案（对照 MessagePipe / VContainer·Zenject / Unity 官方 SO 事件通道模式研读过），
结论与本项目的先决条件：

- **SO 事件通道不采纳**。本项目战斗数值/回合规则等核心逻辑刻意写成纯 C# 静态类，由无头验证台
  （`external/harness/`，dotnet 直引编译产物 + NUnit）在不启动 Unity 的前提下测试；`ScriptableObject`
  实例化走原生 ECall，脱离 Unity 运行时必抛 `SecurityException`——通信层进 SO 等于核心逻辑的
  无头可测性破产。该模式的核心卖点「设计师免编程接线」在单人 + AI 辅助开发下也不存在协作瓶颈。
- **不为通信引入 DI 容器**。本项目的组合根（Bootstrapper 场景 + `DontDestroyOnLoad` 服务 +
  `XxxApi` 出口 + asmdef 分层）本质是手工 DI；引容器（VContainer/Zenject）的真实收益在**构造注入
  与服务生命周期**，不在事件广播——EventBus 的类型化频道已覆盖 SignalBus 的主要能力（类型化
  载荷 + 广播），单为通信引 DI，全项目构造签名改造成本远大于收益。
  **远期重启条件**：组合根手工接线超过 30 处、服务定位确实失控时，单独立项评估 VContainer
  （届时 MessagePipe 作为其事件层一并评估）。
- **响应式（R3/UniRx 系）不做全局范式**。Rx 适合「随时间流动的值」（血量条、拖拽力度），
  当纯事件广播用是杀鸡用牛刀，且与既有命令式代码并存 = 两套范式。仅特定子系统确有需要时局部引入。

## 6. 关卡与数据资产

**数据不是代码**。关卡、海图、武器、船员、调色板都是资产，改数值不需要重编译。

### 6.1 三层结构

| 层 | 类型 | 位置 | 作用 |
| --- | --- | --- | --- |
| **载荷**（字段真源） | `LevelAssetPayload` / `WorldMapAssetPayload` | `Scripts/PirateCrew/Data/Levels/` | 纯 C#，无头验证台能直接构造与断言 |
| **宿主** | `LevelDefinition` / `WorldMapDefinitionAsset`（SO） | 同上 | Unity 引用入口，持有一个 `data` 载荷 |
| **清单** | `LevelCatalog`（SO） | `Assets/Data/Levels/Resources/LevelCatalog.asset` | 把全部关卡资产带进构建包 |

**为什么载荷与宿主分开**：`ScriptableObject` 的实例化在无头环境必崩（原生 ECall），
把字段真源放在纯 C# 载荷上，"资产内容 == golden JSON"这条判据才能在没有 Unity 的情况下算得出来。

### 6.2 两条读取通道（同一份数据）

| 环境 | 通道 | 去哪读 |
| --- | --- | --- |
| 编辑器 / 播放器 | `Resources.Load<LevelCatalog>` | `Assets/Data/**/*.asset` |
| 无头验证台 / 批处理 | 直接读文件 | `Assets/Data/**/_golden/*.json` |

`_golden/*.json` 是**同一份数据的文本渲染**（由迁移器与资产同一次写出），也是 diff 可读的评审面。
门禁 `LevelAssetTests` 逐字节钉住"清单里的资产 == golden JSON"，所以两条通道不可能分叉。

### 6.3 内容来源解析

`Battle/Levels/LevelSourceResolver` 是**唯一**判定"这一局用哪份关卡数据"的地方，优先级：

```
-artReviewLevel 命令行覆盖 > -worldMap / WorldMapRuntime 待出海图 > 默认关卡
```

判定结果是一个显式的 `LevelSource`。重构前这段判断内嵌在 `BattleController` 的四处
`IsWorldMapActive` 分叉里，战斗根类同时还是内容路由器——现在它不是了。

### 6.4 改数据的正确姿势

- **改数值**：改 `.asset`（Inspector）或改 `_golden/*.json` 后跑迁移器；
  不要改 C# 常量（运行时的硬编码关卡数据已删除，grep 应扫不到）。
- **新增一关**：写 golden JSON（或由迁移器产出）→ 跑 `LevelDataMigrator.MigrateAll` 重写资产与清单
  → 跑 `LevelAssetValidator.ValidateAll` 校验 → 跑内容门禁测试。
- 细节见 [关卡数据资产](关卡数据资产.md)。

## 7. 场景与装配

**内容归 Prefab，场景只留"装配清单"**。四个装配脚本产出的场景（Battle / MainMenu / LevelSelect /
CrewManagement）全部折叠成"一个 Prefab 实例"——场景文件因此只有几十行，内容落在可按模块定位、
可在 Prefab 模式里单独打开、可被别的场景复用的 Prefab 资产里。

| 场景 | 角色 | 内容载体 |
| --- | --- | --- |
| `Bootstrapper` | 入口场景：只放组合根，启动后切到主菜单 | 手摆（2 个对象，有意不折叠） |
| `MainMenu` | UI 流程 | `Prefabs/UI/MainMenuScreen.prefab` |
| `LevelSelect` | UI 流程 | `Prefabs/UI/LevelSelectScreen.prefab` |
| `CrewManagement` | UI 流程 | `Prefabs/UI/CrewManagementScreen.prefab` |
| `Battle` | 战斗场 | `Prefabs/PirateCrew/Battle/BattleRig.prefab`（240 对象 / 载体根下 16 根） |
| `UIShowcase` | 组件展示实机调试场（主菜单按名载入，发行集含它） | 场景本体（相机 + 引导件，页面运行时自建） |
| `Pixelart/*` | 像素化出图与调参场（**开发集**，不进发行包） | 手摆 / 装配器 |

**发行场景集**与**开发场景集**由 `Assets/Editor/Build/BuildScenes.cs` 单一真源管理，
构建只打发行集（校验入口：`BuildScript.ValidateReleaseScenes`）。

### 7.1 装配链：顺序是代码，不是文档

Battle 场景的八步装配收在 `Assets/Editor/BattleScenePipeline.cs` 的 `Steps` 表里：
重建骨架 → 空岛摆入 → 样板场景件烘焙 → 场景资产清单 → 小地图接线 → 运行期查找接线 →
WorldKit 资产表 → **折叠为 Prefab 实例**。顺序是**真实依赖**（每步读写上一步落在场景里的东西），
所以它是一条语句接一条语句，而不是一张要背的表。

```bash
# 只重跑 Battle 子链（改战斗场景时的常用入口）
external/unity-run.sh battle -executeMethod PirateCrew.EditorTools.BattleScenePipeline.BuildFromCommandLine -quit
# 整条资产管线（材质/字体/音频/角色全重建，末尾四个场景一起折叠）
external/unity-run.sh all -executeMethod PirateCrew.EditorTools.ArtGate.BuildAll -quit
```

`ArtGate.BuildAll` 的步骤表只是在这条子链前后各接一段资产重建与 M1/M3 场景，
Battle 的八个步骤**只有一份定义**（在 `BattleScenePipeline.Steps`）。
步骤数与顺序由 `Assets/Tests/Battle/SceneAssemblyContractTests.cs` 冻结——换序会红。

### 7.2 折叠态契约（场景必须保持"纯实例"）

折叠的产物不是一个"随便怎么改都行"的场景，而是一条**可校验的不变量**：

- 场景里 **0 个裸对象**（没有 GameObject 块），**恰好 1 个 Prefab 实例块**，且源指向目标 Prefab；
- 实例 **不带任何"非默认"覆盖**——覆盖会把接线/参数散回场景文件，正是折叠要消灭的状态。

校验入口（只读，漂移时退出码 1）：

```bash
external/unity-run.sh collapse -executeMethod PirateCrew.EditorTools.ScenePrefabCollapse.FromCommandLine \
  -collapseMode verify -quit
```

同一组断言也在 EditMode 测试里跑（`SceneAssemblyContractTests.Scene_IsExactlyOnePurePrefabInstance`），
所以"只跑了装配链的一半""有人往场景里手摆对象"都会当场红，而不是等到某个功能静默失效。

> **Prefab 是生成产物，不是手改对象。** 装配脚本才是真源，重跑链会重新生成 Prefab。
> 要持久化手工调整，改生成器，不改产物——这与折叠前手改场景会被 `NewScene` 洗掉是同一件事，
> 只是现在代价从"199 个对象混在一起"缩到了"一个职责明确的 Prefab"。

### 7.3 显式接线，不靠运行期查找

场景内（折叠后：Prefab 内）的依赖**不通过 `GameObject.Find` 解析**。
`BattleLookupWiring` 是装配链的第 ⑥ 步，把关键引用写进 Prefab 并由测试断言非空——
名字改了、层级挪了，测试当场红，而不是运行时静默失效。

- 写入：装配链第 ⑥ 步（`BattleLookupWiring.Wire`，可单独跑）
- 校验：`-executeMethod PirateCrew.EditorTools.BattleLookupWiring.Verify`（缺接线 → 退出码 1）
- 闸门：`-executeMethod PirateCrew.EditorTools.SceneLookupAudit.AuditFromCommandLine`
  （扫全仓运行期查找，白名单外的命中 → 退出码 1；报告落 `docs/项目/审计/运行期查找清退报告.md`）

### 7.4 改场景前后的等价性仪器

`Assets/Editor/SceneWiringAudit.cs` 把场景的完整层级 + 组件 + 序列化引用导成 TSV，
两次转储可比对出"新增/删除/变化的对象清单"——**每条差异都必须能解释**。
折叠前后比对时用 `-sceneAuditStripRoot <载体根名>` 剥掉载体根，两侧路径即对齐，
于是"新增 0 / 删除 0"成为"没有对象被增删、搬动或改接线"的机械证据。

```bash
external/unity-run.sh audit -executeMethod PirateCrew.EditorTools.SceneWiringAudit.DumpBattleFromCommandLine \
  -sceneAuditOut "<绝对目录>" -sceneAuditStripRoot BattleRig -quit
```

### 8.1 UI：Aseprite 观感复刻三层

游戏 UI 以 **Aseprite dark 主题为唯一观感权威**（参考库整仓在 `external/aseprite-ref`：
theme.xml 的 parts/styles/colors 三表 + sheet.png 直切件 + `data/widgets/*.xml` 对话框声明 +
`data/strings/en.ini` 文案）。复刻分三层，**生产界面与调试面板同一套**：

| 层 | 落点 | 说明 |
| --- | --- | --- |
| 控件层 | `Assets/Scripts/UI/Stick/Controls/` | 每件一类 + 代码工厂（SketchButton / SketchButtonSet / SketchButtonSetIcon / SketchPanel / SliderValueLabel…）。像素纪律（顶点像素对齐、字号=字体原生档、件禁乘色、整格坐标）必须在代码强制，所以控件不走 prefab 承载 |
| 装载层 | `Assets/Scripts/UI/Debug/AseDialogLoader.cs` | 解析 `Resources/AseWidgets/*.xml`（自 aseprite `data/widgets` **原封拷贝**，同步工具 `Editor/AseWidgetAssetSync.cs`），按 box.cpp 盒模型语义子集（vbox/hbox/grid/separator/entry/expr/buttonset/check/combobox/button、expansive/homogeneous）实例化控件层；`@.key` 文案查 en.ini。布局数字来自声明文件本身 |
| 面板层 | `Assets/Scripts/UI/Debug/`（DebugMenuHost/WidgetGalleryPanel/AseMenuKit…） | 主菜单「调试场景」→ 可拖动启动器开各面板；对话框只写布局与 cmd 层接线（如 new_sprite 的 advanced 勾选联动），不再手抄数字 |

定案史、装载器覆盖表（未实现语义清单）与判据在
[Aseprite观感对齐](../../项目/交接/归档/Aseprite观感对齐.md) §三之五。

**画布栈与字阶（口径）**：

- **画布 = 恒定像素密度**（红警2 式）：三画布工厂 + `SceneLoader` overlay 全部走
  `ConstantPixelSize × PixelSkin.Unit`——1 画布单位恒 = Unit 屏幕像素，画布逻辑尺寸随分辨率
  整数倍生长（1440p → 1280×720），任何分辨率都无分数缩放。**比例换档单点 = `PixelSkin.Unit`**
  （现 = 2），画布工厂 referenceResolution 按 `1920/Unit × 1080/Unit` 自动跟随；设置面板比例
  下拉就接这一个真源。
- **字体 = 像素字体原生档四档**：16 = 正格点黑16（`ZhengGeDianHei16`），12/10/8 = 缝合像素
  （`FusionPixel12/10/8-zh_hans`，缺字回退链已烘进资产）。**没有的档不硬凑、绝不放大**
  （12px 烘 24 = 翻倍，已否决）；**禁伪粗**（TMP 合成加粗在位图上 = 重影乱码，已全局禁用）；
  位图口径 = 原生档 samplingPointSize + RASTER_HINTED + atlasPadding 0 + 图集 Point +
  `TextMeshPro/Bitmap` 材质。字号是独立体系，不锚定艺术像素。选型样张与许可见
  [ui-font/README](../../images/ui-font/README.md)，行业先例见
  [位图字体像素对齐与行业档案](../渲染/调研/位图字体像素对齐与行业档案.md)。
- **布局数字一律取 `UI/Skin/AseLayout` 令牌层**：theme.xml `<styles>`/`<dimensions>` 的间距
  语法全表登记，`Px()` 是唯一换算出口（theme 数字是设计格，直接当画布像素用 = 比例减半——
  观感挤的根源）；接屏时不手写画布像素字面量。

### 8.2 场景资产：三层分离

场景/环境资产走三层分离，**几何生成全部退出运行时**：

```
资产层 Assets/Art/Models/SceneKit/（烘焙产物 + 手作资产）
         Flagship.fbx / Dock.fbx / 岛体 / 云场 prefab / 陈设件 …
            ↑ 编辑期烘焙器（C#，SceneArtBake） ↑ 手作/精修（Blender → FBX）
数据层 WorldMapCatalog / 关卡载荷——只记「件 id + 摆位 + 种子」，零几何代码
运行时 只做实例化组装 + 真动态系统（海面圆盘 / 水模拟 / 风摆 / 氛围）
```

- **单一管线，两类来源同目录同清单**：C# 程序化生成器已改岗为编辑器烘焙器
  （`Scripts/PirateCrew/SceneArtBake/`，Editor-only）——配方+种子 → 合并网格 → prefab/FBX
  一键落盘；Blender 职责收窄为手作主件与精修回导（`tools/blender/scene/`，FBX 入 SceneKit）。
  manifest 登记上游：程序化件记配方+种子，手作件记 blend 文件路径。
  **船类资产一律走 Blender 手作管线**（`Editor/SceneArtBaker.cs`，产物如 `SceneKit/Flagship.fbx`），
  不做程序化船体。
- **为什么这样分**：确定性生成（固定配方+种子=固定输出）在运行时重算是纯浪费；真动态的只有
  海面圆盘（随相机/图幅）、`WaterSimulationDriver` 高度场、风摆/氛围——这些留在运行时是本分。
- **边界不变式**：
  1. **角色不烘焙**——船员是运行时装配+动画的胶囊体（AGENTS.md 铁律：角色模型不许改），
     本节只覆盖场景/环境资产。
  2. **真动态系统不烘焙**——输出依赖运行时状态，烘焙无意义。既成豁免：
     `Ambient/AmbientMeshFactory.cs`（海鸥/螃蟹/鱼）与运行时 `SceneArt/MeshBuffers.cs` 仍在造网格。
  3. **多样性来自「更多预制变体」而非运行时随机**——需要第 N 种船/岛时加配方（或手作）出第 N 件，
     运行时零成本换装。
  4. **数据层格式不变**——`WorldMapDefinition` 的 id/摆位/氛围档契约、存档与事件契约不受烘焙影响（§6）。
  5. **流式加载不做**——单场景战斗规模用不上 asset bundle 流式，prefab 直引即可。
- **确定性判据**：烘焙器带「同配方两次烘焙逐顶点一致」断言（EditMode），锁资产漂移。
