## 1. 现状盘点（本项目）

**EventBus 已经是强类型泛型总线，不是"字符串总线"**（`Core/EventBus.cs`）：

| 能力 | 出处 | 说明 |
| --- | --- | --- |
| 载荷编译期受检 | `EventBus.cs:14-24` | 泛型 `Publish<T>/Subscribe<T>`，订阅/发布载荷不匹配 = 编译错误 CS1503 |
| 运行期契约对拍 | `EventBus.cs:368-378` | `EventCatalog` 登记键→期望类型，不符写入 `ContractViolations` 并告警 |
| 热路径零分配 | `EventBus.cs:30-32` | 频道内缓存快照数组，订阅不变时 `Publish` 不重建（有分配断言测试） |
| 无载荷哨兵 | `EventBus.cs:53-55` | `NoPayload` 结构，不拿 `object` 混过类型系统 |
| 防泄漏收口 | `EventBus.cs:39-40`、`345-349` | 静态残留由唯一入口 `GameEntryPoint.ResetForNewSession()` 清理 |
| 逃生口受控 | `EventBus.cs:167-173` | `SubscribeDynamic` 全仓唯一使用处是 `AudioService`（契约文档 §0） |

**已知短板（诚实盘点）**：

1. **事件键仍是裸 `string`**——键拼错、键与载荷张冠李戴依旧编译不过不了关，
   只能靠「先登记后使用」纪律 + `EventCatalogTests` 锁登记完整性兜底（契约文档 `:14-19`）。
2. 静态类 = 全局状态，测试隔离依赖 `ResetForNewSession` 纪律。
3. 跨模块调用的另一半（服务定位）靠 `Bootstrapper` 场景摆服务 + 各模块 `XxxApi.cs` 出口，
   无构造注入——依赖方向靠 asmdef 约束（架构总览）。

**本项目特有约束（评估任何方案的先决条件）**：
战斗数值/回合规则等核心逻辑**刻意写成纯 C# 静态类**，由无头验证台
（`external/harness/`，dotnet 直引编译产物 + NUnit）在不启动 Unity 的前提下测试。
`GameObject`/`MonoBehaviour`/`ScriptableObject` 实例化走原生 ECall，脱离 Unity 运行时必抛
`SecurityException`（`external/harness/README.md`）。
**→ 通信层若引入 ScriptableObject，核心逻辑的可测性立即破产。**

## 2. 参照库研读

### 2.1 MessagePipe（Cysharp）——DI 优先的消息管道

- 定位：高性能内存/分布式 Pub/Sub，含 mediator、EventAggregator 替代；自述比 C# event 快、每次 publish 零分配（[README](https://github.com/Cysharp/MessagePipe)）。
- 关键设计：**publisher/subscriber 由 DI 容器管理**，"all subscriptions are unsubscribed when the scope is disposed, which prevents subscription leaks"；另配 **roslyn analyzer** 与 `MessagePipeDiagnosticsInfo` 双保险防订阅泄漏。
- 依赖前提：构建在 `Microsoft.Extensions.DependencyInjection` 之上（Unity 侧接 VContainer / Zenject / 内置 TinyDI）。

**对照本项目**：防泄漏模型 = 生命周期随 DI scope 走，前提是先有容器；本项目没有容器，等效物是「唯一入口 ResetForNewSession」——目标相同（订阅不悬挂），实现路线不同。要完整吃到 MessagePipe 需先引 DI。

### 2.2 R3（Cysharp）——响应式（UniRx 后继）

- 定位：现代 C# 重写的 Rx，强调帧时间算子（游戏引擎刚需）、订阅列表防泄漏、`OnError` 不终止管道（[README](https://github.com/Cysharp/R3)）。
- **对照本项目**：Rx 是一整套范式，适合"随时间流动的值"（血量条、拖拽力度）；拿来当纯事件广播用是杀鸡用牛刀，且与既有命令式代码并存会造成两套范式。仅特定子系统（如音频/环境随机插值）局部引入才合理。

### 2.3 VContainer / Zenject —— DI 容器

- VContainer：Resolve 比 Zenject 快 5-10 倍、零分配，`LifetimeScope` 父子层级天然映射"应用级服务 → 场景级服务"，EntryPoint 可为纯 C# 类（[README](https://github.com/hadashiA/VContainer)）。
- Zenject：最老牌，SignalBus 提供类型化信号广播（[README](https://github.com/modesttree/Zenject)）。
- **对照本项目**：本项目的组合根（Bootstrapper 场景 + `DontDestroyOnLoad` 服务 + `XxxApi` 出口 + asmdef 分层）本质是"手工 DI"。引容器的真实收益在**构造注入与服务生命周期**，**不在事件广播本身**——事件这块 EventBus 已覆盖 Zenject SignalBus 的主要能力（类型化载荷 + 广播）。单为通信引 DI，成本（全项目构造签名改造 + 组合根重建）远大于收益。

### 2.4 SO 事件通道（Unity 官方模式）——designer 驱动

- 模式：事件本身做成 `ScriptableObject` 资产（channel），发布/订阅双方只认识资产、互不相识；设计师可在 Inspector 接线搭游戏流（[Unity 官方 how-to](https://unity.com/how-to/scriptableobjects-event-channels-game-code)、[e-book](https://resources.unity.com/games/create-modular-game-architecture-with-scriptable-objects-ebook)、官方示例 [PaddleGameSO](https://github.com/UnityTechnologies/PaddleGameSO)、[Hipple GDC 演讲](https://www.youtube.com/watch?v=raQ3iHhE_Kk)）。
- **对照本项目：根本性冲突 ×2**——
  ① 通信层进 SO = 核心逻辑离开纯 C# 域，无头验证台测不了（§1 约束）；
  ② 该模式的核心卖点是"设计师无编程接线"，本项目是单人 + AI 辅助开发，不存在该协作瓶颈。
- 社区对比结论同向：SO 事件适合 designer 驱动的 gameplay 流，代码驱动的系统通信适合事件总线——两者是不同工作流而非优劣关系（[wallstop 对照文](https://wallstop.github.io/unity-tips/best-practices/10-event-systems/)）。

## 3. 对照矩阵

| 方案 | 键/载荷类型安全 | 泄漏防护 | 无头可测 | 接入成本 | 设计师接线 |
| --- | --- | --- | --- | --- | --- |
| **现状 EventBus** | 载荷编译期 ✓；键 string 运行期对拍 | 唯一入口清静态 + 契约告警 | ✓（纯 C#） | —（已有） | ✗ |
| MessagePipe | 类型即键，编译期 ✓ | scope dispose + analyzer + 诊断 | △ 需 DI 容器可无头 | 高（先引 DI） | ✗ |
| R3 | 类型即键 ✓ | 订阅列表/Disposable | △ 纯 C# 可测，但范式迁移大 | 高 | ✗ |
| VContainer/Zenject 信号 | 编译期 ✓ | scope dispose | △ 容器本身可无头，改造量大 | 高（全项目） | ✗ |
| SO 事件通道 | 编译期（资产引用）✓ | 随场景/资产生命周期 | ✗ SO 实例化必抛 | 中 | ✓（独有） |

## 4. 建议

- **建议 A（已裁决采纳，2026-09-23）**：保留 EventBus，把「事件键」从裸 `string` 升级为
  **类型化频道**——每个事件一个 `static readonly Event<T>` 实例（键即类型），
  `CrewDamaged` 拼错/张冠李戴从运行期告警升级为**编译错误**；`EventCatalog` 从"运行期真源"
  退化为纯文档（或保留做测试断言）。迁移节奏按 D-2 裁决：**全量一次到位**。
  预期改动：`EventBus` 增类型化频道内核（快照/零分配机制原样保留）+ 全部 `XxxEvents.cs` 与调用点一次改完。
- **建议 B（已裁决关闭，记远期）**：不为通信引入 DI。若未来服务定位复杂度确实失控（组合根手工接线 > 30 处），
  单独立项评估 VContainer（性能与 scoping 设计优于 Zenject），MessagePipe 届时作为其事件层一并评估。
- **建议 C（已裁决不采纳）**：SO 事件通道**不采纳**进模块通信层；若未来出现编辑器工具链的资产间通知需求，再局部使用。
