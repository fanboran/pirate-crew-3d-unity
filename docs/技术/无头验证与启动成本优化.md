# 无头验证与 Unity 启动成本优化

> **这份文档解决什么问题**：无头验证（跑测试 / 验工程 / 出图）单次要花 2~3 分钟，
> 而其中真正跑用例的时间只有十几秒——**成本几乎全在 Unity 冷启动 + 资源导入 + 编译**。
> 本文是「怎么把启动次数降下来」的单一事实源：成本结构 / 官方路线 / 行业做法 / 分工口径 / 落地方案。
>
> 配套：运行器 `tools/headless/run.sh`（档位定义与缓存），无头验证台 `external/harness/README.md`，
> CI 与出包见 [构建与发布手册](../项目/构建与发布手册.md)。

## 1. 成本结构（实测）

| 档 | 用例数 | **测试本体耗时** | 单次墙钟 |
| --- | --- | --- | --- |
| `harness`（纯 C#，不开 Unity） | ~1076 | 秒级 | **秒级** |
| `test EditMode` | 1300 | **15.9 s** | ≈2.5–3 min |
| `test PlayMode` | 8 | **11.6 s** | ≈2.5–3 min |
| `open`（整工程可打开） | — | — | ≈2–3 min |

单条用例约 12 ms；**用例本身几乎免费，约 93% 的墙钟在 Unity 冷启动 + 导入 + 编译**
（实测：从 `run.sh` 启动到测试开始 ≈2 分 26 秒）。

**直接推论**：想提速，要减少的是「**Unity 启动次数**」，不是「用例数量」——
砍掉一半用例只省约 8 秒；少启动一次省约 2.5 分钟。**不要以"少测试"为优化手段。**

### 1.1 一次冷启动的实测分解

从一次 `test PlayMode` 日志里读到的自身计时：

| 环节 | 实测 | 说明 |
| --- | --- | --- |
| `CompileScripts` | **23.1 s** | **全量**重编 574 个 bee 步骤（触发原因：`Assetdatabase observed changes in script compilation related files`） |
| `Domain Reload Profiling` | **11.8 s** | 其中 `LoadAllAssembliesAndSetupDomain` 3.2 s、`AnalyzeDomain` 3.2 s |
| 其余（引擎初始化 / 包解析 / 资源导入 / 场景装载） | ≈2 分钟 | 未逐项分解 |

两点值得注意：

- **脚本重编这块是"每次都付"的**：只要工作区有改动（并行会话常态），Unity 就判定重编，
  于是每次冷启动都吃这 23 s + 12 s。**常驻 Editor 的增量重编（或纯 C# 走 `harness`）直接绕开这 ≈35 s。**
- 日志里另有一次 `CompileScripts: 2.837ms`——说明**无改动时编译几乎为零**，
  这 23 s 完全是"每次拉起新进程 + 树有改动"造成的，不是编译本身慢。

未分解的大头（≈2 分钟）落在引擎初始化 / 包解析 / 资源导入，**这才是 Library 热缓存要治的部分**。

## 2. 官方路线：Unity CLI（MCP 已废弃）

Unity 官方当前推荐的编辑器自动化入口是 **Unity CLI**（命令 `unity`，实验期 1.0.0-beta），
其中与「减少启动」直接相关的四条：

| 命令 | 作用 |
| --- | --- |
| `unity test` | **一次跑完 Edit Mode + Play Mode 测试**并产出 NUnit 报告 |
| `unity recompile` | 重编**正在运行的** Editor 的脚本并列出编译错（退出码 0 成功 / 6 编译错 / 7 无 Editor 应答） |
| `unity open` / `close` | 管理**常驻 Editor**实例，后续命令打给它 |
| `unity test --affected`、`unity watch test` | 只跑**受影响的**用例；`watch` 在项目文件变化时按去抖自动重跑 |

**Unity MCP Server 已被官方标记废弃**，其配置页顶部明示改用 Unity CLI
（理由：更快的迭代、更好的稳定性、能同时面向 runtime 与 Editor）。
→ 因此「驱动开着的编辑器」这条路的**目标实现应从 MCP 改为 Unity CLI**。

**未验证的前提**：Unity CLI 是实验版、且面向较新编辑器；本工程是 **Unity 2022.3.62f1**，
能否安装与使用**必须先验证**（见 §5 第 2 步），不得假设可用。

## 3. 行业做法（CI 侧）

事实标准是 GameCI 的 **Library 缓存**——Unity 的 `Library/` 是构建速度最大单一变量：

| 档 | 状态 | 恢复代价 |
| --- | --- | --- |
| **HOT** | 同机器 / 同分支 / 同 profile | 毫秒（**同卷 move**，O(1)） |
| **WARM** | 换机器或换分支，同 profile | 秒（move + 局部重导） |
| **COLD** | 无可用缓存 | 分钟～小时（全量重导） |

配套要点：

- **别删 `Library`**；同卷用 **move 而非 copy**（50 GB 也是毫秒级）。
- 还原后要**校验不是"空壳 Library"**（`Library/ArtifactDB` 或 `assetDatabase.info` 零字节 = 冷启动），
  否则"看着命中、实则全量重导"。
- **跨机器还原要修 `Library/Bee/*.dag`** 里的绝对路径——路径不匹配会让增量编译失效或静默出错。
- CI 上 **Edit Mode / Play Mode 拆成并行 job**（墙钟取 max 而非相加）。

## 4. 我们这一侧的账

属**操作面**（可改）：

1. 一次验收可能启动 3 次 Unity（`open` + `test EditMode` + `test PlayMode`）——
   其中 `open` 在日常是冗余的（测试跑通即已证明工程可开），只在改 manifest / Packages /
   ProjectSettings / 程序集定义 / .meta 结构后才需要。
2. 没有常驻 Editor：工程里已有 `McpBridgeKick` 垫片，但"驱动开着的编辑器"没落地；
   且原先选的 MCP 路线已被官方废弃（§2）。
3. **worktree 公约要求每个 worktree 各自冷导 Library**（分钟级）——这是有意的隔离代价，
   但并行开发时就是反复冷启动。

不属**操作面**（固有）：

4. Unity 无头冷启动本身重；而"常驻实例 + 增量 + 受影响测试"这套能力，
   官方直到最近才以 Unity CLI 形式提供。

## 5. 方案

### 已完成（口径与运行器）

- `tools/headless/run.sh`：`open` / `test` 两档共用**结果缓存**——key = `HEAD + 工作区状态哈希`，
  30 分钟内同状态且**上次全绿**才回放；**失败永不回放**（宁可重跑）。
- `test` 档接受**过滤器**（第 2 参数 → Unity `-testFilter`，口径是**测试名子串**，
  如 `BattleSceneWiringTests`），可只跑一块；缓存按「平台 + 过滤器」分别记，不同子集不互相回放。
- `PC3D_NO_CACHE=1` 强制重跑；`$TEMP` 缺失时兜底（避免 WSL/Git Bash 下直接退出）。
- `harness` 的 `Battle` 域补齐 `PirateCrew/CharCamDebug`（该域是显式列目录，新增目录要同步登记）。

### 下一步（按序）

1. **口径固化**：按改动面选最小档（见 §6），一次验收不默认三档全跑。
2. **验证 Unity CLI 对 2022.3 的可用性**：装一次 → `unity --help` → 拿本工程跑 `unity test`；
   不可用则退回「常驻 Editor + 自建命令桥」的自研路线。
3. **分解剩余的大头**：编译（23 s）与域重载（12 s）已量化（§1.1），余下 ≈2 分钟的
   引擎初始化 / 包解析 / 资源导入尚未逐项分解——分解后再决定要不要做 Library 预热副本
   （worktree 复用 / 同卷 move 而非 copy）。

### 远期

4. **单入口编排**：一次启动串跑多件装配（字体重建 → Battle 管线 → 菜单场景）。
5. **CI**：GameCI 风格流水线（Library 缓存 + Edit/Play 并行 job），见 [构建与发布手册](../项目/构建与发布手册.md)。

## 6. 口径：按改动面选档

| 改了什么 | 跑什么 | 理由 |
| --- | --- | --- |
| 纯 C# 逻辑（数值 / 规则 / 纯函数） | `harness <域>` | 秒级、不开 Unity、不占 Library 锁，可与其他会话并行 |
| UI / 场景 / 资产内容 | `test EditMode` | Unity 侧权威环境；不必跑 PlayMode |
| 物理 / 播放循环 / MonoBehaviour 生命周期 | `test PlayMode` | 只有它能覆盖 |
| manifest / Packages / ProjectSettings / 程序集定义 / .meta 结构 | 追加 `open` | 只有这类改动会影响"工程能否打开" |
| 收口（准备提交/合并） | `harness All` + 受影响平台的 `test` | 全量体检，但仍**不默认三档全跑** |

**同 HEAD + 同工作区重复验证**：直接重跑命令即可，命中缓存会打印提示并跳过启动；
要强制真跑加 `PC3D_NO_CACHE=1`。
