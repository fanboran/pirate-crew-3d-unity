# 无头验证与 Unity 启动成本优化

> **这份文档解决什么问题**：无头验证（跑测试 / 验工程 / 出图）单次要花 2~3 分钟，
> 而其中真正跑用例的时间只有十几秒——**成本几乎全在 Unity 冷启动 + 资源导入 + 编译**。
> 本文是「怎么把启动次数降下来」的单一事实源：成本结构 / 官方路线 / 行业做法 / 分工口径 / 落地方案。
>
> 配套：运行器 `tools/headless/run.sh`（档位定义、结果缓存、`unlock` 清锁 / `chain` 编排），
> 无头验证台 `external/harness/README.md`，CI 与出包见 [构建与发布手册](../项目/构建与发布手册.md)。

## 1. 成本结构（实测）

| 档 | 用例数 | **测试本体耗时** | 单次墙钟 |
| --- | --- | --- | --- |
| `harness`（纯 C#，不开 Unity） | ~1076 | 秒级 | **秒级** |
| `test EditMode` | 1300 | **15.9 s** | ≈2.5–3 min |
| `test PlayMode` | 8 | **11.6 s** | ≈2.5–3 min |
| `open`（整工程可打开） | — | — | ≈2–3 min |

单条用例约 12 ms；**用例本身几乎免费，约 93% 的墙钟在 Unity 冷启动 + 导入 + 编译**
（实测：从 `run.sh` 启动到测试开始 ≈2 分 26 秒）。

**直接推论**：想提速，要减少的是「**Unity 启动次数**」，不是「用例数量」——
砍掉一半用例只省约 8 秒；少启动一次省约 2.5 分钟。**不要以"少测试"为优化手段。**

### 1.1 一次冷启动的实测分解（已逐项对账）

主样本：`test PlayMode`，工作区有改动（并行会话常态），墙钟 159.1 s；warm 对照：同机同 Library 无脚本改动，
EditMode 墙钟 38.5 s。出处：`$TEMP/pc3d-headless-test-*.log` 内 Unity 自身计时行
（临时目录日志会滚动，复查按「计时行原文」grep）：

| 环节 | 冷（有改动） | warm（无改动） | 计时行原文（grep 锚点） |
| --- | --- | --- | --- |
| **InitialRefreshV2 资产库全量刷新** | **77.6 s (52.7%)** | 10.6 s | `Total: N seconds - InitialRefreshV2` |
| ├ CompileScripts 全量重编 | 23.1 s | 1.2 s | `CompileScripts: NNNN ms` |
| ├ 编译后域重载 | 19.4 s | —（未单列） | `domain reload time=NNNNN ms` |
| └ 资产库 native 刷新（非编译非重载） | 34.9 s | —（未单列） | `Asset DB Process Time: native=NNNNN ms` |
| Licensing 客户端连接 | 12.3 s | 2.8 s | `WinEditorMain.Licensing … Total.` |
| 首次域重载（装配加载） | 12.1 s | 0.8 s | `Domain Reload Profiling: NNNN ms` |
| run.sh 进程外壳（spawn/落日志） | ≈12 s | ≈12 s | 日志文件名时间戳 → mtime 差 |
| 引擎图形初始化 | 4.9 s | 0.1 s | `-nographics`（Null 设备）也照付 |
| 包解析 | ≈4.3 s | 0.6 s | `Package Manager` 段各计时行 |
| 引擎核心（NoGraphics/GI/默认资源） | ≈0.4 s | ≈0.4 s | |
| **测试本体** | 11.6 s | 15.9 s | test-results XML `duration` |
| 对账 | `[Project] Loading completed` 129.4 s | — | `Loading completed` |

三个直接推论：

- **冷热差 ≈120 s 几乎全部由「工作区有改动 → 全量重编 + 双重载」贡献**
  （同一 InitialRefreshV2 环节 77.6 s → 10.6 s；导入了了：全量刷 706 项里 688 项走本地缓存）。
  日志里另有 `CompileScripts: 2.837ms` 的实例，证明编译本身不慢——钱全花在"每个新进程都要重付一遍"。
  注意旧口径「域重载 11.8 s」只是首域那一次：冷启动实际有 **≥2 次大 reload**（首域 12.1 s + 编译后 19.4 s）。
- **Library 预热副本对本机日常冷启动收益 ≈ 0，不做**：大头是刷新的索引/依赖重算而非导入本体；
  它只对新 worktree 首次冷导有救（实测全量刷 ≈102 s）——那一条走 GameCI 式 Library move（§3）即可。
- **每进程固定税 ≈24 s**（Licensing 12.3 + 外壳 12）：无参数可救，只能靠"少启动"摊薄。
  包解析 / 图形初始化 / 引擎核心都是小头，不值得单独立项。

## 2. 官方路线：Unity CLI（MCP 已废弃）

Unity 官方当前推荐的编辑器自动化入口是 **Unity CLI**（命令 `unity`，实验期 1.0.0-beta），
其中与「减少启动」直接相关的四条：

| 命令 | 作用 |
| --- | --- |
| `unity test` | **一次跑完 Edit Mode + Play Mode 测试**并产出 NUnit 报告 |
| `unity recompile` | 重编**正在运行的** Editor 的脚本并列出编译错（退出码 0 成功 / 6 编译错 / 7 无 Editor 应答） |
| `unity open` / `close` | 管理**常驻 Editor**实例，后续命令打给它 |
| `unity test --affected`、`unity watch test` | 只跑**受影响的**用例；`watch` 在项目文件变化时按去抖自动重跑 |

**Unity MCP Server 已被官方标记废弃**，其配置页顶部明示改用 Unity CLI
（理由：更快的迭代、更好的稳定性、能同时面向 runtime 与 Editor）。
→ 因此「驱动开着的编辑器」这条路的**目标实现应从 MCP 改为 Unity CLI**。

**已验证（本机装 CLI 1.0.0-beta.11 实测）——裁决：对本工程的「控制面」不可用**：

- CLI 本体能装能用、认得本机编辑器：官方 Windows 安装器（CDN
  `public-cdn.cloud.unity3d.com/hub/prod/cli/`，SHA256 与清单核对），`unity doctor` 列出
  `2022.3.62f1c1`（`F:/Unity/2022.3.62f1`）；`editors list / install / launch` 这类**编辑器安装管理**可用。
- 但 `unity test` / `open` / `close` / `recompile` / `watch` / `command` 全部依赖 **`com.unity.pipeline`**
  包（官方口径："To use the Unity CLI to control the Unity Editor, install and set up the Unity
  Pipeline package."），而该包注册表全部已发版本（0.2.0-exp.2 ~ 0.8.0-exp.1）的依赖声明均为
  **`unity: 6000.0`**，前置条件明写 "Install the Unity Editor version 6.0 or later"——
  **2022.3.62f1 装不进去**。CLI 对 2022 线编辑器只承诺"能被启动"，不承诺控制。
- → 「驱动开着的编辑器」退回**自研路线：常驻 Editor + 自建命令桥**（`McpBridgeKick` 垫片为起点，§5）；
  日后若升 Unity 6 可重启 CLI 路线（CLI 二进制留装机 `~/.unity-cli/`）。

## 3. 行业做法（CI 侧）

事实标准是 GameCI 的 **Library 缓存**——Unity 的 `Library/` 是构建速度最大单一变量：

| 档 | 状态 | 恢复代价 |
| --- | --- | --- |
| **HOT** | 同机器 / 同分支 / 同 profile | 毫秒（**同卷 move**，O(1)） |
| **WARM** | 换机器或换分支，同 profile | 秒（move + 局部重导） |
| **COLD** | 无可用缓存 | 分钟～小时（全量重导） |

配套要点：

- **别删 `Library`**；同卷用 **move 而非 copy**（50 GB 也是毫秒级）。
- 还原后要**校验不是"空壳 Library"**（`Library/ArtifactDB` 或 `assetDatabase.info` 零字节 = 冷启动），
  否则"看着命中、实则全量重导"。
- **跨机器还原要修 `Library/Bee/*.dag`** 里的绝对路径——路径不匹配会让增量编译失效或静默出错。
- CI 上 **Edit Mode / Play Mode 拆成并行 job**（墙钟取 max 而非相加）。

## 4. 我们这一侧的账

属**操作面**（可改）：

1. 一次验收可能启动 3 次 Unity（`open` + `test EditMode` + `test PlayMode`）——
   其中 `open` 在日常是冗余的（测试跑通即已证明工程可开），只在改 manifest / Packages /
   ProjectSettings / 程序集定义 / .meta 结构后才需要。
2. 没有常驻 Editor：工程里已有 `McpBridgeKick` 垫片，但"驱动开着的编辑器"没落地；
   且原先选的 MCP 路线已被官方废弃（§2）。
3. **worktree 公约要求每个 worktree 各自冷导 Library**（分钟级）——这是有意的隔离代价，
   但并行开发时就是反复冷启动。

不属**操作面**（固有）：

4. Unity 无头冷启动本身重；而"常驻实例 + 增量 + 受影响测试"这套能力，
   官方直到最近才以 Unity CLI 形式提供。

## 5. 方案

### 已完成（口径与运行器）

- `tools/headless/run.sh`：`open` / `test` 两档共用**结果缓存**——key = `HEAD + 工作区状态哈希`，
  30 分钟内同状态且**上次全绿**才回放；**失败永不回放**（宁可重跑）。
- `test` 档接受**过滤器**（第 2 参数 → Unity `-testFilter`，口径是**测试名子串**，
  如 `BattleSceneWiringTests`），可只跑一块；缓存按「平台 + 过滤器」分别记，不同子集不互相回放。
- `PC3D_NO_CACHE=1` 强制重跑；`$TEMP` 缺失时兜底（避免 WSL/Git Bash 下直接退出）。
- `harness` 的 `Battle` 域补齐 `PirateCrew/CharCamDebug`（该域是显式列目录，新增目录要同步登记）。
- **`chain` 单入口编排档**：`bash tools/headless/run.sh chain 类名.方法名[;类名.方法名…]`——
  一次 Unity 启动按序串跑多件 Editor 装配，把「每件一次 ≈2.5 分钟冷启动」合成一次。
  Unity 侧反射编排器 `Assets/Editor/HeadlessChain.cs`（`PirateCrew.EditorTools.HeadlessChain`）：
  全部步骤**开跑前先解析校验**（要求 public static、无参或全默认参，坏名字整体拒绝）、
  逐步计时打点、任一步失败即摘异常并以非零码收口；run.sh 不传 `-quit`（退出码由编排器带出）。
  **不做缓存**——装配会改场景/资产，结果不可回放，每次真跑。
- **`unlock` 清锁档**：僵尸 `Temp/UnityLockfile` 兜底——无锁退出 0；有锁且无 Unity.exe 进程则
  **只删锁文件本身**退出 0；有锁且 Unity.exe 在跑则拒绝退出 3（与 `guard_unity` 同口径）。
- **冷启动大头已逐项分解**（§1.1）：最大剩余 = 「工作区有改动」触发的全量重编 + 双重载 + 刷新牵连；
  每进程固定税 ≈24 s（Licensing + 外壳）；**Library 预热副本不做**（日常收益 ≈ 0）。
- **Unity CLI 已裁决**（§2）：控制面依赖 `com.unity.pipeline`（最低 Unity 6000.0），2022.3 不可用。

### 下一步（按序）

1. **口径固化**：按改动面选最小档（见 §6），一次验收不默认三档全跑。
2. **常驻 Editor + 自建命令桥**（CLI 裁决不可用后「消灭冷启动」的唯一路线）：
   以 `McpBridgeKick` stdio 垫片为起点，把「驱动开着的编辑器执行菜单/装配/测试」落成可用桥，
   让增量编译 + 免冷启动覆盖日常迭代（省的就是 §1.1 里每进程 ≈55 s 重编双重载 + ≈24 s 固定税）。
3. **`chain` 接真实装配序列**：通路已过实机冒烟（`Noop` 靶子），把「字体重建 → Battle 管线 →
   菜单场景」等真实序列接进来，单次启动跑完。

### 远期

4. **CI**：GameCI 风格流水线（Library 缓存 + Edit/Play 并行 job），见 [构建与发布手册](../项目/构建与发布手册.md)。

## 6. 口径：按改动面选档

| 改了什么 | 跑什么 | 理由 |
| --- | --- | --- |
| 纯 C# 逻辑（数值 / 规则 / 纯函数） | `harness <域>` | 秒级、不开 Unity、不占 Library 锁，可与其他会话并行 |
| UI / 场景 / 资产内容 | `test EditMode` | Unity 侧权威环境；不必跑 PlayMode |
| 物理 / 播放循环 / MonoBehaviour 生命周期 | `test PlayMode` | 只有它能覆盖 |
| manifest / Packages / ProjectSettings / 程序集定义 / .meta 结构 | 追加 `open` | 只有这类改动会影响"工程能否打开" |
| 收口（准备提交/合并） | `harness All` + 受影响平台的 `test` | 全量体检，但仍**不默认三档全跑** |

**同 HEAD + 同工作区重复验证**：直接重跑命令即可，命中缓存会打印提示并跳过启动；
要强制真跑加 `PC3D_NO_CACHE=1`。
