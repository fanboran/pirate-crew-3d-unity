# 构建与发布手册

> **这份文档回答什么**：怎么出一个包、版本号从哪来、产物长什么样、构建报告怎么看、
> CI 怎么配、上架前工程侧还要检查什么。
> **不回答什么**：代码规范与模块边界（读 [开发者指南.md](开发者指南.md)）、
> 本次重构的范围与验收契约（读 [工业级重构总纲.md](工业级重构总纲.md)）。
>
> **出处约定**：本文的命令与参数都对应到具体文件与行号口径；
> 凡是**未在本机验证过**的结论都显式标了「未验证」，不假装通过。

## 1. 出包（两条命令，同一套逻辑）

出包脚本在 `pirate-crew/Assets/Editor/Build/`，命名空间 `PirateCrew.EditorTools.BuildSystem`。
菜单与命令行调的是同一套 `BuildScript.Execute`，不存在两条会各自漂移的路径。

### 1.1 编辑器里一键出包

```
菜单：PirateCrew → Build → 一键出包 Windows64（Release）
```

等价于默认参数：win64 / 发行档 / 5 场景发行集 / 版本号取 `BuildVersion.Current` / 输出到
`<仓库根>/external/build/<版本>/win64`。构建结束后产物路径、体积与耗时都打在 Console，
也写进输出目录里的构建报告（§5）；编辑器里没有"打开输出目录"这类动作，路径在报告里可复制。

### 1.2 命令行出包（CI 与本地发布用这条）

```bash
"F:/Unity/2022.3.62f1c1/Editor/Unity.exe" -batchmode -nographics -quit \
  -projectPath "F:/VSCode/pirate-crew-3d-unity/pirate-crew" \
  -executeMethod PirateCrew.EditorTools.BuildSystem.BuildScript.BuildFromCommandLineArgs \
  -logFile - \
  -buildFlavor release \
  -buildCommit "$(git rev-parse HEAD)" \
  -buildBranch "$(git rev-parse --abbrev-ref HEAD)"
```

**这些参数不是 Unity 的，是本工程自己解析的**：Unity 会把不认识的 `-xxx` 原样留在
`Environment.GetCommandLineArgs()` 里，`BuildConfig.Parse` 只挑自己认识的（其余静默忽略），
所以不会与 Unity 自带参数冲突。参数表与解析逻辑同源（`BuildConfig.Args`），
完整用法可以在编辑器里点 `PirateCrew/Build/打印出包参数用法` 打印出来。

**铁律**：`-batchmode` 必须显式带 `-projectPath` 且带 `-nographics`（缺 `-projectPath` 会打开
EditorPrefs 里的"最近工程"；本机不带 `-nographics` 会卡在 GfxDevice 创建）。同一时刻只跑一个 Unity 进程。

### 1.3 只验证不出包（CI 前置 job 用）

两条都不出包，只做预检。**注意 Unity 自身的启动开销**（本机 batchmode 冷启动约半分钟），
所以这里的"快"是相对出包（数分钟）而言，不是"秒级"。

```bash
U="F:/Unity/2022.3.62f1c1/Editor/Unity.exe"
P="F:/VSCode/pirate-crew-3d-unity/pirate-crew"

# 校验配置与发行场景集（版本号 / 场景存在 / 场景覆盖 / 后端可用 / 应用标识）
"$U" -batchmode -nographics -quit -projectPath "$P" \
  -executeMethod PirateCrew.EditorTools.BuildSystem.BuildScript.ValidateReleaseScenes -logFile -

# 只写 PlayerSettings 并读回校验（不出包）
"$U" -batchmode -nographics -quit -projectPath "$P" \
  -executeMethod PirateCrew.EditorTools.BuildSystem.BuildScript.ApplyPlayerSettingsOnly -logFile -
```

## 2. 参数表

| 参数 | 值 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `-buildTarget` | `win64` | `win64` | 目标平台。当前只有 Windows 64 位一种；其余平台未验证，脚本会明确拒绝而不是假装支持 |
| `-buildFlavor` | `release` / `development` | `release` | development 追加 `BuildOptions.Development \| AllowDebugging`，托管剥离关闭 |
| `-buildVersion`（别名 `-pcVersion`） | `0.1.0` | `BuildVersion.Current` | 覆盖版本号，写进 `bundleVersion`、产物名与构建报告 |
| `-buildOutput` | 目录 | `<仓库根>/external/build/<版本>/win64` | 相对路径按**仓库根**解析（不是 cwd） |
| `-buildScenes` | `release` / `development` / `a,b,c` | `release` | 场景集；自定义列表也要过校验 |
| `-buildScriptingBackend` | `mono` / `il2cpp` | `mono` | il2cpp 会在预检阶段检查模块是否安装（见 §3.3） |
| `-buildCommit` | sha | 直读 `.git/HEAD` | CI 注入；报告里 `commitSource` 如实标注来源 |
| `-buildBranch` | 分支名 | 直读 `.git/HEAD` | 分离 HEAD 时为 `unknown`（不编造） |
| `-buildAppId` | `com.company.product` | `com.boranfan.piratecrew3d` | 见 §4.3【提案/待定】 |
| `-buildClean` | 开关 | 关 | 附加 `BuildOptions.CleanBuildCache`（怀疑脏缓存时用） |
| `-buildZip` | 开关 | release 档开 / development 档关 | 打成 `PirateCrew3D_v<版本>_win64.zip` |
| `-buildNoPlayerSettings` | 开关 | 关 | 跳过 PlayerSettings 写入（只想验证构建、不许工程被改写时用） |
| `-buildReport` | 路径 | `<输出目录>/build-report.json` | 同目录另写一份 `.md` |

### 2.1 退出码

| 码 | 含义 | 常见原因 |
| --- | --- | --- |
| `0` | 成功 | 产物存在 |
| `1` | 构建失败 | Unity 侧有 error；看报告的 `result` 与 `errorMessages` |
| `2` | 构建过程抛异常 | `BuildPipeline.BuildPlayer` 抛错或返回 null |
| `3` | 预检失败 | 版本号非法、场景缺失、场景漏登记、后端未安装、图标资源缺失、PlayerSettings 读回不一致 |
| `4` | 参数不合法 | 未知构建档 / 未知平台 / `-buildVersion` 缺值 |

batchmode 下由 `EditorApplication.Exit(code)` 传出；**编辑器 GUI 里不调用 Exit**
（在 GUI 里 exit 会把编辑器关掉），只记日志。

## 3. 版本号规则

### 3.1 单一真源在哪

**`pirate-crew/Assets/Editor/Build/BuildVersion.cs` 的 `BuildVersion.Current`**，当前值 `0.1.0`。
从这里派生的东西：

| 派生点 | 怎么派生 |
| --- | --- |
| `PlayerSettings.bundleVersion` | 构建时由 `PlayerPreset.Apply` 写入并读回校验 |
| `ProjectSettings/ProjectSettings.asset` 的 `bundleVersion` | **唯一允许手改的 PlayerSettings 字段**（当前 0.1.0，已对齐）；build 时被写回同一值 |
| 可执行文件名 | `BuildVersion.ExecutableName` = `PirateCrew3D.exe` |
| 发布压缩包名 | `BuildVersion.ZipName` = `PirateCrew3D_v<版本>_win64.zip`（与 README 的下载文件名同源） |
| Windows 文件版本 | `BuildVersion.NumericVersion` 补成四段（`0.1.0` → `0.1.0.0`） |
| 构建报告 | `version` / `numericVersion` 两个字段 |
| README 版本徽章与下载链 | 人工同步（对应「已发行的 release」，见 §3.2） |

**格式约束**：三段纯数字 `major.minor.patch`，每段 ≤ 65535（Windows 文件版本字段上限，
超了 Unity 会自行截断进而与文档不一致）。`BuildVersion.Validate` 负责判，非法直接预检失败。

### 3.2 为什么 README 的 v0.1.0 与构建版本号是两件事

README 里的 `v0.1.0` 指向**已经发行的 GitHub release**（有 tag、有下载包），
`BuildVersion.Current` 是**下一次构建要打的版本号**。发布节奏上两者会短暂不同步
（例如已发行 v0.1.0、正在准备 v0.2.0），所以门禁对 README 只警告不失败
（`.github/scripts/repo_gates.py` 的 version 门禁）。发新 release 时把 README 一起更新即可。

### 3.3 当前对齐状态与遗留冲突

- `BuildVersion.Current = 0.1.0`、`ProjectSettings.bundleVersion = 0.1.0`、README `v0.1.0` —— **三方已一致**
  （用户 2026-09-21 裁决：以 0.1.0 为准，与已发行 tag 对齐）。
- **遗留冲突（未消除，已登记）**：
  1. `pirate-crew/Assets/Editor/ReleaseGate.cs:27` 的 `BundleVersion = "1.0.0"` 是旧值。
     该文件的菜单 `PirateCrew/Release/应用图标与版本` 会执行 `PlayerSettings.bundleVersion = BundleVersion`，
     **重跑一次就会把 bundleVersion 回写成 1.0.0**。
     处置建议（属该文件的文件域，本轨道未改）：把该常量改成引用 `BuildVersion.Current`，
     或直接删掉版本写入那两行（图标生成本身仍然有用，留着）。
  2. `pirate-crew/Assets/Scripts/UI/UiStrings.cs` 的 `MainVersion = "版本 1.0"` 是**玩家可见文案**
     （主菜单页脚显示"版本 1.0"），与真源 0.1.0 不一致。它属 `Scripts/` 文件域，本轨道未改。
     处置建议：改成 `"版本 " + 真源` 的单一来源（或直接把文案与版本号解耦，只显示 `Application.version`）。

在修好之前，`.github/scripts/repo_gates.py` 把这两处列进版本门禁的**警告通道**
（ReleaseGate 走 `KNOWN_DRIFT` 白名单、UiStrings 走独立的展示串检查），
**只是降级为警告并打印原因，不是允许长期存在**——修好后请把白名单条目删掉。

## 4. 产物结构与命名

### 4.1 目录

```
external/build/                     # gitignored（仓库根 .gitignore 的 external/）
└── 0.1.0/                          # 版本号，来自 BuildVersion.Current
    ├── PirateCrew3D_v0.1.0_win64.zip   # -buildZip 开时生成（release 档默认开）
    └── win64/                      # Unity 播放器输出目录本身
        ├── PirateCrew3D.exe        # 双击即玩
        ├── PirateCrew3D_Data/      # 数据目录（Unity 按 exe 名生成）
        ├── UnityPlayer.dll / MonoBleedingEdge/ ...
        ├── build-report.json       # 构建报告（机器读）
        └── build-report.md         # 构建报告（人读）
```

**为什么 zip 落在 `win64/` 的上一级**：压缩包与"解压即可玩"的目录不互相嵌套，
反复打包时不会把上一次的 zip 卷进这一次。

**为什么输出默认落 `external/`**：`external/` 整目录已 gitignore，出包产物天然不入库；
同时与 `export/`（出图暂存）分开，避免两类过程产物混在一起。

### 4.2 仓库内不该出现的构建产物

`pirate-crew/Build/`、`pirate-crew/Builds/`、`pirate-crew/Logs/` 等（`pirate-crew/.gitignore`
的 `[Bb]uild/` 系列已覆盖）。CI 里用的输出目录是仓库根的 `build/`（被根 `.gitignore` 的
`[Bb]uild/` 覆盖），与本地默认的 `external/build/` 互不干扰。

### 4.3 应用标识【提案/待定】

`PlayerSettings.applicationIdentifier`（Standalone 组）被脚本写成 **`com.boranfan.piratecrew3d`**。
这是 AI 按反向域名习惯拟的**提案值，等用户确认**；换个值只需改
`BuildConfig.AppId` 的缺省或用 `-buildAppId` 传。落成值会出现在构建报告的
`appId` 字段里，可核对。

## 5. 构建报告解读

每次构建（**成功或失败都写**）在输出目录落两个文件。失败也写是有意的：
报告是排查的起点，只在成功时写等于在最需要它的时候没有它。

### 5.1 JSON 字段（`build-report.json`）

| 字段 | 含义 |
| --- | --- |
| `schema` | 报告 schema 版本，字段增删时递增（当前 1），供解析脚本判代 |
| `version` / `numericVersion` | 版本号与四段文件版本 |
| `flavor` / `target` | 构建档 / 目标平台 |
| `sceneSet` / `scenes` | 场景集来源（参数原值）与**实际打进包的场景顺序** |
| `outputPath` / `executablePath` | 产物目录 / 可执行文件绝对路径 |
| `zipPath` / `zipBytes` | 压缩包路径与体积（未打包为空串 / 0） |
| `unityVersion` | 用的 Unity 版本（`Application.unityVersion`） |
| `gitCommit` / `gitBranch` / `commitSource` | 构建自哪个提交；来源 `cli`（CI 注入）/ `git`（直读）/ `unknown` |
| `scriptingBackend` / `appId` | 脚本后端 / 应用标识 |
| `playerSettings` | **本次强制写入并读回校验通过**的 PlayerSettings 条目清单 |
| `result` / `totalErrors` / `totalWarnings` | Unity 的构建结论与计数 |
| `buildSeconds` | 构建耗时（`BuildSummary.totalTime`） |
| `reportSizeBytes` | Unity 统计的构建产物体积（`BuildSummary.totalSize`） |
| `outputSizeBytes` / `outputFileCount` | 输出目录**实测**体积与文件数（不含报告自身） |
| `topFiles` | 体积前十的产物文件（一眼看出体积花在哪） |
| `errorMessages` | 构建步骤里的 error/exception 消息（最多 20 条） |

`outputSizeBytes` 与 `reportSizeBytes` 会给两个数是有意的：前者是磁盘上真实占用
（含 exe、dll、Mono 运行时），后者是 Unity 口径的构建数据量。排查"包怎么这么大"看前者 + `topFiles`。

### 5.2 Markdown（`build-report.md`）

同一份数据的可读版：结论表 / 产物表 / 场景清单（带 index）/ 体积 TOP / 本次写入的 PlayerSettings /
error 摘要（有错时）。适合直接贴进 PR 或 issue，不必让读者去看 JSON。

## 6. 场景清单：发行集与开发集

### 6.1 两个集合

| 集合 | 场景 | 用途 |
| --- | --- | --- |
| **发行集**（5） | `Bootstrapper`(index 0) → `MainMenu` → `Battle` → `CrewManagement` → `LevelSelect` | 打进发行包 |
| **开发集**（6） | 发行集 + `ToonPilot` | 编辑器 Play / 播放器出图（等距像素卡通试点场景） |

单一真源是 `pirate-crew/Assets/Editor/Build/BuildScenes.cs`（静态表）。
选静态表而不是 `Assets/Scenes/ScenesManifest.asset` 的三条理由（编译期可校验、不含 GUID、
可进代码评审 diff）写在该文件的类注释里，此处不重复。

### 6.2 与 Build Settings 的关系（这是最容易踩的地方）

**出包不读也不写 `EditorBuildSettings`**：场景列表由 `BuildPlayerOptions.scenes` 显式传给
`BuildPipeline.BuildPlayer`。两个理由：

1. 本机 batchmode 下 `EditorBuildSettings.scenes` 的 API 写入**不落盘**（已有事故记录，
   见 `Assets/Editor/ToonPilotSetup.cs` 的注释）；显式传参天然绕开这个坑。
2. Build Settings 是"编辑器里按 Play 想看什么"的列表，**必须留 ToonPilot**（播放器出图入口依赖它），
   而发行包不该含它。两者诉求相反，不该共用一个列表。

想让两者一致时用显式菜单动作（不是构建的副作用）：

```
PirateCrew/Build/同步 Build Settings（开发集 6 场景）    # 日常用这个
PirateCrew/Build/同步 Build Settings（发行集 5 场景）    # 提交发行前的准备
```

### 6.3 场景集的校验项

`BuildScenes.Validate`（供预检与 CLI 调用）逐条判：

1. 非空、元素是**场景名**而不是路径（传 `Assets/Scenes/Battle.unity` 直接报错）
2. 无重复（重复会让包内出现同名场景，加载依赖顺序，属静默故障）
3. 场景资产真实存在（`AssetDatabase.LoadAssetAtPath<SceneAsset>` 非空）
4. `[0]` 必须是 `Bootstrapper`（播放器启动场景）
5. **覆盖 `SceneNames` 声明的全部场景**——运行时 `SceneLoader.ChangeScene` 会切到的场景
   若不在包里，玩家手里会 `LoadScene` 失败。这条用反射列 `SceneNames` 的 `public const string`
   自动比对，新增场景常量忘了进发行集就会变成一条报错
6. 发行档禁止出现仅开发场景（`ToonPilot`）

同一套判据在 CI 里有一份不依赖 Unity 的实现：`.github/scripts/repo_gates.py scenes`
（本机可跑：`python .github/scripts/repo_gates.py scenes`）。

### 6.4 与 `M3SceneSetup.cs` 的冲突（登记，未处置）

`pirate-crew/Assets/Editor/M3SceneSetup.cs:449` 的 `RegisterBuildSettings()` 是**幂等全量写入**
6 场景（含 `ToonPilot`），自带一份硬编码数组，每次跑装配链都会覆盖 Build Settings。
它与本手册 §6.1 的"开发集"语义相同但两处维护。**出包不受影响**（构建不读 Build Settings），
但两处清单会各自漂移。处置建议：把该方法的数组换成 `BuildScenes.DevelopmentSet()`
（一行改动，需该文件的文件域所有者执行）。在那之前，改动场景清单要同时看这两处。

## 7. PlayerSettings：脚本是真源，YAML 是产物

`PlayerPreset.Apply` 在每次构建时显式写入下列字段，并**读回校验**（读了不一致直接判预检失败，
不产出一个"配置与声明不符"的包）：

| 字段 | 值 | 依据 |
| --- | --- | --- |
| `companyName` | `BoranFan` | 项目作者署名（与既有 YAML 一致） |
| `productName` | `Pirate Crew 3D` | 窗口标题与系统里的名字 |
| `bundleVersion` | `BuildVersion.Current` | §3.1 |
| `applicationIdentifier`(Standalone) | `com.boranfan.piratecrew3d` | §4.3【提案/待定】 |
| 图标（`IconKind.Application` 全部尺寸槽） | `Assets/Art/Textures/AppIcon.png` | 一张 1024 PNG 填满全部槽，Unity 构建期按槽缩放 |
| 默认分辨率 | 1920×1080 | 与 README 系统需求页一致 |
| 全屏模式 | `FullScreenWindow` | 保持项目既有行为（`fullScreenMode: 1`），不改成独占全屏 |
| `resizableWindow` / `runInBackground` | false / true | 保持既有行为 |
| 图形 API 顺序 | `[Direct3D11]`（并关掉"用平台默认"） | 让 README 声明的"DirectX 11 兼容"与实际作出的包对得上 |
| 脚本后端 | `mono`（可 `-buildScriptingBackend il2cpp`） | §7.2 |
| `apiCompatibilityLevel` | `NET_Standard_2_0` | 与工程现值一致；升级会改变可用 BCL 面，无收益 |
| 托管剥离等级 | release `Low` / development `Disabled` | §7.3 |

### 7.1 唯一手改的 YAML 字段

`ProjectSettings/ProjectSettings.asset` 的 `bundleVersion` 是本手册唯一允许手改的 PlayerSettings
字段（改它是因为版本号要在**未构建**时也正确，例如 README 与 tag）。构建时脚本会把它写回
`BuildVersion.Current`，所以只要真源对，YAML 不会漂。

**副作用提醒**：跑一次构建会写 PlayerSettings，因此 `ProjectSettings/ProjectSettings.asset` 会变。
首次跑完请 `git diff` 确认改动只有预期字段——尤其是图标的写入路径：新 API
（`PlayerSettings.SetIcons(NamedBuildTarget, …)`）写 `m_BuildTargetPlatformIcons`，
而仓库里现有图标数据在旧的 `m_BuildTargetIcons` 下，首次写入会把图标迁到新字段
（这是有意的工业化动作，不是事故）。不想让工程被改写时用 `-buildNoPlayerSettings`。

### 7.2 脚本后端：本机只装了 Mono（未验证的 IL2CPP）

实测本机 Unity 的 `Editor/Data/PlaybackEngines/WindowsStandaloneSupport/Variations/` 下只有
Mono 变体（`mono`、`win32/win64_player_*_mono`），**没有 `win64_il2cpp`**，也没有 IL2CPP 平台模块。
所以缺省后端是 **Mono**；显式传 `-buildScriptingBackend il2cpp` 时，
`PlayerPreset.CheckScriptingBackend` 会先检查变体目录是否存在，不存在就**在预检阶段失败**
并给出安装指引（Unity Hub 给 2022.3.62f1c1 追加安装 "Windows Build Support (IL2CPP)"），
而不是构建到一半报一句难懂的 IL2CPP 错误。

**未验证**：本机没有 IL2CPP 模块，所以 IL2CPP 路径**从未真正构建过**，
检查逻辑与 PlayerSettings 写入都只经过编译验证（§10）。

### 7.3 托管剥离为什么停在 Low

release 档取 `Low`：剥掉未使用的引擎代码但不碰托管类型。**故意不用 Medium/High**——
本项目有反射依赖（`SceneNames` 常量反射校验、`EventCatalog` 反射测试），
提高剥离等级需要先补 `link.xml` 保留清单，否则是"构建成功、运行期找不到类型"的静默故障。
要提等级，先把保留清单和一条"剥离后仍能跑"的验证补上。

## 8. CI 配置与 secrets

CI 在 `.github/workflows/ci.yml`，三个 job：

| job | 触发 | 做了什么 |
| --- | --- | --- |
| `repo-gates` | 每次 push / PR | 纯文本门禁（无需 Unity、无需 license）：版本号单一真源、发行场景集交叉校验、仓库卫生（行尾策略 / `.meta` 配对 / IDE 产物）。实现在 `.github/scripts/repo_gates.py`，本机可跑 |
| `unity-tests` | 每次 push / PR | `game-ci/unity-test-runner@v4` 跑 EditMode + PlayMode（矩阵两档），产物上传 artifact |
| `build-windows` | 手动触发 或 推 `v*` tag | `game-ci/unity-builder@v4` 调本工程的出包入口 `BuildScript.BuildFromCommandLineArgs`，上传产物与构建报告 |

### 8.1 secrets 清单

| secret | 什么时候需要 | 怎么拿 |
| --- | --- | --- |
| `UNITY_LICENSE` | Unity **Personal** | 用 game-ci 的激活流程生成 `.ulf`（本地 `Unity -batchmode -createManualActivationFile` → 上传转 `.ulf`，或跑 game-ci 的 activation workflow），把 `.ulf` 全文存成 secret |
| `UNITY_EMAIL` + `UNITY_PASSWORD` + `UNITY_SERIAL` | Unity **Plus / Pro** | Unity 账号邮箱、密码、序列号；三者同时提供 |
| `GITHUB_TOKEN` | 需要 | GitHub 自动注入，**不需要手工配置** |

**workflow 里没有任何密钥字面量**，全部经 `secrets.*` 注入；未配置时 Unity job 一定失败——
那是"没有 license 跑不了 Unity"的事实，不是 CI 配错了。

### 8.2 本机环境与 CI 环境的差异

| | 本机 | CI |
| --- | --- | --- |
| OS | Windows 10 | Ubuntu latest |
| Unity | 2022.3.62f1c1，`F:/Unity/2022.3.62f1c1/Editor/Unity.exe` | game-ci 的 `unityci/editor` 镜像，版本由 `UNITY_VERSION` 指定 |
| license | 本机已激活 | 从 secrets 注入 |
| 脚本后端 | 只有 Mono（§7.2） | 镜像自带模块，两侧缺省可能不同 |
| 无头验证台 | `external/m2-harness/*.csproj`（不入库） | **不可用**——它用 `HintPath` 指向本机 `F:\Unity\...` 的 DLL |

两条直接后果：

1. **无头验证台在 CI 里跑不了**。所以 CI 的静态 job 用的是纯文本门禁（`repo-gates`），
   而不是假装能在云上编译 Unity 程序集。要在 CI 里做"能编译"的证据，靠的是 `unity-tests` 那个 job。
2. 出包 job **故意不指定** `-buildScriptingBackend`，让本机与 CI 各用各的缺省，
   差异由构建报告的 `scriptingBackend` 如实记录。

### 8.3 CI 的真实状态：未验证

`ci.yml` **从未在 GitHub 上执行过**（本仓库此前没有任何 `.github/`，本机也没有 Docker / Runner）。

## 11. 仓库卫生（行尾策略与忽略规则）

### 11.1 行尾策略

`.gitattributes` 为 Unity 序列化资产钉死 LF：`*.meta` `*.unity` `*.prefab` `*.asset` `*.mat` `*.controller`。

**为什么**：本仓库 `core.autocrlf=true`。缺省时 git 签出把 LF 转 CRLF，而 Unity 改写文件写回 LF——
于是"Unity 一保存，整个文件变成一行尾 diff"，真实变更被淹没（2026-09-17 审计 §七的 47 个 `.fbx.meta`
行尾漂移事故即此类）。

**为什么可以放心加**：全仓索引里 `i/crlf` 文件数为 **0**，也就是说这些扩展名的内容在 git 里本来就
存成 LF，加属性只固定"以后签出也是 LF"，**不改动已入库内容的任何一个字节**。

改动前后必须跑的验证（本机实测：加属性前后 `git status` 只多出 `.gitattributes` 自己一行）：

```bash
cd /f/VSCode/pirate-crew-3d-unity
git status --porcelain > /tmp/before.txt
# 改完 .gitattributes 后
git status --porcelain > /tmp/after.txt
diff /tmp/before.txt /tmp/after.txt      # 只应出现 .gitattributes 一行
git ls-files --eol | awk '$1=="i/crlf"' | wc -l   # 应恒为 0
```

**为什么不给 `*.cs` 也钉 `eol=lf`**：工作树里有 18 个 `.cs` 是 CRLF（363 个里），
钉上会让它们立刻显示为已修改（行尾不匹配），而那批文件分属其他轨道。
留待各轨道自行统一；`.editorconfig` 里已把 `end_of_line = lf` 写成 C# 的约定。

### 11.2 忽略规则

- 仓库根 `.gitignore`：**没加新规则**（`external/`、`export/` 已覆盖出包与出图产物；
  `[Bb]uild/` 已覆盖各类构建目录）。只补了一段注释，说明 `[Bb]uild/` 没有锚点会误伤
  "名字叫 Build 的源码目录"。
- `pirate-crew/.gitignore` 加了两处：
  1. **`!Assets/Editor/Build/`（反选）**——`[Bb]uild/` 会命中出包脚本自己的源码目录
     `Assets/Editor/Build/`，不反选这些文件会在 `git status` 里整体消失**且不报错**。
     git 的规则是"父目录被排除后无法再反选其内容"，所以反选的必须是目录本身。
     验证：`git check-ignore -v pirate-crew/Assets/Editor/Build/BuildScript.cs`（应无输出）。
  2. `/Assets/Screenshots/`——Unity MCP 的 `manage_camera` 默认落图目录，
     属过程产物，按 `export/` 同款纪律不入库。
- `*.csproj` / `*.sln` / `.vs/` / `*.user` 已由 `pirate-crew/.gitignore` 覆盖，无需补。

### 11.3 代码风格

`.editorconfig`（仓库根，新建）声明了本仓库**实际在用**的风格（4 空格缩进、Allman 花括号、
块级 namespace、私有字段 `_camelCase`、行宽上限 120），每条都附了实测统计口径，
不是理想化规范。细节与样本见 [开发者指南.md](开发者指南.md) 的「编码规范」一节。

**一个实测踩到的坑**：`.editorconfig` 的注释行里**不要写等号**。
实测（`editorconfig-core-js` 3.0.2，2026-09-21）：含等号的 `#` 注释会被解析成一条**属性**
（键名变成 `# …`、值被等号切开），注释静默变成数据。本文件已按此纪律把注释里的等号改成汉字或箭头。
验证方法（本机可跑，5 类文件各解析一次看有没有以 `#` 开头的键）：

```bash
cd <临时目录> && npm install editorconfig --silent
node -e "
const ec=require('editorconfig');
(async()=>{for(const f of ['pirate-crew/Assets/Editor/Build/BuildScript.cs','pirate-crew/Packages/manifest.json'])
  console.log(f, JSON.stringify(await ec.parse(f)));})();
"
# 期望：.cs 命中 4 空格 + 全套 csharp_* 规则；.json 命中 2 空格；没有任何键以 '#' 开头
```
