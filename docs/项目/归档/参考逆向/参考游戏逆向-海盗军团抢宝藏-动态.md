# 参考游戏逆向 · 海盗军团抢宝藏 —— 动态试玩观察

> 静态反编译分析见姊妹篇《参考游戏逆向-海盗军团抢宝藏-静态.md》（ffdec 反编译 AS2）。本篇记录**运行时观察**：菜单流程、交互死点、Ruffle 运行日志与 swf 字符串挖掘。
> 原版身份：Nitrome《Mutiny》(2008) 汉化版（swf 内请求 `www.nitrome.com/php/retrieve_scores.php` 证实）。

## 1. 试玩环境与方法

- 运行环境：Ruffle 0.6.0（wasm，wgpu-webgl 渲染），本地 `http.server` 8000 端口
- 驱动方式：headless Edge + CDP 远程调试（端口 9527），工具链在 `external/tools/`：
  - `cdp.mjs`——CDP 单动作控制器（open/shot/click/drag/move/keypress/eval/console/dimensions）
  - `ocr.ps1` + `prep_ocr.py`——WinRT OCR + 裁剪放大二值化预处理（像素艺术字识别率低，仅辅助）
  - `color_blocks.py`——canvas 区域量化色块连通域分析（找按钮/人物结构）
  - `imgdiff.py`——前后截图差分（>15% 判定界面切换，3-6% 为海面动画噪声）
- 无视觉模型可用（当前会话不支持图片输入、云端视觉 API 够不到 localhost），全部靠上述"盲操作+差分取证"

> ⚠ **勘误（2026-09-13）**：上面这条前提**是错的**——实测证明会话模型可以直接读取 PNG 并准确描述内容
> （读 `external/playtest-shots/02_menu.png` 能正确说出标题、四个按钮、角落版本号与版权行）。
> 因此本次采用的"盲操作"是被错误前提驱动的过度绕路。
> **但下文的技术结论仍然有效**：所有关键结论（按钮真实坐标、元件原点偏移、`tt` 覆盖层阻塞）都用
> 静态反编译的 `PlaceObject` 表或 Ruffle 日志做了交叉验证，不依赖视觉确认。
> 后续再做图像相关判断时**先实测能力再定方法**，不要沿用旧会话的能力假设。

## 2. 菜单流程实测（index.html 版坐标，canvas 874×656 @ 页面(183.5,105)）

```
主菜单（海面+一排海盗人物）
  ├─ PLAY    (620,440) ✓ → 1P/2P 选择界面（f89 game_select）
  ├─ SCORES  (620,480) ✓ → 排行榜界面（等 nitrome.com LoadVars，本地无数据但不卡流程）
  ├─ HELP    (约620,520) （推断，未验证）
  └─ CREDITS (620,560) ✓ → 制作名单（OCR 认出 CHRIS BURT 等 Nitrome 成员名）
1P/2P 选择（提示语："CLICK ONE OF THE BUTTONS BELOW … 1 PLAYER … COMPUTER OR … FRIEND"）
  ├─ 1p_button  舞台(163,263)px → 全屏(413,505) ✓ → level_select_1p
  └─ 2p_button  舞台(387,263)px → 全屏(843,505)（未试）
level_select_1p（15 关网格 5×3）
  └─ ls_1 实测全屏(360,189) ✓ → game 帧（76.3% 全屏切换，进入战斗）
game 帧 ✓ —— 海岛战场+右上小地图(216×136)+底部三段黄条 HUD+开场对白（SpeechBubble，1P 固定 2 段，OCR 读出台词碎片）
```

- 主菜单四按钮竖排于中部偏下，按钮与海面背景同为像素风、无明显色块差，靠**逐层点击+差分**定位（620,480 首次命中的其实是 SCORES 不是 PLAY——先后进了 SCORES 与 CREDITS 才反推出 PLAY 在 y≈440）
- **坐标换算经验（重要）**：SWF 舞台 550×400，debug 全屏 canvas 1256×768 下 scale=1.92、offset x=100（Ruffle 日志 `retessellated: new_scale=1.92` 可反推验证）。PlaceObject 的 translation 是**元件原点**而非视觉左上/中心——1p_button 直接换算即命中，而 ls_1 按 (110,68) 换算成 (311,131) 未中、实测网格左上在 (360,189)（元件内容相对原点有偏移）。**结论：静态坐标给出量级，最终以色块/动块实测校准**。
- SCORES 界面结构：深灰背景 + 顶部标题带 + 两侧对称人物 + 底部信息条（实为 game_select 风格布局，1P/2P 界面与之同构——初期曾误判为同一界面）

## 4. 交互观察与遗留问题（Ruffle 0.6.0）

1. **初期"1P/2P 界面死点"已推翻**：根因是点击位置全都不在真按钮上（1p_button 实际在舞台 (163,263)，此前盲猜的位置全部偏移）。用静态反编译坐标换算后一击命中——**盲操作+差分与静态 PlaceObject 表互相校准**是本次逆向方法论的核心。
2. **game 帧角色交互未打通（遗留）**：进入战斗后，点击/拖拽场上角色均未触发选中与武器面板。结合静态篇输入链路分析，按可能性排序：
   - 开场对白吞点击（`if(Controller.speechBubble)` 前置分支，1P 固定 2 段）——已连点 4 次推进，但无法从 JS 层确认对白是否彻底结束；
   - **tt 转场层嫌疑（头号）**：全屏白矩形常驻 root depth 210（在武器面板 d39、角色层之上），alpha 动画到 0 后若 Ruffle 仍对其做命中测试，`Controller.content.onMouseDown` 永远收不到事件——这恰好解释"菜单按钮（onRelease）能点、游戏内（content.onMouseDown）点不中"。真 Flash 中 alpha=0 的 Shape 不参与命中。验证需执行 AS（`_root.tt._visible=false`），Ruffle 无 AS 执行通道，**无法从 JS 层修复或确诊**；
   - 30px 选中半径 + 必须点中角色本体图形（content 子树）。延时差分已定位场上 4 个角色活动块（(226,360)/(321,448)/(534,362)/(628,449)），点击其中心未选中，与上一条嫌疑互斥性待定。
   - 结论：投掷闭环（选人→面板→弹弓拖拽→爆炸→AI 回合→胜负）的**动态验证未完成**，但静态篇已给出全链路伪代码与公式（v=0.25×拖距、上限 20/30、两阶段选择、inactivity≥10 帧推进回合），Unity 版实现以静态篇为准。
3. **菜单键盘无响应是预期**：全 swf 菜单不响应键盘（键盘仅在 game 帧用），勿据此判断界面卡死；按钮也不设手型光标（SimpleButton 基类不设 useHandCursor）。
4. 已验证可交互：主菜单 PLAY/SCORES/CREDITS、1P 按钮、关卡 ls_1——输入映射链路整体正常。

## 6. 对 Unity 版的移植启示（已与静态篇合并定稿）

1. 武器清单以 17 种为准（静态篇 §武器有全部机制/数值），Godot 版 6 种是子集——M2 SO 数值资产按全集建表，分批实现
2. 回合状态机命名直接对照 Controller 方法族（startTurn/finishTurn/isTurnComplete/continueTurn/totalTurnsTaken）；"静止即推进"（inactivity≥10 帧）替代回合计时器
3. 关卡数据内嵌（EmbeddedLevels，33 关 XML）→ Unity 版走 ScriptableObject 关卡资产
4. 原版网站桥依赖（解锁/分数）在 Unity 版不存在，用本地存档替代；得分公式 `floor(平均血量×20 − 回合数×25)`、下限 `关号×10`
5. 自定义光标（CustomCursor）、范围圈（rangeCircle）、瞄准虚线（dottedLine，15 段预测线含 weight 重力步进）是核心交互反馈，M2 的 UI/瞄准系统需对应实现
6. 两阶段选择交互（30px 点选角色 → 面板选动作/武器 → 弹弓拖拽）+ 投掷公式 v=0.25×拖距（上限 20，香蕉/跳伞/朗姆 30）直接进 M2 数值
7. 角色无属性差异（HP 100/weight 1），差异靠武器与关卡 luck——Godot 版 crew_config.json 的差异化设计与原版不同，重制时二选一并记录取舍
