## 详情

**【流程提速】Unity 协作摩擦收账**（走查批次被 Unity 冷启动、缺常驻驱动、残锁卡出的账）——

① **驱动开着的编辑器**执行菜单/装配（不再要求关编辑器）：原定目标实现 Unity CLI 已裁决**不可用**——
CLI 本体在 2022.3.62f1 机器上能装能认，但控制面命令（test/open/recompile/watch）全部依赖
`com.unity.pipeline` 包，该包全部已发版本要求 Unity 6000.0+，2022.3 装不进去（证据与出处见
无头验证与启动成本优化 §2）——退回**常驻 Editor + 自建命令桥**，以工程内 `McpBridgeKick` stdio
垫片为起点；
② **单入口编排**：一次 batchmode 启动串跑多件装配——已落 `run.sh chain` 档 +
`PirateCrew.EditorTools.HeadlessChain` 反射编排器（步骤开跑前全量解析校验、逐步计时、
摘反射包装异常、带退出码收口；装配会改场景/资产，故不做缓存）；
③ **编辑器退出补清锁兜底**（残锁连害两轮）——已落 `run.sh unlock` 档（只删锁文件本身，
Unity.exe 在跑时拒绝，口径与 `guard_unity` 一致）；
④ **量化导入 vs 编译**：已逐项分解并冷热对账（改动触发全量刷新 77.6 s vs 无改动 10.6 s、
每进程固定税 ≈24 s、冷热差 ≈120 s 全是重编双重载牵连），结论记无头验证与启动成本优化 §1.1。

**为什么要做**：单次 Unity 冷启动 ≈2.5 分钟，而用例本体只有十几秒——见无头验证与启动成本优化 §1
的实测表；分解后口径更狠：**少启动一次省的远比少测几条多**，固定税与重编牵连都只能靠少启动摊薄。
