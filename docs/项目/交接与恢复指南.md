## 4. 环境铁律（踩过坑，不要重犯）

### 4.1 Unity 进程

- **batchmode 必须显式带 `-projectPath` 且带 `-nographics`**。缺 `-projectPath` 会打开 EditorPrefs 里的"最近工程"，
  可能污染/锁住别的项目——本项目曾因此产生**杀不死的僵尸进程**卡住 `Temp/UnityLockfile`，只能重启机器清理。
- **一次只跑一个 Unity 进程**（`Library/` 锁是独占资源）。多 agent 并行时，涉及 Unity 的验证由协调者串行执行。
- **跑完 PlayMode 测试后检查 `ProjectSettings/EditorSettings.asset`**：实测（2026-09-13）PlayMode 测试运行过程会把
  `m_EnterPlayModeOptionsEnabled` 从 `0` 改成 `1`（配 `m_EnterPlayModeOptions: 3` = 关掉域重载 + 场景重载）。
  这会**静默改变静态状态语义**（例如 `EventBus` 这类静态事件中心在两次 play 之间不再被重置），
  不是本项目想要的默认值 → 提交前用 `git checkout -- pirate-crew/ProjectSettings/EditorSettings.asset` 还原。
- **`core.autocrlf = true` 且仓库无 `.gitattributes`**：Unity 写出的 YAML 是 LF，git 入库按 CRLF 归一，
  于是每次 Unity 改写文件都会出现"整文件行尾变化"的噪音警告。已登记为待办（见 [待办事项.md](待办事项.md) 工程基建），
  本次未擅自改仓库级行尾策略。
- 本环境 **batchmode 没有可用的渲染路径**（不带 `-nographics` 会卡在 GfxDevice 创建），
  所以 `Camera.Render` / `ScreenCapture` **拿不到真实像素**——需要出图的验收必须用图形界面编辑器会话。

### 4.2 无头验证台（这是本项目最重要的效率杠杆）

`external/harness/`（**不入库**，`external/` 已 gitignore）用 `dotnet` 直接引用 Unity 已编译程序集 + NuGet NUnit，
**不启动 Unity 就能编译工程源码并跑纯 C# 测试**，从而绕开 `Library/` 独占锁。

```bash
cd /f/VSCode/pirate-crew-3d-unity
mkdir -p external/harness-<你的域> && cp external/harness/Harness.csproj external/harness-<你的域>/
cd external/harness-<你的域>
dotnet test  Harness.csproj -p:HarnessScope=Battle    # 跑测试
dotnet build Harness.csproj -p:HarnessScope=Runtime   # 只编译（快）
```

| `HarnessScope` | 编译范围 | 用途 |
| --- | --- | --- |
| `All` | `Scripts/**` + `Tests/*.cs` + `Tests/PlayMode/*.cs` | 全量体检（含 31 条第 4.3 节所说的必然失败项）。⚠ MSBuild 通配符**不递归子目录**，`Tests/PlayMode` 是显式补的一行；PlayMode 用例在本域**只编译**、不可在无头环境运行（2026-09-13 发现并修补） |
| `Data` | Core + `PirateCrew/Data` + `Tests/Data` | 数值层 |
| `Combat` | Core + `PirateCrew/Combat` + `Tests/Combat` | 战斗纯逻辑 |
| `Battle` | Core + Data + Combat + Battle + UI + `Tests/Battle` | 战斗组装层与弹体（**刻意排除 `Rendering/`**，避免并行 agent 互相干扰） |
| `Rendering` | Core + `PirateCrew/Rendering` | 描边 RendererFeature（需 URP 程序集） |
| `Runtime` | `Scripts/**` | 纯运行时编译检查 |
| `DataEditor` | `Scripts/**` + `Assets/Editor/**` | **进 Unity 之前抓编辑器脚本的编译错误** |

**能力边界（务必理解，别误判）**：`GameObject` / `MonoBehaviour` / `ScriptableObject` 的实例化走原生 `ECall`，
脱离 Unity 运行时必抛 `SecurityException`。实测 44 条 M1 EditMode 测试在该台里 13 通过 / 31 失败，失败全部因为
`new GameObject()`。**这不是回归，是固有边界。**

→ 因此本项目的核心逻辑**刻意分成两层**：纯 C# 静态类（可无头测，秒级迭代）+ MonoBehaviour 薄壳
（只拿引用、驱动、调纯函数）。**写新逻辑时请沿用这个分层**，否则会失去无头测试能力。

### 4.3 图像与观感

- **本会话模型可以消费图像**（2026-09-13 实测：`Read` 一张 PNG 能准确描述内容）。
  历史上"模型无法看图"的结论是错的，见 §9 的勘误。
- 编辑器打开时优先走 **MCP 的 `unity-mcp`**：`manage_camera` 的 `screenshot`
  （`capture_source` 选 `game_view`/`scene_view`、`include_image=true` 返回内联 PNG、`batch=surround/orbit` 多角度）、
  `manage_scene` 的 `scene_view_frame`。这样**不另开 Unity 进程、不抢锁**。
  - ⚠ **bridge 不会在首次打开工程时自启**（这是"编辑器开着但 MCP 报 `No Unity Editor instances found`"的根因，
    2026-09-13 实测查明）：
    - MCP for Unity v10 默认走 **stdio** 传输（ZCode 侧 `mcp-for-unity` 的 `--transport` 默认也是 stdio），
      编辑器侧必须监听本地 socket 才会被发现。
    - 包里负责启动的是 `StdioBridgeHost.StartAutoConnect()`，但 `StdioBridgeHost` 的**静态构造只在类被首次触达时执行**
      ——只打开工程、不打开 MCP 窗口时无人触达它。
    - `StdioBridgeReloadHandler` 的职责只是"domain reload **之后恢复**"（resume），不负责首次启动。
    - `HttpAutoStartHandler` 只管 HTTP 路径（`if (!useHttp) return;`），且要 `EditorPrefs` 的
      `MCPForUnity.AutoStartOnLoad` 为 true（默认关闭）——所以它救不了 stdio。
  - **本项目的处理（已生效并验证）**：`Assets/Editor/McpBridgeKick.cs`（`[InitializeOnLoad]`，反射调用
    `StdioBridgeHost` 以便包缺失时优雅降级）在编辑器加载时自动启动 bridge。
    菜单 `PirateCrew/MCP/启动 stdio Bridge` 可手动重触发；不需要了就删掉该文件（连同 `.meta`）。
  - **生效验证方式**（2026-09-13 实测通过）：`Assets/Editor/McpBridgeKick.cs.meta` 已生成
    + `netstat -ano | grep ":6400"` 显示 `LISTENING` 且 PID 等于 Unity 编辑器进程
    + `manage_scene get_active` 能返回场景。三者齐备即为正常。
  - **若报 no instances**（说明该脚本还没被编辑器导入）：让用户**点一下 Unity 窗口**
    （Auto Refresh 会在重获焦点时导入新脚本）或按 `Ctrl+R`，或打开 **`Window > MCP for Unity`** 手动启动。
    ⚠ 从外部无法强制编辑器刷新——包里**没有 FileSystemWatcher**，没有"投递命令"的通道，
    而唯一能提供进程间通信的东西恰好就是那个没起来的 bridge。所以这一步只能由用户在编辑器里完成。
  - 已实测可用的 MCP 工具（编辑器开着时）：`manage_scene`（get_active/get_hierarchy/load/save）、
    `read_console`、`manage_graphics`（`feature_list` 可列 URP Renderer Feature）、
    `manage_camera` 的 `screenshot`、`execute_menu_item`、`execute_code`、`manage_editor`（play/stop）、

### 4.4 改动 shader 的验证标准（血的教训，别用静态核对代替）

**唯一算数的验证是：图形界面编辑器进 play mode 后 `read_console` 里 0 条 shader error。**
静态核对 `#include` 文件是否存在、`grep` 符号是否定义，**只能证明"符号存在"**，证明不了：

- include 链**自洽**：`GlobalIllumination.hlsl` 里逐个符号都能 grep 到，但它自己的函数体用了
  `BRDF.hlsl` 的 `BRDFData` 而它并不 include `BRDF.hlsl` → 真实编译报 `unrecognized identifier 'BRDFData'`；
- 额外 Pass **会被执行**：URP 的 `DrawObjectsPass` 用固定 ShaderTagId 列表取 pass，**每个 tag 槽位只取一个 pass**。
  描边 Pass 若和本体 Pass 同标 `"LightMode"="UniversalForward"`，会被**静默丢弃**——
  材质正常、本体正常、Console 一点报错都没有，就是没有描边。要加额外 pass 就给它一个独立且未被占用的
  `LightMode`（本项目用 `"SRPDefaultUnlit"`）。

两次事故的完整复盘（含定位手法）在 [描边Shader调试.md](../技术/渲染/描边Shader调试.md) §八，改 shader 前值得先读一遍。

## 6. 关键架构决策与理由（新会话不要重新论证）

记录"为什么"，避免推翻已定的东西：

1. **数值三层**：纯 C# `WeaponCatalog`/`CrewCatalog`/`LevelCatalog`（**真值来源**，可无头测）
   → ScriptableObject 定义类（引擎侧引用与策划调参）→ Editor 生成器 `DataAssetGenerator`（幂等产出 `.asset`）。
   理由：SO 实例化在无头环境必崩，但数值又必须可测；生成器里**不允许**出现第二份数值副本（避免真值分叉）。
2. **纯逻辑 / MonoBehaviour 分层**：见 §4.2。这不是风格偏好，是为了保住无头测试能力。
3. **程序集划分**：`PirateCrew.Gameplay`（玩法）/ `PirateCrew.Tests`（EditMode）/ `PirateCrew.PlayModeTests` /
   `PirateCrew.Rendering`（**独立**，因需引用 URP 程序集）。
   - asmdef 引用**只写 name 或只写 GUID，双写会 duplicate**（M1 踩过）。
   - **Unity 只对名称以 `UnityEngine.` 开头的程序集自动引用**（uGUI 的 `UnityEngine.UI` 因此可用）；
     Cinemachine 这类普通包程序集必须显式写进 `references`——`PirateCrew.Gameplay.asmdef` 已加 `"Cinemachine"`，
     所以相机代码用**强类型** `CinemachineVirtualCamera`，**不要退回反射**。
4. **跨模块通信**：只走 `Core/EventBus` 的字符串事件（snake_case），事件名与载荷必须登记在
   [EventBus事件契约.md](../技术/架构/EventBus事件契约.md)。禁止 `GameObject.Find`、禁止跨模块裸 `GetComponent`。
   同模块内调用、生命周期通知、每帧高频数据**不走** EventBus。
5. **3D 化的四个决策**（写代码注释里已交代，改前先读）：
   - px→单位固定 **1 瓦片 = 1 单位（32px）**，常量集中在 `LevelGeometry`
   - Flash 的 y 轴向下 → Unity y 向上，**显式取负翻转**；注意 `ExplosionResolver.deltaVy` 是 Flash 约定算出的
   - 重力/力度按 `Time.fixedDeltaTime = 1/25` + `Physics.gravity = -19.53125` 配平，使 Flash 的
     `vy += w` 与 PhysX 半隐式欧拉**逐步严格相等**——这是"预览 = 实弹"的根基（Godot 版预览≠实弹是已知教训）
   - 落水即死取**全局规则**（Flash §4.1/§4.3；Godot 版只在单关开启属漂移）
6. **AI 随机数**：自写 xorshift32 而**非** `System.Random`——后者的算法在 .NET 8（验证台）与 Unity Mono 之间
   不同，同 seed 会分叉，会导致确定性测试在两边结果不一致。
7. **AI 的一处显式增强**：Flash §6 打分不含武器伤害，无法满足"能命中时优先高伤害"，故补
   `DamageScoreWeight = 0.5`（设 0 可恢复纯原版，两种模式都有测试）。
8. **弹体程序化构建**：`WeaponProjectile` 默认用图元 + 颜色在运行时造，`projectilePrefab` 为可选覆盖。
   好处是既有场景无需重新装配就能工作（新增必填序列化字段会让场景变成"未接线"）。

### 已定决策（不要重新论证）

1. **三层带是同心环，不是"上下横贯 + 左右补边"**。第一版按后者画，水平带的斜面带顶到左右外缘、
   把两侧外环截断——**四角的轮廓线不闭合**，创始人看图直接指出"4 角不是连着的"。
   改成同心环后固化成判据：外环必须 8 连通为 1 段、且无端点。详见规范 §一.1。
2. **切角按整格切，不按像素切**。按像素切会出 2px→1px 的**离格**台阶（几何上是 45°、在 2px 体系里
   既不平也不斜），读成"角被啃了一口"。判据 `floor(dx/u)+floor(dy/u) < 深度`，默认深度 1 格
   （2px；条状件端头那档是 2 格，方角是 0）。详见规范 §一.2。
3. **色阶要"分得开"，不只是单调**。第一版 `Light` 的中间档与亮档亮度比 0.97、`Danger` 的中间档与
   暗档 0.93——单调性判据放行，但斜面根本读不出来。判据已加"相邻档亮度比 ≤ 0.90"（参照实测 0.55~0.74）。
4. **UI 九宫格件不进像素纹理的约定目录**：域内规则把 `textureType` 定死为 `Default`，
   而九宫格必须是 `Sprite`（否则切片边框消失、UGUI 拿空 sprite、画面退化成白块且控制台不报错）。
   两档共用同一份五项值（`PixelArtTextureRules.ApplySprite`），只在 Sprite 专有项上不同。
5. **按压位移不进贴图**（进了九宫格切片就错位），统一取 `BeveledPixelSpriteBuilder.PressOffset = (1,-1)`。

## §36 3D 像素渲染外部参照调研（六视频 + 两源码 + t3ssel8r 全频道）（2026-09-22）

### 现状一句话

**一条把 v3 定成新渲染管线蓝本的候选路线**"。**观感锚点尚未裁决**：创始人已表态「最喜欢 V3 的观感」，

### 本轮提交索引

| 提交 | 内容 |

### 已定决策（不要重新论证）

1. **v2 / v3 / v5 不是同一个算法**，要拆两条线看：
   - **描边这条线**：v2、v3 同族（**屏幕空间**）——v2 判据是"原始深度差 + 邻域法线点积过阈值"，
     v3 判据是"**连通域**（用法线预测深度看残差，跨 `step` 走）+ 1px 膨胀 + 优先级仲裁"，后者更强。
   - **边缘光/内线这条线**：v3 与 v5 同族（**不在描边 pass 里做**）——v3 是"色带在连通域断开处降一档"
     加"边缘光门控在连通域上"；v5 是"改明暗"。v2 没涉及。
2. **v3 那支视频不是讲描边**。它的 Cast Renderer 资产里 `SloanePixelartOutlineRendererFeature` 与
   `Debug` 都是 **`m_Active: 0`（关闭）**；简介只提"叠了个边缘光 + 在法线变化剧烈的地方把光照放暗一级
   + 微弱的抖动"。所以画面上的线 = `RimLightShading()`（边缘光，屏幕空间光向门控、只在朝光侧亮起）
   ＋ `DiffuseShading()` 里 `if (ndotl > singleLevel && connect < _ConnectivityAntialiasingThreshold)
   ndotl -= applyAA * singleLevel`（**连通域断开处压暗一档**）两件的合成——**方向随光而变**，
   这正好解释"柱子是亮边、石阶是暗线"。**别再把它当描边方案引用。**
3. **"v5 在材质/物体层"这条结论作废**（作者原话推翻，第三轮才收敛）：t3ssel8r 的边缘高光/阴影是
   **"the depth buffer is sampled for adjacent points, and the pixel is brightened or dimmed based on
   whether it is closer or further to the camera than its neighbors"**——**屏幕空间信息**，
   载体是物体着色器（`Pixel Art Block Shader`），**后又被重写为 normal pass**
   （"much more reliable at producing clean results"）。**不要再用抽帧推断 v5。**
4. **v4 的抖动贴图实测是标准 2×2 Bayer `{0, 0.25, 0.5, 0.75}`，且未做中点归一化**；而它的
   soft-light 以 **0.5 为恒等点**，取值均值 0.375 ⇒ **整幅画面被系统性压暗**。**本仓现行
   `(m+0.5)/16` 是对的，不要照抄 v4。**（此条为第一手实测：两张 `dithstyle.png` 已解码逐像素核对）
5. **v1 的色彩空间口径**：**旁白与官方英文字幕是 CIE Lab**（"OKLab" 在字幕里零出现），
   **只有简介文案写 OKLab**。本仓取 **OKLab**（理由与公式见文档 §4.5）。
6. **相机口径统一（2026-09-22 创始人确认）：俯角真等距 35.264° + 方位角固定 45°**。
   待办里原有"方位可旋转（创始人修正）"一条与渲染篇 §2、立项任务书**三处冲突**，已按**固定**改，
   右键环绕退役、观察模式保留为调试出口。
7. **v3 的架构可以整体作为新渲染管线蓝本**（我上两轮的反对已自我推翻，别再重复那套论证）：
   - 反对①"相机是玩法与场景流转的一部分"**不成立**——v3 的 Cast Camera 是
     `SetParent(transform, false)` 建的**主相机子物体、local 恒等**，主相机被 Cinemachine 照常驱动、
     白搭一个渲染代理；`m_ThisCamera` 只是被清掉 `cullingMask` 与远裁面，退化成"纯变换持有者 + 把结果
     blit 上屏"。**换架构不需要重接 Cinemachine。**
   - 反对②"整套材质重写"**不算成本**——它本来就在美术翻新立项的范围内。
   - 反对③"降采完就是最终画面"**正是要改的东西**，不是理由。
   - 剩下只有三条**非技术**约束：**(a)** 先定观感再定架构（架构是为观感服务的）；**(b)** v3 的相机
     snap **只做了一半**（`BeforeRendering` 里把视图矩阵平移分量 `viewMatrix.m03/m13` 四舍五入到
     `unitSize` 整数倍再全局下发——好处是**不动物体相机 Transform**，正好绕开风险 R6"Cinemachine 与
     像素完美打架"；但**我没找到"把 snap 残差转成 UV 偏移补偿回平滑移动"的那一半**，本仓两步法是裁决
     要做的，照搬要自己补）；**(c)** 本仓参照库纪律要求"**读懂核心实现后基于参照翻译改编**"、
     "**参照库不入库**"——**源码级翻译改编，不要 vendor 整包**。
8. 本仓"全分辨率渲染 → point 降采"与 v3 的"5× 超采样 → 点采样降采"**是同一种形状**
   （v3 的降采样 compute 就是取每块中心点；那个 `DownSamplingAA` 变体是**没写完的 stub**——
   只有 `_DiffThreshold`/`MinCount` 声明、函数体是空的，**所以它的干净不来自超采样**）。
   真正差别在**降采之后**：v3 在目标分辨率上还跑 Priority / Connectivity / Shading 半个管线。

### 本轮读出来的硬事实（**不要重新论证**）

1. **v3 与本仓的真分野 = "着色发生在哪一档分辨率"**，不是"用哪个 shader"：
   本仓是**全分辨率前向着色 + 事后降采**（降采完就是最终画面，没有第二次着色机会）；
   v3 是**物体 pass 只写 G-buffer（7 张 MRT @1600×900）、不做任何着色**，全部着色与后处理**在 320×180 域上**跑。
   ⇒ 渲染篇 §3.1 推论 4 说的"几何直接渲进 RT"只覆盖这条改动的**一半**（省 fill rate），另一半是"低分辨率域上的着色"。
2. **双相机结构不需要重接 Cinemachine**（§36 已定，这里补上机制）：Cast 相机是主相机**子物体、local 恒等**
   （`SloanePixelartCamera.cs:283-285`），主相机被清掉 `cullingMask`/远裁面后退化成"变换持有者 + 上屏 blit"。
3. **真实执行次序**：`BeforeRendering`(BeforeRender) → `BeforeRenderingPostProcessing`(BeforeShading 清 4 张着色缓冲) →
   `AfterRendering` 九特征**按 asset 数组顺序**：RenderOpaqueObject → Connectivity → Priority → Shading(5 子 pass) → Combine → **Outline(关)** → **Debug(关)** → ColorCorrection。
   完整表见蓝图 §1.3。
4. **v3 里其实没在跑的东西（四条源码实证，别再当观感来源）**：
   - **`PriorityManagement` 是死 pass**：① 连着两次 `SetTargetBuffer`，后者覆盖（`ComputeShaderPass.SetTargetBuffer` 是覆盖语义）；
     ② kernel 写 `RWTexture2D _UVBuffer` 但**全仓没有一处绑它**；③ 目标换成 1600×900 后 `id.xy * _SamplingScale` 读越界。
     ⇒ UV 缓冲保持 BeforeRender 清的灰色 ⇒ `GET_UV_WITH_PRIORITY` 位移恒为 0 ⇒ **优先级仲裁对它画面的贡献是 0**。
   - **`SloanePixelartDownSampling.compute` 与 `KuwaharaFilter.compute` 是孤儿**（GUID 在 assets/scenes/prefabs/cs 里零引用），
     且前者 AA 分支是空壳、后者四向不对称。
   - **`Outline` 与 `Debug` 特征 `m_Active: 0`**（Outline 的 shader 源码是完整的，移植内线时是一手材料）。
   - **第 8 个 MRT 输出（lightmap UV）没有绑定目标**：`m_OpaqueBuffersIdentifiers` 长度只有 7（缓冲 1..7），
     而片元有 8 个输出；`TargetBuffer` 枚举里根本没有 LightmapUV 成员 ⇒ `_LightmapUVBuffer` 永不绑定 ⇒ GI 实际只走 SH。
5. **v3 的 5× 超采样不是画质手段**：降采就一句 `_Target[id.xy] = _Source[id.xy*scale + scale/2]`（**点采样、无 box 平均**）。
   超采样的真实用途是**给连通域判据提供"单元内 5×5 的细粒度深度/法线"**（判据要跨 `step` 走中间像素）。
   ⇒ 这直接决定本仓的超采样档要不要保留（蓝图 §7.2 第 2 条）。
6. **v3 的上屏 blit 不随屏幕宽高比**（ResultBuffer 固定 320×180，全仓没有一处设 `Camera.aspect`/`rect`）⇒ 非 16:9 会拉伸。
   **本仓 `PixelationRendererFeature` 的"高锁 360、宽随宽高比、偶数对齐"更对，要保留**。
7. **v3 两处真 bug（照搬会继承）**：① `ReleaseBuffers` 里 `m_TargetBuffers = null;` 写在 `foreach` **循环体内**
   （`SloanePixelartCamera.cs:127-131`）⇒ 只有第 1 张被释放，**其余 14 张每次 `GetBuffers()` 全泄漏**（挂在 `OnValidate` 上）；
   ② 边缘光抑制 AA 处 `if(rimLightInfo.r > 0 || g > 0 || g > 0)` —— **`g` 判两次、`b` 一次没判**
   （`ShadingPass.hlsl:93` 与 `:222`），纯蓝边缘光不会抑制降档。
8. **画面上的"柱亮边 / 石阶暗线"的源码机制**（§36 只定了"不是描边"，这里补机制）：
   `RimLightShading()`（屏幕空间光向 × 连通域四方向门控，`RimLight.hlsl:16-20`）＋ `DiffuseShading()` 里
   `if(ndotl > singleLevel && connect < 0.75) ndotl -= applyAA * singleLevel`（**连通域降一档**）两件合成 ⇒ **方向随光而变**。

1. **构建会剥离"只被 `Shader.Find` 引用的 shader"**——构建日志里既无编译记录也无报错，
   运行时 `Shader.Find` 返回 null，画面只剩背景色。⇒ 着色 shader 必须由 Feature 的序列化字段持有。
2. **Cast 相机的层掩码不能跟主相机同步**（主相机被清成 0）——否则物体 pass 的 `cullResults` 为空、
   什么都不画且不报错。
3. **抖动幅度必须在物体 pass 施加**（着色 pass 只读偏移量）——漏了就是"关着也有规律点阵"。
4. **判据的块边长不能用"最小 lag 平移相等"**（大面积平涂图会误判成 2）：要用"行内最短同色段"，
   并且必须排除底部开发版水印那条抗锯齿带。
5. **同一 `RenderPassEvent` 内，特征数组顺序 = 执行顺序**——装配器每次重建列表，不让历史残留改掉次序。
6. **两范式抖动的性质差别已被量化**（实测 1920 PNG，RT 高 180）：
   Bayer 4×4 幅度 0.5 → 跳变率 0.25（渐变态）；v3 1-bit 密度图案幅度 0.5 → 0.92、1.0 → 1.00（两态撕边）。
   这是"选哪种抖动"第一次有数可依。
7. **三档 RT 高的宽度自适应都对**：高 180/360/90 → 宽 320/640/160（块 6/3/12），
   即"高锁档、宽随宽高比、偶数对齐"这套本仓口径已在实拍上验证。
8. **无抖动时低分辨率域是纯平涂**：平坦占比 0.93~0.98、跳变率 0.01~0.03 ⇒
   色带边界天然落在低分辨率像素上，不再需要"逐像素操作与 RT 块对齐"那条旧纪律。

## §40 像素化路径 r4 修正轮（2026-09-22）（3D 渲染线）

> **这一轮干了什么**：创始人看 r3 出图后逐条驳回——"没光影 / 只有上描边 / 角色是胶囊不是台柱 /

> 本轮把**根因**找出来修掉、把描边**按方案还原**，出图色号已与解析式逐位对上。

### 1. 根因：一条通道一肩挑两职，整屏旁路光照

`PixelartObject.shader` 的 `prop.a` 同时是"着色 pass 判定这是墨线像素"的标记
**和**物体 pass 写出的 `_AAScale` 占位属性，而 `_AAScale` 的 Properties 默认值恰好是 **1.0**
⇒ **每一个不透明像素**都满足"prop.a > 0.5 ⇒ 原样输出 albedo、跳过全部着色数学"。
症状：所有面同色、色号与 albedo 十六进制逐位相同、没有任何光影、**没有任何报错**，
旧的四项判据（块边长/色数/平坦度）全部照过。

对策：删除 `_AAScale`，通道语义改成**排他**（只有墨线 pass 写 1）；判据新增
**判据五「亮暗跨度」**= `(最亮−最暗)/最亮`（只统计占比 ≥0.5% 的大色块、剔除近黑墨线）。
两轮实测：**正常 0.76~0.80 / 事故 0.46**，阈值 0.60。用 p4 的旧 PNG 回放验证过：事故轮每一张都 FAIL。

### 2. 描边：撤销我自造的屏幕空间方案，按渲染篇 §5 还原反向壳

创始人指出"你不应该着重参照我给你的 V3 技术方案吗"。回查蓝本与渲染篇，两处原文：

- 渲染篇 §5 第 103 行：**不用屏幕空间边缘检测**（正交下反向壳线宽天然恒定、内缘不出杂线）。
- 蓝本 §8 裁决点 3 推荐：**外轮廓 = 反向壳 + 内部转折 = 连通域降档**，两者正交可并存。
- （v3 自己的 `OutlinePass.hlsl` 确实是屏幕空间 4 邻域膨胀，但它在 v3 里**是关着的**——蓝本 §4.3，
  且门控依赖 P4 才有的连通域结果；`external/sloane-urp` 里有源码可复核。）

于是按渲染篇 §5 的六轮实拍配方重写，**三条因果链缺一条描边就断**（都写进了代码注释）：

| # | 做法 | 缺了会怎样 |
| --- | --- | --- |
| ① | 大平面（地面）`renderQueue = 1999`，Feature 按队列分段**先把它整体画完** | 它 `ZWrite On` 的本体会把壳环整圈盖掉 |

## §41 像素化路径 r5（2026-09-22 晚）：像素网格锁整数倍 + 描边闭合 + 角色真正站住

> 创始人连续三轮现场反馈（"全屏像素不齐/放大看却正常"、"下边缘为什么还是没有描边"、
> "球头上为什么还有平板、身体为什么不是台柱"）三条都成立。本轮逐条查机制并修掉，
> 顺带挖出两个**"编辑器里对、播放器里错"**的坑。归档 [r5](../images/pixelart-path/r5/README.md)。

### 1. 像素口径：**锁"放大倍数"**，不锁"画布高度"（创始人裁决）

旧口径"锁 RT 高 216、宽随宽高比"只在**屏幕高是 216 的整数倍**时成立：1920×1080 ✓，
但 2560×1440 → 2560÷384 = **6.67（非整数）**、1366×768 → 3.56 ⇒ 块边长在 6/7 之间混排
= "全屏像素不齐、放大到 1:1 看却正常"。现在锁 **`pixelScale = 5`**（一个艺术像素占 5 屏幕像素），
RT 由实际屏幕反推：1080p → 384×216、1440p → 512×288、4K → 768×432，块恒为 5。
另加 **`worldPerPixel`**（每艺术像素多少米）：**分辨率越高可见范围越大**（1080p 28m、1440p 37m）。
播放器日志会打一行"像素网格：屏幕 … → 放大 5× → 艺术画布 …（整数映射是否严格）"，残余像素会报警。

### 2. 描边下缘：实测 97% vs 0%，改 `ZTest Always` 闭合

程序化判据（沿平台剪影逐列扫近黑像素）：`ZTest LEqual` + 拉近 5×（渲染篇 §5 原配方）下，
上缘有墨线的列 98%、**下缘 0%**；改 `ZTest Always` 后下缘 48%、墨线像素总数 1.18 万 → 2.33 万。
机制：深度测试的对手是**先画完的地面**，而壳在下缘那圈投射的深度是物体的**背面**（18m 见方的台面
背面深达十几米，0.65m 的拉近杯水车薪）；而深度测试对本路径本就多余——墨线画在本体之前、
本体随后盖回重叠区 ⇒ 关掉它即闭合。**代价**：相邻物体互相漏线（旧链也记过同一条）。
另：外扩方向**必须归一化**，否则朝屏的面外扩不足 1 像素、整圈被光栅化吃掉。

### 3. 角色造型：照本仓既有裁决，不再手搓

`CrewVisualPrefabBuilder`（用户裁决 2026-09-14）写着**两件式 = 圆球 + 圆台柱**，
三角帽/头巾/腿/靴/臂**全部删除**。我此前手搓的"两块方块 + 一块帽檐平板"两处都错。
现改为**实例化 `Sailor.prefab` 只换材质**：Body 圆台柱（顶 r 0.35 / 底 r 0.40 / h 1.20 / 16 段）、
Head 圆球（r 0.35，球心在柱顶上方）、总高 1.85m。

### 4. 两个"编辑器里对、播放器里错"的坑（都无报错）

| 坑 | 症状 | 机制 | 修法 |
| --- | --- | --- | --- |
| 船员根上的 **Rigidbody** 没剥掉 | 编辑器里包围盒完全正确，播放器里角色比场景低 **11.441m**、被地面挡住看不见 | 编辑态不跑物理；播放器里自由落体，采集在载入后约 1.5 秒 ⇒ ½·9.81·1.5² ≈ 11m | 先 `UnpackPrefabInstance(Completely)` 解包，再按**白名单**剥组件（只留 Transform/MeshFilter/MeshRenderer），**当场断言无残留**。实测：预制体实例上 `DestroyImmediate` 删不掉 `Rigidbody` 与 `PirateBase` |
| 落点埋进台体 | 蓝船员"只剩上半身" | (-7.5, 0, 6) 在 step1 的 ±9 足迹**之内** ⇒ 埋进 0.5m 台体 | 地面件一律 |x| 或 |z| > 足迹；装配期跑**落点不变式** |

> 这两个坑正是创始人两次用不同措辞报的同一件事（"角色和场景比太小" / "平底的角色站到地面**和内容**了"）。

### 5. 新增：管线调试档（`_PixelartDebugMode`）

着色 shader 加 0=正常 / 1=albedo / 2=法线 / 3=逐物体参数 四档，出图脚本加了 `dbg-*` 三张。
**排查纪律**：`dbg-*` 是中间缓冲的直接视图（平涂、无光照、无内部色带**是设计如此**），
`pa-*` 才是最终出图——别看错图。判据脚本对 `dbg-*` 只判块边长。

### 6. 归档格式改了：原生 PNG（不再压 1280 宽 JPEG）

把 1920 宽的像素图缩到 1280 宽（因数 3.33，**非整数**）会当场打乱块边长——"全屏像素不齐"
有一半来自这里。像素图归档的缩放因子必须是整数；原生 PNG 既精确又更小（单张 37~57KB）。

### 7. 遗留

1. **相邻物体互相漏线**（角色↔台面接触圈）与左立柱左缘一小块 2 像素杂物：同源于反向壳的
   "相邻物体"限制，需 Stencil/分层方案。
2. 暗部色口径（v3 纯乘暗 vs 渲染篇 §4.2 替换式暗部色）与描边线宽：仍待裁决（[r4 README §7](../images/pixelart-path/r4/README.md)）。
3. 云彩关接入 + 固定视角 + 直入画面：等"直入"形态确认。

### 8. 出包/采集的操作坑（本轮又踩两次）

**每次 batchmode 跑完可能留下僵尸 Unity 进程**（日志里是 `abort_threads: Failed aborting`），
下一次运行会直接 `Fatal Error! 似乎有另一个正在运行的 Unity 实例打开了此项目` 且**退出码仍是 0**、
日志里没有 BuildReport——看起来"构建成功但产物没更新"。⇒ **每次 Unity 调用前先
`taskkill //F //IM Unity.exe //T`**，并核对构建日志里有没有 `result=Succeeded`。
**不要手删 `Temp/UnityLockfile`**（本轮删过后遇到一次 Mono 在 ReloadAssembly 阶段直接死掉）。

## §42 像素化路径 r6（2026-09-22 深夜）：**逐物体独立描边**

> 创始人：「为什么每个物体没有单独描边，我给你的 V3 也不是只有一个单一描边的啊，
> 角色自己的描边和场景描边应该是独立的啊」。这是架构问题（绘制粒度），本轮解决。

**病灶**：绘制是"所有壳画完 → 所有本体画完"⇒ 任何环都被随后画的本体盖掉 ⇒ 全场景只剩最外一圈。

**修法（四件必须成对）**：
1. **逐物体提交**：放弃 `DrawRenderers`（按 tag 分批），改为自己收集 renderer + 逐物体
   `CommandBuffer.DrawRenderer`，两条 pass 的索引**按 pass 名解析**（`FindPass("PixelartOpaque"/"PixelartInk")`，
   不写死序号）。
2. **远 → 近**排序。
3. 每个物体**壳先画、本体后画**（近物的本体把覆盖处远物的环盖掉 = 正确遮挡）。
4. 壳 **`ZTest Always` + `ZWrite Off`**（用 LEqual 时环跟"先画完的大平面"抢深度，
   近侧下缘覆盖实测 **0%**）。

实测：墨线像素 **13150 → 51225**；三级台面各有闭合环、立柱/木箱/角色各自成环。
**代价**：自己排绕开引擎裁剪（本路径几十个物可忽略；接真实内容后若成瓶颈改用 `CullingResults` 可见列表）。

**顺带**：`_PixelartInkDepthPull` 参数化且**每帧下发**（`ZTest Always` 后已非必需，留作对照档）——
上一版放在"尺寸变化时才下发"的位置，出图脚本逐档改它不生效（两个档出图完全相同，踩过）。

**角色"没台柱感 / 太矮"的量**：中机位下角色只有 **15 低分辨率像素高**（近机位 36），
模型 12% 的锥度折算 **≈1.1 像素** ⇒ 读不出来。是**取景比例**问题，不是渲染问题。
两条路（都要创始人拍）：取景更近 / 加大模型锥度（后者是改 2026-09-14 的船员裁决，须先提案）。

归档 [r6](../images/pixelart-path/r6/README.md)。判据五项全绿。

② **batchmode Unity 关停挂死**：邻居会话那个进程在 `Batchmode quit successfully invoked` 之后
持续吃满 CPU 十几分钟、一直持着 `Library` 锁，只能强杀——判据是"日志已确认工作写完 + 进程仍活且吃 CPU"。

**下一位接手的第一件事**（优先级从高到低）：① 帧级调色板 LUT 索引口径（仍默认关）；
② 实时阴影调参（仍默认关，云场那边"船员贴在云上"的观感偏弱就是这个缺口）；
③ 把本路径接进**真正的 Battle 关卡 1**（本路径要求场景里每个 renderer 都是本路径物体 shader，
海面 rig / FX / HUD 逐个换材质是那一轮的活）；④ 描边闭合率判据按深度/法线不连续重写。

## §46 像素化路径 r12（2026-09-22）：中机位 14 m + 游戏内俯角固定 30°（3D 渲染线）

**创始人当轮原话**：「比当前的 mid 略微近一点的距离最好，要不我在游戏内调整一个我看着最顺眼的距离当做基准，

1. **取景**：中机位 16 → **14 m**（十关同一组数）。14 不是随手取的：游戏内滚轮是整数档 OrthoSize、
   可见高度 = 2 × OrthoSize，所以游戏内能滚到的只有偶数米，**14 m = 正交档 7**——图与游戏内是同一个档。
   为此 HUD 提示条加了镜头档读数 `BattleCameraController.RuntimeVisibleMeters`（"镜头 N m"），
   创始人可以在游戏里滚到顺眼的那一档、念出米数，取景表照改（这是**临时调参读数**，基准定下后可删）。
2. **游戏内俯角 30°**：`BattleCameraController.OrthoPitchDegrees` 由真等距 35.264° → **30°**，
   且**取值直接引用出图口径 `PixelartPilotScene.PitchDegrees`**（出图与游戏内必须同一个投影，
   否则"拿宣传图比观感"本身不成立）。方位角改为**可自由旋转**（右键环绕是现役玩法，俯角无输入路径）；
   已知取舍：只有方位 45° 及其对称位给出斜率相等的对称菱形，别的方位下地面阶梯长短不一，不做 snap。
   Battle 场景烘焙机位（FollowOffset ≈ (18.371, 15, 18.371)）走 `BattleScenePipeline` 重烘；
   装配器不再自带一份俯角公式（改用 `OffsetDirectionForPitch`），`CameraFeelRulesTests` /
   `BattleSceneWiringTests` 断言改写。**35.264° 那条旧裁决整条作废。**

**验证**：EditMode 1307 / 失败 0，PlayMode 7 / 失败 0；dev 出包 + 十关重拍，判据全绿；
L01/L03 的 wide/close 两档与 r10 逐像素**差异 0.000%**（证明渲染没变，中机位差异只能归给取景）。

**两条踩坑记录**：

- 装配链 `BattleSceneSetup.RegisterBuildSettings()` 会把 `EditorBuildSettings.asset` 从 17 个场景
  覆盖成 3 个（入口/主菜单/战斗）——**只重跑 Battle 子链也会踩**（本轮实测）。跑完必须查一遍再提交。

  （34434 → 35928），跳的是那条读数按颜色猜出来的**分母**。该读数在脚本里本来就只报不判。

## §43 凹槽语法收口 + 组件总表重排 + 出图改名（2026-09-22 收尾后走查）

> 创始人第五轮走查三问："凹槽 Track 怎么画风和别的不一样？""为什么是 1× 的图？"
> "这图一个个的元素都偏到姥姥家了"。

### 1. 凹槽 Track 补上全家共有的近黑描边（**规则 0**）

- 症状：同一屏里面板近黑收边、条槽**彩色顶到最外缘**，整排凹槽读成"另一种画风"。根因是
  §一 的两套语法各自量自两张参照图，条槽那套当年没把参照条的**最外圈深近黑**量进来。
- 改法：条槽变**五段** —— `INK 描边 / 外环(S2·S1) / 斜面(S4·S3) / 内暗线(S2·S1) / 槽底(Floor)`，
  仍装在 `PlateBorder = 4u` 里（第 5 段落在拉伸区）。受光侧的"亮"由**填充条自带的上亮沿**承担。
- 判据：契约测试逐张查条槽最外 1u 四边都近黑（`Lum < 0.25×255`），并把"上内暗线 = 上外环"
  的取样层从 `h-1-2u` 改到 `h-1-3u`（差一层就红）。
- 顺带修 `DrawTrackFill` 的填充边距：原 `3u`（= 1 艺术像素，填充盖住整个框）→ **6 艺术像素**
  （= 令牌表里那条"框"），与 showcase 的血条口径一致。

### 2. 组件总表重排（`BuildComponentSheet` 重写）

- **一件一行 + 左列行名，行名与行垂直居中**；行高/间隙全部取自令牌表（行高 = 件高，间隙 14/28）。
  第一版的毛病是行名贴行的上边缘（视觉上"飘"）、各段行距手算、末段还与页签叠在一起。
- **布局走一条自顶向下的游标**，画布高度**按游标实算后裁**（`planHeight` 是上限，超了直接抛）。
  踩过的坑：布局写"距顶"、画布存"距底"，裁的必须是画布**末尾** cursor 行——第一版从 0 起裁，

### 1. 状态可读性（悬停 / 按压）——回答"行业最佳实践真是这样吗"

像素 UI 的通行做法（Terraria / Enter the Gungeon 一类）：**悬停 = 整块提亮一档、按压 = 整块
沉一档 + 高光移到对侧 + 内容右下沉 1 个艺术像素**；都不用渐变/发光。本仓原实现只做了
"对调 + 上抬 25%"，实际只有 1px 唇边在变，确实低于通行可见度。修正：
- `HoverLift` 0.25 → **0.5**（整条色阶抬半档，一眼可辨）；
- 按压在对调之外加 **`Ramp.Sunk(0.5)`**（每档向暗侧邻档混半档，`Floor` 沉向墨色）——
  对调保几何、下沉保可见，锁板判据按状态取表（常态 / 悬停 / 按压三张锁板表）；
- `PixelSkin.PressOffset` (1,-1) → **(3,-3)**：原值只有 1 屏幕像素，比一个艺术像素还小，
  既看不出沉、又把件挪出了像素栅格。

### 2. 页签缝隙——"页签是一条带，不是各自的小牌"

- 组件总表：页签改**等宽相邻零间隙**，且整体**压进宿主描边 2 艺术像素**（页签底边无带，
  盖住宿主的墨色描边后脸贴脸）。
- 运行时 `SketchWidgets.Tabs`：原来 `tabWidth - 6` 留了 6px 缝，改**零间隙**
  （相邻两道描边贴在一起正好读成分隔线）。

### 3. 盖章文字"上下不等距"——墨迹居中

像素字体的 ascent/descent 不对称，盖章脚本原先按**左上锚**放字 → 按钮字贴上边。
改为按 `font.getbbox` 的**实际墨迹**居中进行盒（清单 y = 行盒顶，盒高 = 字号），
实测按钮字上留 16 / 下留 17 屏幕像素（1px 差是字形自身的墨迹不对称）。

### 4. 实机调试窗口（UIShowcase.unity）——两版迭代

- 第一版直接复用采集链路的旧陈列页，被创始人当场打回：**字体是手写体、尺寸不在 3:1 栅格上、
  展示的还是手绘皮组件**——"图上 promise 的东西没兑现"。
- 定稿：`PixelShowcasePage`（运行时真件页）——**逐行镜像组件总表**（面板 7 tone × 三态 /
  凹槽真实用法 / 填充 5 色 / 语义件 / 页签 / 三态按钮），全部矩形与字号落在艺术像素栅格
  （坐标尺寸 = 艺术像素 × 3），纵向 ScrollRect + 像素滚动条（对齐 game-2 版式），
  按钮页签全部真件可点。`UiShowcaseBoot` 只管 Canvas + 滚动 + 返回总览。
- 场景 `Assets/Scenes/UIShowcase.unity`（相机 + 引导件，内容运行时自建、刻意不折叠），
  由 `UiShowcaseSceneSetup` 构建/登记 Build Settings；菜单 **PirateCrew/UI/打开组件展示（构建并播放）**
  一步进实机；命令行出口 `CaptureFromCommandLine`（必须带图形跑）自动出
  `export/ui-pixel-4a/showcase-live.png`。状态机踩坑：进 Play 触发 domain reload 会把
  `EditorApplication.update` 订阅和闭包清掉——状态放 `SessionState` + `InitializeOnLoadMethod` 重挂。

### 5. 像素字体落地（本轮真正入库）

- `FusionPixel12-zh_hans.ttf` + OFL 入 `Assets/Art/Fonts/`；
- `FontAssetBuilder` 加**位图口径档**：采样 12 / RASTER_HINTED（不走 SDFAA）/ padding 0 /

  缺字 fallback → 楷体正文；

- 已接入：组件展示实机窗口整页 + 返回总览钮。**全局切换**（`UiKit.RuntimeFont` 三档 +
