# M2-3D 空间模型对齐（Unity ← Godot 3D 基准）

> **这份文档解决什么问题**：Unity 版第一版把 Flash 原版的 2D 侧视坐标 1:1 搬进了 Unity 的 XY 平面，
> 并用正交相机 + `FreezePositionZ` 把深度锁死，结果是"披着 3D 引擎的 2D 游戏"。
> 而 Godot 版（本项目的设计参照）是**真 3D**：XZ 地面竞技场、45° 三维相机、单位沿 Z 分路。
> 本文定义对齐后的坐标/运动学契约，**改这些常量与换算前必读**。
>
> 两个基准的分工（不要混）：
> - **Godot 版 → 空间结构、相机、场景布置、单位分路**（本文主要来源）
> - **Flash 逆向文档 → 数值、公式、回合规则、武器表**（`docs/技术/参考逆向/参考游戏逆向-海盗军团抢宝藏-静态.md`）
>
> ⚠ 为什么不照抄 Godot 版的数值：它的弹道/伤害层是**占位实现**，自身不自洽——
> 预览 `throw_dir = dir + UP*0.7`、`speed_scale = 18`、`gravity = -18`，实弹却是
> `velocity = dir * power / weight`（少一个 ×18）、`_THROWN_GRAVITY = -9.8`；
> `DamageCalculator` 用的是凭空造的 `20m / 0.02` 常数，与 Flash 的爆炸公式无关。
> 照抄会把"预览≠实弹"这个 Godot 版已知漂移一起搬进来，而 Unity 版已经用
> "预览与实弹共用同一份 `Ballistics` 输出 + 同一 dt/重力"修掉了它——这条不变量必须保住。

---

## 1. 坐标系（本文档是权威）

```
世界 X = 竞技场横向      ← Flash 的 px（瓦片格 gridX）
世界 Z = 竞技场纵深      ← Flash 的 py（瓦片格 gridY；原 2D 侧视的"竖直"轴 → 3D 的"纵深"轴）
世界 Y = 高度（向上为正） ← 原 Flash 的"重力方向"；地面顶面 y = 0，水面 y = -0.4（`LevelGeometry.WaterSurfaceY` 现行值；本文早期版本写 -0.2 已过时）
```

**要点**：

- 竞技场是 **XZ 水平面**（不是 XY 竖直面）；重力沿 **-Y**。
- Flash 的 2D 关卡被当作**平面图**重新投影：`(gridX, gridY) → (X, Z)`。
  原来表示"平台高度"的 gridY，现在表示"纵深位置"。因此 Flash 的
  `waterTileY` **不再参与映射**（见 §4 水域）。
- **1 瓦片 = 2 世界单位 = 32px**（现行 `LevelGeometry.TileWorldSize = 2`；本文早期"1 瓦片 = 1 单位"口径已过时——M2 落地时为对齐竞技场跨度放大了格距）。
- **y 轴不再取负**：Flash 的 py 直接成为 +Z。理由：侧视图里"越往下"= 越靠近观众；
  在平面图里"越靠近观众"= +Z（相机在 +Z 侧），方向天然一致，无需翻转。
- 单位枢轴（pivot）离地 `UnitPivotHeight = PixelsToUnits(16 - bottomExtent) = 8/32 = 0.25`，
  即脚底贴 y = 0、枢轴在 y = 0.25。这与 Flash `py = (gridY+0.5)*32 + 16 - bottomExtent`
  中那 8px 偏移是同一个量，只是从"屏幕高度"变成"世界高度"。

## 2. 竞技场与相机（对齐 Godot `battle.tscn` / `orbit_camera.gd`）

| 元素 | Godot 基准 | Unity 目标 |
| --- | --- | --- |
| 地面 | `PlaneMesh(50,50)` + `BoxShape3D(50,0.2,50)`，沙色 | XZ 平面，尺寸 = 关卡 `widthTiles × heightTiles`，顶面 y = 0 |
| 水面 | `PlaneMesh(100,100)`，y = -0.1，无碰撞 | XZ 平面，y = -0.4（现行 `WaterSurfaceY`），比地面外扩一圈，无碰撞 |
| 相机 | `Camera3D` 透视，`pitch = 45°`、`distance = 18`、`yaw = 0`（可右键环绕 + 滚轮缩放） | **正交相机**：俯角**固定 30°**、方位角**可自由旋转**（2026-09-22 创始人裁决；透视 45°/distance 15 为历史值）、OrthoSize 整数档（特写 5/全场 17/全景 `span×0.3`，滚轮 [3,60]）、Transposer 距离恒 30、平滑跟随焦点；拖拽映射仍走相机基向量（§3），故坐标/弹道/拾取链路与 yaw 取值无关 |
| 光照 | `DirectionalLight3D` 斜射 + `shadow_enabled` | 平行光斜射 + 软阴影 |
| 环境 | `WorldEnvironment`：procedural sky、`ambient_light_source = Sky`、`glow_enabled` | 天空盒 + 环境光（URP Volume 的 Bloom 可选） |
| 单位分路 | 每队 3 人，x 相同、z = 0 / ±4 | **不再固定三路**：沿用在 Flash 关卡数据里作者写好的 `gridY`（即 Z），保留关卡内容 |

> **关于"每队三路"**：Godot 的 `battle.tscn` 是**手工测试场景**（3v3 硬摆），不是关卡管线
> （它的 `island_generator.gd` 只有 20 行、是桩）。所以 Unity 侧不硬编码三路，
> 而是把 Flash 关卡的 33 关坐标（已转写在 `LevelCatalog`）当作平面图投影到 XZ，
> 这样既得到真 3D 的纵深散布，又保住了作者写好的关卡内容。

## 3. 投掷与瞄准（对齐空间结构，数值取 Flash）

- **方向**：屏幕拖拽 `(dx, dy)` → 世界水平方向。
  Godot 硬编码为 `Vector3(-dx, 0, -dy)`；Unity 改成**用相机基向量投影**：
  `horiz = camRight.xz * (-dx) + camForward.xz * (-dy)` 再归一化。
  这样 yaw 变化（相机绕转）时映射仍然正确——Godot 那套硬编码在环绕后会失真，是它的潜在缺陷。
- **力度/初速大小**：仍用 Flash 的 `Ballistics.TwangVelocity`（`0.25 × 拖拽距离`、`twangMax` 等比限速），
  取其输出**模长**作为速度大小 `s`（px/帧）。
- **抬升**：`throwDir = normalize(horiz + UP * ThrowLift)`，`ThrowLift = 0.7`；
  最终速度 `v_world = s * FlashSpeedScale * throwDir`。
  （Godot 预览用 0.7、实弹用 0.8，此处统一取 **0.7 单一常量**，以满足"预览 = 实弹"。）
  速度**大小**由 Flash 的 `twangMax` 决定，抬升只决定仰角——这样限速语义不被破坏。
- **重力**：仍沿 -Y，`Physics.gravity = WorldGravity(1) = (0, -19.53125, 0)`，
  `Time.fixedDeltaTime = 1/25`。这条让 PhysX 半隐式欧拉与 Flash 的 `vy += w; y += vy` 逐步等价，
  是"预览 = 实弹"的根基，**不动**。
- **"预览 = 实弹"这条不变量的载体变了（重要）**：2D 时代它靠"预览调用同一份平面 `Ballistics.PredictTrajectory`"
  成立；3D 化后重力与水平面正交，平面内变成匀速，平面那份 `vy += w` 的积分**不再描述实弹**，
  所以不变量的载体改为 **`ThrowTrajectory.Predict`**：它与 PhysX 用同一套半隐式欧拉（`v += g·dt; p += v·dt`）、
  同一份初速（`FlashLaunchVelocityToWorld`）、同一份重力与 dt。
  原用例 `LevelGeometryTests.Ballistics_And_WorldSemiImplicit_Match_Exactly` 已由
  `ThrowTrajectory_Predict_MatchesHandComputedSemiImplicitEuler` +
  `ThrowTrajectory_Predict_WithPhysXFrame_OnlyGravityActsOnY` 接替（2026-09-13）。
  ⚠ 不要因为"找不到那条老用例"就以为不变量丢了；**也不要**让任何人再写第二套 3D 积分。
- **瞄准落点**：射线打 XZ 地面（`aimPlane` 的法线从 +Z 改成 +Y，平面从 z=0 改成 y=0）。
- **选中拾取**：沿用 Flash 的屏幕空间 30px 规则（`SelectionRadiusPixels`），它本来就与维度无关，**不动**。

## 4. 水域与死亡（§4.4 全局规则）

- 水面 = 世界 Y 阈值常量 `WaterSurfaceY = -0.4`（`LevelGeometry.cs:197` 现行值；M4 起海洋平面亦按此对齐），不再是关卡 `waterTileY`。
- 判定 `IsBelowWater(worldY, WaterSurfaceY)`；方向无关——从 X 或 Z 任一侧掉出地面都会落到水面以下。
- 关卡数据里的 `waterTileY` 自此**仅作历史字段**保留，不参与运行时（地图已平坦化，与 Godot 基准的平面竞技场一致）。

## 5. 爆炸与击退（Phase 2 处理，方向：3D 球）

- Godot 基准是 3D 球形（`blast_radius` + 3D `distance`），Flash 的公式是 2D 平面内的
  `falloff = 1 - d/radius`、`damage = maxDamage * falloff`、击退 `5k` 径向 + `-6k` 向上。
- **合成口径**：距离用 **3D 距离**（含高度差），公式与常数仍取 Flash；
  击退 = **3D 径向单位向量 × 5k** 再叠加 **+Y × 6k** 的抬升项。
- 实现方式：给 `ExplosionResolver` 的坐标/目标加第三个分量（默认 0），
  使既有 2D 用例（z=0）结果**逐值不变**，从而 86 条 Combat 测试保持绿色；3D 运行路径传真实高度。

## 8. 遗留问题（收尾状态）

> 本节只记录**已收尾的判定结论**与**仍未收尾的项**；不写变更过程（变更见 Git 历史）。
> 更完整的任务板在 `docs/项目/待办事项.md`，跨会话状态在 `docs/项目/交接与恢复指南.md`。

- **AI 自抛落点质量项（已实现）**：Flash §6.2 的 `s += (t.ey − this.y) × −0.003` 在 2D 里比较的是
  **高度**轴（落点越高越好）。XZ 重投影后平面 y 变成**纵深**轴，原语义失效。3D 下「落点更好」定义为
  **预测落点与目标的 XZ 水平面像素距离越近越好**，故该项改为水平距离的线性罚项
  `s −= landingToTargetDistance × 0.003`（常量 `AiEvaluation.SelfLandingDistanceWeight`）。
  「目标」取敌方存活质心（`AiBattlefield.EnemyCentroid`；无存活敌人时它回落到 actor 自身位置，
  于是退化为「别把自己扔太远」，不会出现除零/空集合）。
  系数沿用原式的 0.003/px 斜率：典型 200px 落点偏差 ≈ −0.6，与紧随其后的质心项
  `pixelDiff / 500`、近敌项 `k ≤ 0.2` 同数量级，保持「线性小权重项」定位。
  注意 `s *= (1 + evilness)` 写在敌人循环内（§6.2 原版事实），当乘子前基分为负时 evilness 会放大惩罚——
  这是公式形态的固有性质，不作「修正」。
- **`Ballistics` 与 `ThrowTrajectory` 的分工（已定）**：XZ 竞技场下的 3D 抛物线逐步积分**只有**
  `ThrowTrajectory.Predict` 一处（预览、实弹、AI 同源）。`Combat/Ballistics` 只保留与维度无关的
  Flash 标量公式：弹弓初速 `TwangVelocity` / 满力距离 `FullForceDragDistance` / 撞地与撞墙速度积分。
  原 2D 平面预测方法 `PredictTrajectory`（`vy += weight` 的平面积分）已无运行时调用方，随 2D 模型废弃
  一并移除；**不要**再以它作为弹道预览的参照。
- **天空盒材质归位（已完成）**：`BattleSky.mat` 位于 `Assets/Art/Materials/`（环境资产，不属于 Prefab），
  由 `M2BattleSceneSetup.SkyMaterialPath` 引用。材质 **GUID 不变**，`Battle.unity` 的
  `m_SkyboxMaterial` 引用无需改动。

## 原版 2D→3D 的灵魂译法契约（2026-09-14 用户裁决："别抄成全在一排平面上，肯定是抄灵魂"）

原版是 **2D 侧视**：行 rowY 是**离水面的竖直高度**，不是深度。译法：
1. **rowY → 高度**：grass_top/甲板行的行号决定该岛悬浮高度（行号越大浮越高，贴水行贴水）；换算以水面行为 0 向上累计，相邻可互达岛高差 ≤ 投掷竖直跨越上限（≈3.3 世界单位），大高差保留原版"越水武器/绕路"语义。
2. **Z 深度是 3D 新增维度**：每岛 2-5 格厚度（按 X 跨度缩放），相邻岛 Z 错开制造纵深；单位在岛厚内按确定性规则分路。
3. **单位坐标语义不变**：gridX/gridY 仍是原版 (x, 行)；落位时 gridY 查所属岛 → 世界高度=岛高 + 岛内 Z 分路。
4. earth/岩石行=岛体厚度（视觉），grass_top/甲板行=可站顶面。
（旧"gridY→Z 直接铺平面"口径废止——那正是用户警告的"一排平面 pancake"。）

**【想象力条款（2026-09-14 用户二次裁决："翻译的时候发挥想象力，别被具体坐标框住，要是这关真的是 2D 变成 3D 的感觉"）】**
上述映射是**底线约束不是设计方法**。硬锚点只有四个：①单位出生在正确的岛的可行走面；②岛间相对高度次序保持；③隔水对与水距语义保持；④每关的记忆点必须在（大船/乌鸦巢/最高峰等）。底线之上是**重制设计师的自由**：岛形有机化（把像素方块读成"这座岛本来该有的样子"）、Z 纵深按 3D 构图摆布、尺寸 ±30% 呼吸、高度按可读性与手感调。每关先写一句"这关的灵魂是什么"再做布局；自检=原版玩家能否凭构图和记忆点认出"当年那关"。
