## 4. 环境铁律（踩过坑，不要重犯）

### 4.1 Unity 进程

- **batchmode 必须显式带 `-projectPath` 且带 `-nographics`**。缺 `-projectPath` 会打开 EditorPrefs 里的"最近工程"，
  可能污染/锁住别的项目——本项目曾因此产生**杀不死的僵尸进程**卡住 `Temp/UnityLockfile`，只能重启机器清理。
- **一次只跑一个 Unity 进程**（`Library/` 锁是独占资源）。多 agent 并行时，涉及 Unity 的验证由协调者串行执行。
- 本环境 **batchmode 没有可用的渲染路径**（不带 `-nographics` 会卡在 GfxDevice 创建），
  所以 `Camera.Render` / `ScreenCapture` **拿不到真实像素**——需要出图的验收必须用图形界面编辑器会话。

### 4.2 无头验证台（这是本项目最重要的效率杠杆）

`external/m2-harness/`（**不入库**，`external/` 已 gitignore）用 `dotnet` 直接引用 Unity 已编译程序集 + NuGet NUnit，
**不启动 Unity 就能编译工程源码并跑纯 C# 测试**，从而绕开 `Library/` 独占锁。

```bash
cd /f/VSCode/pirate-crew-3d-unity
mkdir -p external/harness-<你的域> && cp external/m2-harness/M2Harness.csproj external/harness-<你的域>/
cd external/harness-<你的域>
dotnet test  M2Harness.csproj -p:HarnessScope=Battle    # 跑测试
dotnet build M2Harness.csproj -p:HarnessScope=Runtime   # 只编译（快）
```

| `HarnessScope` | 编译范围 | 用途 |
| --- | --- | --- |
| `All` | `Scripts/**` + `Tests/*.cs` | 全量体检（含 31 条第 4.3 节所说的必然失败项） |
| `Data` | Core + `PirateCrew/Data` + `Tests/Data` | 数值层 |
| `Combat` | Core + `PirateCrew/Combat` + `Tests/Combat` | 战斗纯逻辑 |
| `Battle` | Core + Data + Combat + Battle + UI + `Tests/Battle` | 战斗组装层与弹体（**刻意排除 `Rendering/`**，避免并行 agent 互相干扰） |
| `Rendering` | Core + `PirateCrew/Rendering` | 描边 RendererFeature（需 URP 程序集） |
| `Runtime` | `Scripts/**` | 纯运行时编译检查 |
| `DataEditor` | `Scripts/**` + `Assets/Editor/**` | **进 Unity 之前抓编辑器脚本的编译错误** |

**能力边界（务必理解，别误判）**：`GameObject` / `MonoBehaviour` / `ScriptableObject` 的实例化走原生 `ECall`，
脱离 Unity 运行时必抛 `SecurityException`。实测 44 条 M1 EditMode 测试在该台里 13 通过 / 31 失败，失败全部因为
`new GameObject()`。**这不是回归，是固有边界。**

→ 因此本项目的核心逻辑**刻意分成两层**：纯 C# 静态类（可无头测，秒级迭代）+ MonoBehaviour 薄壳
（只拿引用、驱动、调纯函数）。**写新逻辑时请沿用这个分层**，否则会失去无头测试能力。

### 4.3 图像与观感

- **本会话模型可以消费图像**（2026-09-13 实测：`Read` 一张 PNG 能准确描述内容）。
  历史上"模型无法看图"的结论是错的，见 §9 的勘误。
- 编辑器打开时优先走 **MCP 的 `unity-mcp`**：`manage_camera` 的 `screenshot`
  （`capture_source` 选 `game_view`/`scene_view`、`include_image=true` 返回内联 PNG、`batch=surround/orbit` 多角度）、
  `manage_scene` 的 `scene_view_frame`。这样**不另开 Unity 进程、不抢锁**。
  - ⚠ **bridge 不会在首次打开工程时自启**（这是"编辑器开着但 MCP 报 `No Unity Editor instances found`"的根因，
    2026-09-13 实测查明）：
    - MCP for Unity v10 默认走 **stdio** 传输（ZCode 侧 `mcp-for-unity` 的 `--transport` 默认也是 stdio），
      编辑器侧必须监听本地 socket 才会被发现。
    - 包里负责启动的是 `StdioBridgeHost.StartAutoConnect()`，但 `StdioBridgeHost` 的**静态构造只在类被首次触达时执行**
      ——只打开工程、不打开 MCP 窗口时无人触达它。
    - `StdioBridgeReloadHandler` 的职责只是"domain reload **之后恢复**"（resume），不负责首次启动。
    - `HttpAutoStartHandler` 只管 HTTP 路径（`if (!useHttp) return;`），且要 `EditorPrefs` 的
      `MCPForUnity.AutoStartOnLoad` 为 true（默认关闭）——所以它救不了 stdio。
  - **本项目的处理（已生效并验证）**：`Assets/Editor/McpBridgeKick.cs`（`[InitializeOnLoad]`，反射调用
    `StdioBridgeHost` 以便包缺失时优雅降级）在编辑器加载时自动启动 bridge。
    菜单 `PirateCrew/MCP/启动 stdio Bridge` 可手动重触发；不需要了就删掉该文件（连同 `.meta`）。
  - **生效验证方式**（2026-09-13 实测通过）：`Assets/Editor/McpBridgeKick.cs.meta` 已生成
    + `netstat -ano | grep ":6400"` 显示 `LISTENING` 且 PID 等于 Unity 编辑器进程
    + `manage_scene get_active` 能返回场景。三者齐备即为正常。
  - **若报 no instances**（说明该脚本还没被编辑器导入）：让用户**点一下 Unity 窗口**
    （Auto Refresh 会在重获焦点时导入新脚本）或按 `Ctrl+R`，或打开 **`Window > MCP for Unity`** 手动启动。
    ⚠ 从外部无法强制编辑器刷新——包里**没有 FileSystemWatcher**，没有"投递命令"的通道，
    而唯一能提供进程间通信的东西恰好就是那个没起来的 bridge。所以这一步只能由用户在编辑器里完成。
  - 已实测可用的 MCP 工具（编辑器开着时）：`manage_scene`（get_active/get_hierarchy/load/save）、
    `read_console`、`manage_graphics`（`feature_list` 可列 URP Renderer Feature）、
    `manage_camera` 的 `screenshot`、`execute_menu_item`、`manage_gameobject`/`manage_asset` 等。
  - 排查用的实测判据：项目下 `Assets/UnityMCP/Log/` 是否存在、注册表
    `HKCU\Software\Unity Technologies\Unity Editor 5.x` 下有无 MCP 相关键
    （本项目实测该日志目录从未生成，属正常——McpLog 走 Editor.log）。
    注意 8080 端口常被其它程序（如 Steam 的 steamwebhelper）占用，别误判成 MCP；
    本项目的 bridge 端口是 **6400**（`HttpEndpointUtility.DefaultPort`）。
  - 判断依据：编辑器是否真的打开了本工程，看 `Temp/UnityLockfile` 是否存在、时间戳何时更新
    （Unity 打开工程还会生成 `ProjectSettings/PackageManagerSettings.asset`、`URPProjectSettings.asset`）。
  - **锁被占时不要跑 batchmode**（会失败或抢占）；此时要验证只能用 MCP，或等用户关掉编辑器。
  - **礼貌约束**：进 play mode 采集画面会占住编辑器（该工程期间用户不能编辑），
    且会加载场景、覆盖用户当前打开的场景。做这类操作前先跟用户确认时机。
- 判断动态手感/动画节奏时，静帧不够——`Read` 支持 MP4，**录一小段视频再看**。
- 程序化测量的退路仍然有效（`external/tools/` 下的 `ocr.ps1`、`color_blocks.py`、`imgdiff.py`），
  适合回答"画面是否全黑""某区域出现什么颜色""改前改后差多少"，但回答不了"好不好看"。

## 5. 门禁命令（改完代码后必跑）

```bash
U="F:/Unity/2022.3.62f1c1/Editor/Unity.exe"
P="F:/VSCode/pirate-crew-3d-unity/pirate-crew"

# 编译 + 导入（同时给新脚本生成 .meta）
"$U" -batchmode -nographics -quit -projectPath "$P" -logFile -

# EditMode 全量
"$U" -batchmode -nographics -projectPath "$P" -runTests -testPlatform EditMode \
  -testResults "F:/VSCode/pirate-crew-3d-unity/external/results-editmode.xml" -logFile -

# PlayMode 全量（把 EditMode 换 PlayMode）
```

**注意**：新脚本必须经过 Unity 导入才会生成 `.meta`（`.meta` 要入库，否则引用会漂）。手写 `.meta` 也可行
（字段结构与 Unity 生成的逐字段一致、GUID 为 32 位 hex 即可，Unity 会保留），但优先让 Unity 生成。

**关键验收技巧**：`BattleSmokeTests` 里有一条场景级用例，**未接线时 `Assert.Ignore`、接线后自动生效**。
所以看 PlayMode 结果的 `skipped` 是否归零，就能判断"场景是否真接线"——比只看有没有失败可靠得多。

## 6. 关键架构决策与理由（新会话不要重新论证）

记录"为什么"，避免推翻已定的东西：

1. **数值三层**：纯 C# `WeaponCatalog`/`CrewCatalog`/`LevelCatalog`（**真值来源**，可无头测）
   → ScriptableObject 定义类（引擎侧引用与策划调参）→ Editor 生成器 `M2DataAssetGenerator`（幂等产出 `.asset`）。
   理由：SO 实例化在无头环境必崩，但数值又必须可测；生成器里**不允许**出现第二份数值副本（避免真值分叉）。
2. **纯逻辑 / MonoBehaviour 分层**：见 §4.2。这不是风格偏好，是为了保住无头测试能力。
3. **程序集划分**：`PirateCrew.Runtime`（玩法）/ `PirateCrew.Tests`（EditMode）/ `PirateCrew.PlayModeTests` /
   `PirateCrew.Rendering`（**独立**，因需引用 URP 程序集）。
   - asmdef 引用**只写 name 或只写 GUID，双写会 duplicate**（M1 踩过）。
   - **Unity 只对名称以 `UnityEngine.` 开头的程序集自动引用**（uGUI 的 `UnityEngine.UI` 因此可用）；
     Cinemachine 这类普通包程序集必须显式写进 `references`——`PirateCrew.Runtime.asmdef` 已加 `"Cinemachine"`，
     所以相机代码用**强类型** `CinemachineVirtualCamera`，**不要退回反射**。
4. **跨模块通信**：只走 `Core/EventBus` 的字符串事件（snake_case），事件名与载荷必须登记在
   [EventBus事件契约.md](EventBus事件契约.md)。禁止 `GameObject.Find`、禁止跨模块裸 `GetComponent`。
   同模块内调用、生命周期通知、每帧高频数据**不走** EventBus。
5. **3D 化的四个决策**（写代码注释里已交代，改前先读）：
   - px→单位固定 **1 瓦片 = 1 单位（32px）**，常量集中在 `LevelGeometry`
   - Flash 的 y 轴向下 → Unity y 向上，**显式取负翻转**；注意 `ExplosionResolver.deltaVy` 是 Flash 约定算出的
   - 重力/力度按 `Time.fixedDeltaTime = 1/25` + `Physics.gravity = -19.53125` 配平，使 Flash 的
     `vy += w` 与 PhysX 半隐式欧拉**逐步严格相等**——这是"预览 = 实弹"的根基（Godot 版预览≠实弹是已知教训）
   - 落水即死取**全局规则**（Flash §4.1/§4.3；Godot 版只在单关开启属漂移）
6. **AI 随机数**：自写 xorshift32 而**非** `System.Random`——后者的算法在 .NET 8（验证台）与 Unity Mono 之间
   不同，同 seed 会分叉，会导致确定性测试在两边结果不一致。
7. **AI 的一处显式增强**：Flash §6 打分不含武器伤害，无法满足"能命中时优先高伤害"，故补
   `DamageScoreWeight = 0.5`（设 0 可恢复纯原版，两种模式都有测试）。
8. **弹体程序化构建**：`WeaponProjectile` 默认用图元 + 颜色在运行时造，`projectilePrefab` 为可选覆盖。
   好处是既有场景无需重新装配就能工作（新增必填序列化字段会让场景变成"未接线"）。

## 11. 下一步（M3 入口）

M3 = 船员管理循环：`Roster` / `Progression`（+NUnit）→ `CampaignManager` + 关卡选择 UI →
招募 → 编成 → 出战 → 结算打通 → 进度/名册接 `SaveManager`（M1 已就绪）。

动手前先读 `../game-3/pirate-crew-3d/modules/{crew_management,campaign}/`（各 3-4 个 `.gd`，是骨架）
与 `../game-3/docs/gdd.md`，并按 AGENTS 的「参照库强制」先找开源 Unity 参照。

若要先收尾 M2：优先做 §8 的两件（需要图形界面会话），或按 §7 清单逐项补。

### 11.1 收尾 M2 的首选任务：描边接线 + 出图（已有可复用路线）

背景见 §7 第一条——描边 Feature 挂了但**没有任何渲染器使用描边材质**，所以描边视觉上无效。
编辑器已可连 MCP（§4.3），因此这条链可以整条用 MCP 走完，不必手写脚本：

1. **建描边材质**：用 `PirateOutline.shader` 建两个材质资产（hover / selected 两态），
   放到 `Assets/Art/Materials/` 或 `Assets/Prefabs/PirateCrew/Materials/`。
   hover/selected 的观感基准在 `docs/描边Shader调试.md` 与 Godot 侧实现说明里
   （hover 淡白、selected 青 `#49d9d6f2`）。
2. **挂到单位**：优先改 `Assets/Editor/M2BattleSceneSetup.cs` 的船员 Prefab 生成段（保持程序化装配风格），
   在单位渲染器上设该材质；不要手改 Prefab YAML。改完**重新执行** `M2BattleSceneSetup.BuildAll`
   （注意顺序：`SceneSetup.BuildAll` 必须在 `M2BattleSceneSetup.BuildAll` **之前**，否则占位场景会覆盖战斗场景）。
3. **进 play mode 打一场**：用 `manage_editor`（`play`）或 `execute_menu_item`。
   如需先加载场景用 `manage_scene` 的 `load`（**会覆盖用户当前打开的场景，先确认时机**）。
4. **逐档采集**：跑菜单 `PirateCrew/Rendering/采集描边调试截图`（`execute_menu_item`），
   或直接用 `manage_camera` 的 `screenshot`（`include_image=true`）逐档取图。
5. **看图判断并微调**：对照 `docs/描边Shader调试.md` 里"每档应看到什么"，自己判断偏离后改
   `_OutlineWidth`/`_OutlineColor`/`_DebugMode` 等参数再采集。**观感与手感的最终验收要交给用户**（§8）。

出图后按 AGENTS 的图形学调试截图规范补 `export/描边-debug/` 与说明页（截图入库策略见 AGENTS 注意事项）。
